# 第31章 —— 一条命令生成一个项目

代码位置：`packages/ainative-cli/src/ainative_cli/main.py`、`scaffold.py`

## 从"复制上一个项目的文件夹"到脚手架工具

如果你观察过团队里怎么开一个新项目，很可能会看到这样的场景：有人打开上一个项目的文件夹，手动复制`pyproject.toml`、`README.md`、几个入口文件，再一处处修改项目名字——这个过程很容易漏改某个地方（比如`pyproject.toml`里的`name`字段忘了改，或者复制过来的依赖列表里带着上一个项目根本用不到的包）。`ainative-cli`要解决的就是这个问题：**用一条命令，按照一份"模板"，生成一套内容正确、依赖精简的新项目骨架**。

## argparse：一个"子命令"结构的命令行工具

这个包用Python标准库的`argparse`来解析命令行参数。理解`ainative new my_app --type minimal`这条命令是怎么被解析的，关键在于"子命令"这个概念：

```python
parser = argparse.ArgumentParser(prog="ainative", description="AI Native Framework CLI")
subparsers = parser.add_subparsers(dest="command")

new_parser = subparsers.add_parser("new", help="生成一个新项目骨架")
new_parser.add_argument("project_name", help="新项目的名称")
new_parser.add_argument("--type", dest="project_type", default="minimal", choices=sorted(TEMPLATES), ...)
new_parser.add_argument("--force", action="store_true", help="目标目录已存在且非空时仍然覆盖写入")

subparsers.add_parser("list-types", help="列出全部可用的项目类型")
```

像`git commit`、`git push`这样"一个主命令+一个子命令"的结构在命令行工具里很常见，`argparse`原生支持这种模式——`add_subparsers()`创建一个"子命令注册表"，之后每个`add_parser(名字)`注册一个具体的子命令，每个子命令可以有自己独立的一组参数。`choices=sorted(TEMPLATES)`这个细节值得留意：**它把"这个参数只能是几个固定值之一"这条校验规则，直接交给`argparse`框架去做**——用户如果输错了模板名（比如打错字），`argparse`会自动报错并退出，不需要在代码里手写一段`if project_type not in TEMPLATES: raise ...`的校验逻辑。

## `store_true`：命令行"开关"参数

`new_parser.add_argument("--force", action="store_true", ...)`这一行值得单独讲——它定义的不是"需要跟一个值的参数"（比如`--type minimal`那样），而是一个**开关/旗标参数**：命令行里出现了`--force`这个词本身，解析结果里对应的属性就自动变成`True`；完全不写这个参数，属性就是`False`。这是命令行工具里表达"是/否"这种二元选项的标准方式。

## 一个平台兼容性的真实细节：Windows下的编码问题

`main.py`的开头有这样一段代码：

```python
if sys.platform == "win32" and hasattr(sys.stdout, "reconfigure"):
    sys.stdout.reconfigure(encoding="utf-8")
    sys.stderr.reconfigure(encoding="utf-8")
```

这行代码要解决的是一个真实存在、容易被忽略的问题：**Windows终端在某些语言/区域设置下，标准输出的默认字符编码不是UTF-8**。如果CLI工具要打印中文（比如`list-types`命令里模板的中文描述），不做这个设置，程序可能会在Windows上因为编码不匹配而直接崩溃报错，或者显示出乱码。`hasattr(sys.stdout, "reconfigure")`这个检查是一层防御——较老的Python版本或者某些特殊的输出重定向场景下，`sys.stdout`可能压根没有`reconfigure`这个方法，直接调用会导致`AttributeError`，先用`hasattr`探测一下再调用，是更保险的做法。这提醒我们：**写一个要在多个操作系统上运行的命令行工具，字符编码往往是一个容易被忽视、却真实会导致崩溃的细节**。

## `main(argv=None)`：为什么函数要接受一个可选参数

```python
def main(argv: list[str] | None = None) -> int:
    parser = _build_parser()
    args = parser.parse_args(argv)
    ...
```

这个函数被设计成既可以真正从命令行调用（`argv`留空，`argparse`内部会自动读取真实的`sys.argv`），也可以在测试代码里直接传入一个模拟的参数列表：

```python
main(["new", "my_app", "--type", "minimal"])
```

这样写测试**不需要真的启动一个子进程去执行一整条命令行字符串**，而是直接在同一个Python进程内调用`main()`函数、检查它的返回值和副作用（比如是否真的生成了预期的文件）——这是一种很实用的"让命令行工具的核心逻辑变得可以被单元测试直接调用"的设计模式，值得在自己写CLI工具时借鉴。

## 本章小结

- 子命令结构（`argparse`的`add_subparsers`）是命令行工具里"一个主命令+多个子命令"这种常见结构的标准实现方式。
- 把参数合法性校验（比如"只能是这几个值之一"）交给`argparse`框架本身去做，比手写校验逻辑更简洁、也更不容易遗漏。
- 跨平台命令行工具需要留意字符编码这类容易被忽视的细节——Windows终端的默认编码可能不是UTF-8，输出中文会导致崩溃或乱码。
- 让`main()`函数接受一个可选的`argv`参数，能让命令行工具的核心逻辑在测试中被直接调用，而不需要真的启动子进程模拟命令行输入。

## 动手做

```python
from ainative_cli.main import main
import tempfile, os

with tempfile.TemporaryDirectory() as tmpdir:
    exit_code = main(["new", "demo_project", "--type", "minimal", "--dir", tmpdir])
    print("退出码：", exit_code)
    print("生成的文件：", os.listdir(tmpdir))
```

## 面试可能会问

**问：你会怎么设计一个命令行工具，让它的核心逻辑既能真正在终端里运行，又方便写自动化测试？**

答题思路：讲清楚"让入口函数接受一个可选的参数列表（默认从真实命令行读取，也可以在测试里传入模拟参数）"这个模式，说明它避免了"必须真的启动一个子进程去测试CLI行为"这种更笨重、更慢的测试方式。如果能补充"命令行参数的合法性校验应该优先交给解析框架本身处理，而不是散落地手写"，会显得对命令行工具设计有更全面的认识。
