# 第26章 —— 什么时候需要一个图

代码位置：`packages/ainative-workflow/src/ainative_workflow/graph.py`

## 一个容易被"技术偏好"带偏的决定

假设你要做一个"报销审批"功能：员工提交报销单，系统先校验金额和发票，金额超过阈值的需要主管审批，主管迟迟不处理的要有超时兜底，最后再写入财务系统。

你打开搜索引擎，看到一堆讲"多agent编排"、"workflow graph"、"LangGraph"的文章，很容易产生一个念头："这是个有阶段、有依赖、有分支的流程,我应该建一个DAG（有向无环图）编排引擎来管它。"

这个念头本身没有错——DAG确实很适合这类问题。但`ainative-workflow`这个包最值得学的第一课，恰恰是**它差点没有被建出来**。它的模块docstring里写了一段不常见的坦白：

```python
"""轻量DAG工作流编排引擎。

这是ainative-workflow的核心新设计——两个被审计的真实生产项目都没有采用
"图编排引擎"这条路径（都选择了"单agent+分阶段提示词+HITL中断"的更轻量
方案，且有真实案例证明过早建设"跨agent网关/编排基础设施"容易变成从未
被使用的负资产）。本模块面向确实需要"多个明确阶段、阶段间有依赖关系、
支持条件分支、支持从某个节点暂停后恢复"这类场景，提供一个足够轻量、
不引入任何外部依赖（不需要Postgres/Redis/专门的workflow服务）的DAG
执行引擎，而不是照搬某个真实项目里不存在的代码。
"""
```

翻译成人话：审计过的两个真实生产项目，需求上跟"报销审批"这类场景很像，但工程师们最终**都没有引入图编排引擎**。它们选择了"一个agent、把流程拆成几段提示词依次执行、遇到需要人工确认的地方就用HITL中断一下"这条更朴素的路径。而且有真实的反面案例：曾经有团队提前搭好了一整套"跨agent网关/编排基础设施"，指望以后用得上，结果这套东西从来没有真正被用起来过，变成了没人维护、也没人敢删的"负资产"。

这是本章要讲的第一个、也是最重要的工程判断力：**基础设施要跟着真实需求走，不要跟着"这个技术很酷/大家都在用"走**。DAG引擎不是被禁止使用，而是要留给"确实需要"的场景——那具体是什么场景？

## 什么时候真的需要一张图

把docstring里的判断标准拆开看，DAG引擎值得被引入，通常是因为同时满足这几点：

第一，**流程有多个明确的阶段**，而不是一段连续的、由同一个agent自己决定"下一步做什么"的自由对话。如果你的流程本质是"agent不断思考、调用工具、再思考"，那是agent循环的问题，不是DAG的问题。

第二，**阶段之间有依赖关系**，比如"校验"必须在"提交"之后、"审批"必须在"校验通过"之后——这种"谁必须在谁之前"的约束关系,画出来会是一张图，而不是一条直线。如果所有阶段永远按固定顺序依次执行、没有分支也没有并行的可能，一个简单的函数调用链（`step1(); step2(); step3()`）就够了，不需要一个通用的图执行引擎。

第三，**需要条件分支**——某些节点要不要执行,取决于前面节点算出来的结果（比如报销金额超过阈值才需要主管审批）。

第四，也是最关键的一点：**支持从某个节点暂停后恢复,而不是从头重跑**。真人审批往往需要几小时甚至几天,这段等待时间里,程序不能一直占着一个线程傻等,而是要把"跑到哪儿了"这件事完整地记录下来,人做完决定后再从那个点继续,前面已经做完的步骤不能重来一遍(想象一下报销审批系统每次主管点了"批准"之后,程序又把发票OCR识别重新跑一遍——这是纯粹的浪费,而且如果这一步本身有副作用,比如"给财务系统发一条通知",重跑还可能导致这条通知被发两次)。

如果你的场景不满足"暂停恢复"这一条,只是简单的"先做A、再做B",那么用一个agent配合分阶段提示词、遇到需要人工确认的地方直接`raise`一个中断异常,可能就已经足够,不需要一整套图执行引擎的复杂度。这正是那两个被审计的真实项目做出的选择。工程判断力体现在这里:先问"我的场景是否真的需要暂停/恢复、条件分支、显式依赖这几样东西",而不是先问"用什么框架看起来更专业"。

## 数据模型:一个节点长什么样

想清楚"要不要用"之后,我们来看这个引擎具体是怎么建模的。核心概念只有三个:`WorkflowNode`(节点定义)、`WorkflowRun`(一次执行的状态)、`NodeStatus`(节点状态)。先看节点:

```python
@dataclass(frozen=True)
class WorkflowNode:
    """DAG里的一个节点。"""

    name: str
    fn: NodeFn
    depends_on: tuple[str, ...] = ()
    output_key: str | None = None
    condition: ConditionFn | None = None
    skip_if_dependency_skipped: bool = True
```

`WorkflowNode`是`frozen=True`的——一旦定义好一个节点(比如"校验发票"这个节点),它就不应该在运行过程中被改动。这跟下面马上要看到的`WorkflowRun`形成鲜明对比:`WorkflowRun`是可变的,因为它记录的是"这一次具体跑的进度",每执行完一个节点,进度就要往前推进一格。这是这份代码里"什么该冻结、什么不该"的设计原则——**定义(不变)和状态(可变)要分开建模**,这个原则在你以后设计任何"配置 vs 运行时状态"的系统时都用得上。

`fn`是这个节点真正要执行的逻辑,它的类型是这样声明的:

```python
NodeFn = Callable[[dict[str, Any]], Any]
ConditionFn = Callable[[dict[str, Any]], bool]
```

这两行不是在定义类,而是给一长串`Callable[...]`类型起了个短名字——`NodeFn`就等同于"一个函数,接收一个`dict`,返回任意类型";`ConditionFn`是"一个函数,接收一个`dict`,返回`bool`"。之后代码里到处写`NodeFn`,不用每次都重复这一长串类型注解。

节点接收的这个`dict`,就是所有节点共享读写的上下文——`fetch`节点算出一个原始数据,写进`context["raw"]`;`validate`节点从`context["raw"]`里读出数据做校验,再把校验结果写进`context["is_valid"]`;下一个节点又能读到这个`is_valid`。节点之间"传递数据"完全靠读写同一个字典,没有更复杂的消息传递机制——这也是"轻量"的一种体现。

`output_key`决定了节点返回值写去`context`的哪个key;如果留空(`None`),返回值直接被丢弃,这个节点被认为是"纯副作用节点"(比如只是发一条通知,不需要把返回值存起来给后面用)。

`depends_on`是一个节点依赖的上游节点名称的元组——注意类型是`tuple[str, ...]`而不是`list[str]`,这不是随意选择:因为`WorkflowNode`整体是`frozen=True`的,如果字段用可变的`list`,理论上还是可以拿到这个list之后原地修改它(参考第5章讲过的"frozen锁不住字段指向的可变对象内部"这个坑),用不可变的`tuple`能从类型层面更彻底地表达"这份依赖关系定义好之后就不该再变"的意图。

## 条件跳过:一个节点被跳过,连带的下游怎么办

`condition`和`skip_if_dependency_skipped`这两个字段,负责实现"根据前面的结果决定要不要跳过某个节点"这件事。判断逻辑集中在`_should_skip`方法里:

```python
def _should_skip(self, node: WorkflowNode, run: WorkflowRun) -> bool:
    for dep in node.depends_on:
        if run.node_status[dep] == NodeStatus.SKIPPED and node.skip_if_dependency_skipped:
            return True
    return node.condition is not None and not node.condition(run.context)
```

这个方法要回答两个层次的问题。第一层:**我依赖的上游节点,有没有被跳过?**如果有,而且我自己没有声明"即使上游被跳过我也要继续"(即`skip_if_dependency_skipped`保持默认的`True`),那我也应该被跳过——这背后的直觉是,大多数情况下"上游被跳过"意味着上游本该产出的数据根本不存在,我这个节点缺少必要的输入,硬跑下去大概率会报错或者产出没有意义的结果,不如干脆也跳过。但这不是唯一选择:如果某个步骤本身是"可选的锦上添花"(比如"发一条可有可无的提醒"),即使它被跳过了,后面的主流程也应该正常继续,这时候把`skip_if_dependency_skipped`设为`False`就能表达这种"上游跳过不影响我"的语义。

第二层,如果第一层不成立(没有因为依赖被跳过而连带跳过),再看节点自己声明的`condition`回调——`node.condition is not None`,如果压根没声明条件回调,视为"总是执行",不跳过;声明了的话,调用它、传入当前`context`,回调返回`False`就意味着跳过。回到报销审批的例子:"主管审批"这个节点的`condition`可以写成`lambda ctx: ctx["amount"] > 10000`,金额不超过阈值时,这个节点被跳过,流程直接走向"自动通过"。

## `_execute`循环的整体结构

把节点定义、跳过判断都理解了之后,再看驱动整个执行过程的`_execute`方法的骨架就很自然了(完整的暂停/恢复/异常处理逻辑我们放到第28章详细讲,这里先看整体结构):

```python
async def _execute(self, run: WorkflowRun) -> WorkflowRun:
    for name in self._order:
        status = run.node_status[name]
        if status in (NodeStatus.COMPLETED, NodeStatus.SKIPPED):
            continue

        node = self._nodes[name]

        if self._should_skip(node, run):
            run.node_status[name] = NodeStatus.SKIPPED
            continue

        run.node_status[name] = NodeStatus.RUNNING
        try:
            result = node.fn(run.context)
            if hasattr(result, "__await__"):
                result = await result
        except WorkflowPaused as paused:
            ...
        except Exception as exc:  # noqa: BLE001
            ...

        if node.output_key is not None:
            run.context[node.output_key] = result
        run.node_status[name] = NodeStatus.COMPLETED
        run.completed_order.append(name)

    return run
```

这里有一个值得单独拎出来讲的小技巧:`hasattr(result, "__await__")`。`WorkflowNode.fn`既可以是普通同步函数(直接返回结果),也可以是`async def`定义的协程函数(调用后返回一个"还没有真正执行完、需要被await"的对象)。`__await__`是Python所有协程对象都具备的一个特殊方法,`hasattr(result, "__await__")`就是在问"这个返回值,是不是一个可以被await的东西"。如果是,就`await`它拿到真正的结果;如果不是,`result`原样使用。这样一来,调用方在定义节点时,完全不需要提前告诉引擎"我这个节点是同步的还是异步的",引擎自己通过检查返回值的"长相"就能自动识别——这是Python里典型的"鸭子类型"(duck typing)风格:不关心你是什么类型,只关心你有没有我需要的那个方法/属性。

循环本身按照构造时算好的拓扑顺序(下一章会详细讲这个顺序是怎么算出来的)依次遍历每个节点,靠`status in (COMPLETED, SKIPPED)`这一行自然地跳过已经处理过的节点——这一行代码同时服务了"第一次运行"和"从暂停点恢复后继续跑"两种场景,不需要为"恢复"单独写一套逻辑,这也是一种值得学习的简化:与其为不同的调用路径各写一套流程,不如让状态检查本身自然地区分"这个节点该不该被(重新)处理"。

## 本章小结

- 引入一个通用的DAG编排引擎是有成本的决定,不是默认选项——两个真实审计过的生产项目都选择了"单agent+分阶段提示词+HITL中断"这条更轻量的路径,过早建设"以后可能用得上"的编排基础设施,真实发生过变成从未被使用的负资产的案例。
- 真正需要DAG引擎的信号是:流程有多个明确阶段、阶段间有显式依赖关系、需要条件分支、并且需要"暂停后从中间恢复而不是从头重跑"——最后一条尤其关键,如果你的场景不需要长时间等待人工输入,更轻量的方案往往够用。
- `WorkflowNode`(节点定义)用`frozen=True`,`WorkflowRun`(执行状态)不加`frozen`——定义是不变的,状态是随执行推进不断变化的,这两者要在设计上分开。
- 条件跳过分两层判断:先看依赖的上游是否被跳过(默认连带跳过,除非显式声明`skip_if_dependency_skipped=False`),再看节点自己的`condition`回调。
- `hasattr(result, "__await__")`是一种鸭子类型检测手段,让同一个执行引擎能够无差别地支持同步函数节点和`async def`协程函数节点,调用方不需要显式声明。

## 动手做

用真实的`Workflow`/`WorkflowNode` API,搭一个"金额小于1000自动通过、否则跳到审批节点"的最小流程,体会条件跳过是怎么生效的:

```python
import asyncio
from ainative_workflow import Workflow, WorkflowNode


def fetch(ctx: dict) -> dict:
    return {"amount": 500}


def auto_approve(ctx: dict) -> str:
    return "auto-approved"


def manual_approve(ctx: dict) -> str:
    return "manually-approved"


wf = Workflow([
    WorkflowNode(name="fetch", fn=fetch, output_key="raw"),
    WorkflowNode(
        name="auto_approve", fn=auto_approve, depends_on=("fetch",),
        output_key="decision", condition=lambda ctx: ctx["raw"]["amount"] < 1000,
    ),
    WorkflowNode(
        name="manual_approve", fn=manual_approve, depends_on=("fetch",),
        output_key="decision", condition=lambda ctx: ctx["raw"]["amount"] >= 1000,
    ),
])

run = asyncio.run(wf.run({}))
print(run.node_status)   # auto_approve应为COMPLETED,manual_approve应为SKIPPED
print(run.context["decision"])
```

试着把`fetch`里的金额改成`5000`,再跑一遍,观察两个节点的状态是怎么反过来的。

## 面试可能会问

**问:什么时候你会选择引入一个DAG编排引擎,什么时候不会?**

答题思路:不要一上来就讲DAG本身怎么实现,先讲判断标准——流程是否有多个明确阶段、阶段间是否有真实的依赖/分支关系、最关键的是是否需要"暂停后从中间恢复"这个能力。如果能举出反例(比如"如果只是一个agent循环调用工具、自己决定下一步,那不需要DAG,那是agent循环的问题"),并提到"过早建设编排基础设施可能变成没人用的负资产"这类真实工程教训,会比单纯背诵DAG的技术优点更有说服力,体现的是你有判断"什么时候不该用某个技术"的能力,而不只是知道这个技术存在。
