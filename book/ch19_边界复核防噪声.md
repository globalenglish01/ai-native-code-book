# 第19章 —— 边界复核防噪声

代码位置：`packages/ainative-eval/src/ainative_eval/gate.py`（`maybe_recheck_boundary`函数）

## 一个真实场景："差一点点"到底算不算过

延续上一章的场景：你的部署门禁里有一项检查是LLM评分——让一个模型给"这次AI回复的语气是否得体"打个0到1之间的分数，`green_min`设成0.8，也就是说0.8分以上才算GREEN、可以放行。

现在假设某次发布，这项检查跑出来的分数是0.79。只差0.01分。你会怎么办？

如果严格按照`status_from_score`的逻辑（第18章讲过），0.79没有达到0.8，会被判成YELLOW甚至直接拦截。但这里有个现实问题：**LLM打分本身是有随机性的**——同样的输入，同样的评分prompt，同一个模型问两次，很可能一次给0.79、一次给0.82。如果这次评分恰好抽到了偏低的那一次，一个"实际上完全合格"的发布，会因为一次评分的运气不好被硬生生拦下来。反过来，如果这次评分恰好偏高，一个真正有问题的发布也可能侥幸放行。**卡在阈值边缘的分数，往上一次评分和往下一次评分之间的差别，很可能只是噪声，不是真实质量的变化**。

那能不能干脆把每次评分都多跑几次取平均，从根源上消除这个问题？可以，但那意味着**所有的评分——不管离阈值远近——都要多付出几倍的成本**。一个分数是0.95的检查，跟一个分数是0.5的检查，其实都不需要担心"差一点点就翻盘"的问题，因为它们离阈值足够远，噪声不太可能真的影响最终判定。真正需要担心的，只有那些卡在阈值附近的分数。

`maybe_recheck_boundary`要解决的就是这个问题：**只在分数真的落在阈值附近的容差区间里时，才多花一次成本重新评一次，成本只在真正需要的地方付出**。

## 完整函数：一步步拆解

```python
def maybe_recheck_boundary(
    score: float,
    green_min: float,
    *,
    boundary_tolerance: float,
    recheck_max_diff: float,
    rescore: Callable[[], float | None],
) -> tuple[float, bool, str]:
    if abs(score - green_min) > boundary_tolerance:
        return score, False, ""

    recheck_score = rescore()
    if recheck_score is None:
        return score, False, "(boundary recheck failed to produce a score, using first result)"

    diff = round(abs(score - recheck_score), 4)
    if diff > recheck_max_diff:
        return score, True, (
            f"boundary recheck inconsistent: first={score} recheck={recheck_score} "
            f"(diff {diff} > {recheck_max_diff}), needs manual review"
        )
    conservative = min(score, recheck_score)
    return conservative, False, (
        f"boundary recheck consistent: first={score} recheck={recheck_score} "
        f"(diff {diff} <= {recheck_max_diff}), using conservative value={conservative}"
    )
```

签名上先看两个细节。第一，函数参数列表里的`*`——这是Python里"强制关键字参数"的写法，`*`之后的所有参数（`boundary_tolerance`、`recheck_max_diff`、`rescore`）调用时必须写成`maybe_recheck_boundary(0.79, 0.8, boundary_tolerance=0.05, recheck_max_diff=0.1, rescore=my_rescore_fn)`这样明确带上参数名，不能只按位置传值。这对这个函数特别重要——它有好几个都是`float`类型的参数，如果允许按位置传参，很容易把`boundary_tolerance`和`recheck_max_diff`的顺序传反而完全不自知（两个都是形似的小数，编译期和运行期都不会报错，只会悄悄产生一个错误的判定阈值）。第二，`rescore: Callable[[], float | None]`——一个不接收参数、返回`float`或`None`的函数。这里"怎么重新评分"这件事本身被完全抽象成了一个可替换的函数，`maybe_recheck_boundary`自己不关心复核到底是重新调用一次LLM、还是换一个更严格的模型、还是走别的什么流程，这些细节全部由调用方通过闭包提前准备好，传进来的只是"调用它就能拿到一个新分数（或者失败时的None）"这一个动作。

## 第一步：判断是否真的落在边界里

```python
if abs(score - green_min) > boundary_tolerance:
    return score, False, ""
```

`abs(score - green_min)`算的是"这次分数离`green_min`门槛线有多远"——不管是高于还是低于，只看距离。如果这个距离已经超出了`boundary_tolerance`（比如设成0.05），说明这次分数离边界够远，不太可能是"评分噪声"导致的误判，直接采信首次分数，不触发复核，`needs_review`给`False`，`note`给空字符串（表示"这次压根没有触发复核这回事"）。

这里有个值得注意的地方：**这个判断对偏高和偏低的分数是对称的**。也就是说，一个0.84分（比0.8高出0.04）和一个0.76分（比0.8低了0.04），只要都落在容差范围内，都会触发复核。也许你会觉得奇怪——0.84明明已经"超过"了门槛，为什么还要多此一举地复核？原因和开头场景里说的一样：0.84同样可能是"运气好抽到了偏高的一次"，真实水平可能只有0.78。边界复核的目的不是"帮压线的分数争取通过"，而是"确认这个分数本身站不站得住脚"，所以无论压线偏高还是偏低，都一视同仁地触发复核。

## 第二步：复核本身也可能失败

```python
recheck_score = rescore()
if recheck_score is None:
    return score, False, "(boundary recheck failed to produce a score, using first result)"
```

`rescore()`调用的可能是又一次LLM调用——LLM调用本身就可能因为超时、解析失败等各种原因拿不到有效分数（回忆一下第14章讲的`judge_response`，正是因为judge模型的输出经常需要"防御性解析"）。如果复核这一步本身失败了，没有第二个分数可以比较，这里的处理是**退回采信首次评分，而不是让整个检查跟着失败**——复核机制本身出故障，不应该比"没有触发复核"更糟糕。同时`note`里写明了原因，方便日后排查日志时知道"这次为什么没有真正完成复核"，而不是让人困惑"明明应该触发复核的分数，为什么日志里没看到两次评分的对比"。

## 第三步：两次分差决定信不信这个分数

```python
diff = round(abs(score - recheck_score), 4)
if diff > recheck_max_diff:
    return score, True, (
        f"boundary recheck inconsistent: first={score} recheck={recheck_score} "
        f"(diff {diff} > {recheck_max_diff}), needs manual review"
    )
conservative = min(score, recheck_score)
return conservative, False, (
    f"boundary recheck consistent: first={score} recheck={recheck_score} "
    f"(diff {diff} <= {recheck_max_diff}), using conservative value={conservative}"
)
```

`round(x, 4)`把差值四舍五入保留4位小数——这是为了避免浮点数计算天然存在的极小误差（比如`0.1 + 0.2`在计算机里可能算出`0.30000000000000004`这种结果）让展示出来的分差看起来不整洁。

真正的判定逻辑分两条路：

**分差在`recheck_max_diff`以内**：两次评分基本一致，说明这个分数是"稳"的，不是噪声导致的偶然结果。这时候用`min(score, recheck_score)`——**取两次里较低的那个，而不是平均值**——作为最终判定依据。为什么选更保守的那个？源码注释直接点明了这是刻意的设计倾向："治理门控这类'宁可错杀不可放过'的场景，选择偏保守的数值是刻意的设计"。想象两次评分是0.83和0.79，平均是0.81（依然过关），但取较低值是0.79（不过关）。治理门禁面对的是"部署前的最后一道关"，一旦放行出了问题，代价往往比"多复核一次、多等一会儿"大得多，所以这里宁可选择让判定更严格的那个数字，而不是"各打五十大板"式的平均。

**分差超过`recheck_max_diff`**：两次评分差距太大，说明这次判定本身就不稳定——一次觉得达标、一次觉得不达标，没有理由武断地采信任何一次结果。这时候返回`needs_review=True`，交给人工确认，而不是随便选一个数字硬凑一个自动判定。注意这个分支里`score`（首次分数）仍然被原样返回，但源码注释特意说明**这个返回值实际上不会被下游用来做"是否放行"的决定**——因为`needs_review=True`会让上层的状态机（第18章讲的`decide()`）直接把这个维度归入`NEEDS_REVIEW`分支，直接计入拦截原因；这里返回的`score`只是用来展示/记录，方便日志里留一份"复核前的分数长什么样"的痕迹。

## 为什么这是"防噪声"而不是"放宽标准"

这一章标题是"边界复核防噪声"，值得强调一下这个词用得很精确：这个机制**不是在放宽通过标准**。它不会让一个明显不合格的0.5分变成合格，也不会让一个稳稳当当的0.95分被平白无故地拉低。它做的事情，是**专门盯住"落在阈值附近、单次结果不足以自证靠谱"的那一小撮分数，多花一次成本去确认这次结果到底稳不稳**——如果稳，就按更保守的那个数字判定；如果不稳，干脆不装作能自动判定，坦诚地交给人。这是"把稀缺的复核成本，精确地花在真正有噪声风险的地方"这个工程原则的具体体现——而不是无差别地对所有评分都做多次采样（那样成本会成倍上涨），也不是完全不做任何复核（那样卡在边界的判定质量会被噪声左右）。

## 本章小结

- 卡在阈值附近的分数最容易被"评分本身的随机噪声"误导——往上一点还是往下一点，可能只是运气，不是真实质量的变化，边界复核机制就是为了识别并处理这种情况。
- 只在分数落在`green_min ± boundary_tolerance`范围内才触发复核，把稀缺的复核成本精确花在真正有噪声风险的地方，而不是无差别地对所有分数都多次采样。
- 边界复核对偏高、偏低的分数一视同仁地触发——目的是确认这个分数本身站不站得住脚，不是专门为压线分数"网开一面"。
- 两次分差在容许范围内时，取较低（更保守）的那个分数作为最终判定依据，而不是取平均——治理门禁这类场景刻意选择偏保守的判断倾向。
- 分差过大说明判定本身不稳定，不应该武断地采信任一次结果，而是标记`needs_review=True`交给人工确认——这不是"放弃自动化"，而是诚实地承认"这次自动判定没有足够把握"。

## 动手做

```python
from ainative_eval import maybe_recheck_boundary

# 场景1：分数离阈值很远，不触发复核
result = maybe_recheck_boundary(
    0.95, green_min=0.8, boundary_tolerance=0.05, recheck_max_diff=0.1,
    rescore=lambda: 0.5,  # 就算这里返回一个很离谱的分数，也不会被调用到
)
print(result)  # (0.95, False, "")

# 场景2：分数卡在边界，复核结果一致 —— 采信更保守的那个
result = maybe_recheck_boundary(
    0.79, green_min=0.8, boundary_tolerance=0.05, recheck_max_diff=0.1,
    rescore=lambda: 0.82,
)
print(result)

# 场景3：分数卡在边界，复核结果差距很大 —— 交给人工复核
result = maybe_recheck_boundary(
    0.79, green_min=0.8, boundary_tolerance=0.05, recheck_max_diff=0.1,
    rescore=lambda: 0.55,
)
print(result)

# 场景4：复核本身失败（比如LLM调用超时）
result = maybe_recheck_boundary(
    0.79, green_min=0.8, boundary_tolerance=0.05, recheck_max_diff=0.1,
    rescore=lambda: None,
)
print(result)
```

试着调整`boundary_tolerance`和`recheck_max_diff`这两个参数，观察同样一个0.79分在不同容差设置下，是直接采信、触发复核后一致、还是触发复核后转入人工复核。

## 面试可能会问

**问：如果用LLM打分来做自动化的发布门禁，你会怎么处理"分数卡在阈值边缘"这种情况？**

答题思路：先说明问题的本质——LLM评分有随机性，卡在阈值边缘的分数，一次评分的运气好坏可能直接决定放行还是拦截，这不是真实质量差异，而是噪声。然后讲边界复核的思路：只在分数落在阈值附近的容差区间内才触发一次重新评分（强调"只在需要时才付出成本"这个考量，而不是无差别多次采样），复核结果一致就取更保守的那个值（说明"治理场景宁可错杀不可放过"的取向），复核结果不一致就诚实地标记为需要人工复核，而不是硬凑一个自动判定。如果能补充"这个机制不是放宽标准，而是把稀缺的复核成本精确用在真正有噪声风险的地方"，会体现出你理解的是这个机制的设计动机，而不只是记住了它的实现步骤。
