# 第11章 —— 背压与限流

代码位置：`packages/ainative-guardrail/src/ainative_guardrail/backpressure.py`

## "被动发现"和"主动预警"的区别

假设你的系统有一个任务队列，Agent不断往里面塞待处理的任务，另一个消费者进程不断把任务取出来处理。如果生产速度长期大于消费速度，队列会持续增长——传统情况下，这类问题往往是"下游超时了""内存爆了"之后才被动发现，这时候故障已经真实发生，用户已经受到影响。

`ainative-guardrail`的`backpressure.py`模块想解决的，是把这类问题的发现时机**提前**——本章要看的两个类都遵循同一个原则："提前告警而不是事后发现"。

## `QueueBacklogMonitor`：队列深度预警，带"去抖"

最直接的想法是"队列深度超过阈值就告警"，但一个容易被忽略的细节是——如果队列长期停留在阈值以上，每次检查都打一条警告日志，运维的日志系统会被刷屏，反而让真正重要的信号被淹没。`QueueBacklogMonitor`用一个简单的状态标记解决了这个问题：

```python
def record_depth(self, current_depth: int) -> bool:
    self.peak_depth = max(self.peak_depth, current_depth)
    if current_depth >= self._warn_threshold:
        if self._warned:
            return False   # 已经告警过，这次不重复打印
        self._warned = True
        logger.warning("[Backpressure] queue depth %d has reached the warn threshold (%d)", ...)
        return True
    self._warned = False   # 深度回落到阈值以下，重置标记
    return False
```

这个逻辑的关键在于`self._warned`这个标记：**第一次跨越阈值时才真正打印警告，之后只要深度持续保持在阈值以上，都不会重复打印**——直到深度回落到阈值以下，标记被重置，下一次如果又重新涨回阈值以上，才会被当作一次全新的告警。这种"跨越边界才触发、持续超标不重复触发"的模式，叫**去抖（debounce）**，在监控告警场景里非常常见——原因很简单：**一条被淹没在几百条重复警告里的关键信息，等于没有发出过**。

## `RateLimitedConsumer`：滑动窗口限流

这一节的重点，是理解"滑动窗口"限流和更简单的"固定间隔"限流有什么本质区别。

一个朴素的限流实现可能是"每隔`window_seconds / max_calls`秒允许一次调用"——比如允许每10秒钟5次调用，那就是每2秒一次。但这种"固定间隔"限流有一个边界问题：如果每次都卡着2秒的间隔调用，理论上可以在"上一个10秒窗口的最后1秒"和"下一个10秒窗口的最前1秒"里挤进去两倍于预期的调用量，造成短时间的突发超速。

`RateLimitedConsumer`用的是**滑动窗口**：不是固定分割时间段，而是持续追踪"最近`window_seconds`秒内，究竟发生过几次调用"：

```python
def __init__(self, *, max_calls: int, window_seconds: float) -> None:
    self._call_times: deque[float] = deque()

def _prune_expired(self, now: float) -> None:
    cutoff = now - self._window_seconds
    while self._call_times and self._call_times[0] <= cutoff:
        self._call_times.popleft()

def time_until_next_slot(self) -> float:
    now = time.monotonic()
    self._prune_expired(now)
    if len(self._call_times) < self._max_calls:
        return 0.0
    oldest = self._call_times[0]
    return max(0.0, (oldest + self._window_seconds) - now)
```

这里用`deque`（双端队列）存"每一次真正发生的调用，各自是什么时刻"，每次判断时先把"已经滑出窗口"的旧记录清理掉，再看剩下的记录数量是否已经达到上限。如果达到了，还需要等待的时间，就是"最早那条记录滑出窗口"所需要的时间——这样无论调用发生的时间点多么不规律，**任意连续`window_seconds`秒的区间里，调用次数永远不会超过`max_calls`**，不存在固定间隔限流那种"边界突发"的漏洞。

## 为什么用`time.monotonic()`而不是`time.time()`

这里选用的是`time.monotonic()`，而不是更常见的`time.time()`。两者的区别值得记住：

- `time.time()`返回"墙上时钟"时间——如果系统时间因为人工调整、网络对时校准等原因发生跳跃（比如手动往回调整了系统时间），用它计算的时间差会突然出现异常的负数或者巨大的跳变。
- `time.monotonic()`返回一个"只会单调递增、不受系统时间调整影响"的计时器读数——这个数字本身没有实际的日历含义（不能拿它当"现在几点"用），但专门适合"测量两个时间点之间到底经过了多久"这类场景。

限流窗口关心的正是"过去了多长时间"，而不是"现在是几点几分"，所以`time.monotonic()`是更安全、更不容易出bug的选择。这是一个值得在任何"计算时间间隔"的代码里留意的细节。

## "限流"是源头限制，不是消费端硬扛

模块docstring里特别强调了一句设计原则：

> 入队速率限制是"源头限制"而不是"消费端限流"：`RateLimitedConsumer`保证真正被处理的任务不超过下游允许的速率，如果需要处理的任务比速率允许的更快到达，调用方必须显式等待（`await acquire()`），而不是把所有任务都塞给下游、指望下游自己扛住。

这句话的意思是：`RateLimitedConsumer`只负责"告诉你现在能不能调用、还要等多久"（`time_until_next_slot()`），**它不会替你把多余的任务偷偷丢弃，也不会自己去做排队缓冲**——真正要不要等待、怎么等待（同步sleep？异步await？重新塞回队列？），由调用方自己决定。这是一种"只做一件事、把决策权留给调用方"的设计克制，避免这个类试图变成一个大而全的"任务队列管理器"。

## 本章小结

- 队列积压监控要在跨越阈值的那一刻主动告警，并且用"去抖"避免持续超标时反复刷屏。
- 限流应该用滑动窗口而不是固定间隔分割，否则在窗口边界附近可能出现允许的突发超速。
- 计算时间间隔应该用`time.monotonic()`而不是`time.time()`，避免系统时钟被调整导致计算出错误的时间差。
- 限流器只负责"告诉你能不能调用、还要等多久"，不负责替调用方做等待/丢弃的决定——保持职责单一。

## 动手做

```python
from ainative_guardrail.backpressure import RateLimitedConsumer
import time

limiter = RateLimitedConsumer(max_calls=3, window_seconds=2.0)

for i in range(5):
    wait = limiter.time_until_next_slot()
    print(f"第{i+1}次调用，需要等待 {wait:.2f} 秒")
    if wait > 0:
        time.sleep(wait)
    limiter.record_call()
```

观察前3次调用是不是立刻放行，第4次开始是不是需要真的等待。

## 面试可能会问

**问：如何设计一个限流器，避免在窗口边界处出现突发超速？**

答题思路：先说明"固定间隔限流"在窗口边界处的漏洞（能在两个窗口交界处挤进双倍流量），再介绍"滑动窗口"的解决思路——持续追踪最近一段时间窗口内的真实调用时间戳，而不是死板地按固定时间段分割。如果能补充"用`time.monotonic()`而不是`time.time()`来避免系统时钟调整带来的计算错误"，会展示出更扎实的实现细节把控能力。
