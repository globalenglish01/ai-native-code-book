# 第23章 —— 落盘前的脱敏代理

代码位置：`packages/ainative-memory/src/ainative_memory/redacting_backend.py`

## 摘要写进了磁盘，手机号也一起写进去了

第22章讲了对话历史要按token预算裁剪，但裁剪之后被丢弃的那部分历史内容去哪了？真实系统里常见的做法不是简单丢弃，而是"摘要溢出"（summarization overflow）：把超出预算、即将被丢弃的旧对话内容，先让LLM压缩成一段摘要，再把这段摘要写到磁盘上长期保存，需要的时候再读回来——这样既控制了实时预算，又没有真的永久丢失信息。

但这里藏着一个很容易被忽略的隐私问题：如果这段旧对话里，用户之前提到过自己的手机号、身份证号、家庭住址，摘要压缩之后，这些敏感信息很可能原封不动地被包含进摘要文本里，然后这段摘要被直接写进了磁盘文件。**裁剪逻辑本身认认真真地控制了token预算，却没人管这份最终落地生根、可能被日志采集、被备份、被别的系统读取的文件里，是不是混进了不该出现在磁盘上的个人隐私信息**。

这一章要看的`redacting_backend.py`，解决的正是这个问题：在"内容真正写入磁盘"这一步之前，插入一道脱敏关卡，而且这道关卡的实现方式，几乎不需要修改任何已有代码。

## Proxy模式：包一层，只拦截你关心的方法

模块docstring交代了设计来源：

> 改造自真实项目里验证过、几乎零耦合的设计：`SummarizationMiddleware`把对话历史溢出（overflow）内容落盘之前，需要先做PII脱敏。本模块提供一个只拦截真正执行"写入"的方法（`write`/`edit`/`awrite`/`aedit`）、其余方法透传给底层backend的代理类——不关心底层backend具体是本地文件、S3还是别的什么，只要求它有这几个方法（鸭子类型）。

先想一下，如果不用这里的设计，你会怎么解决这个问题？一个直接的思路是：找到所有调用"写文件"的地方，在每一处调用之前手动插入一行"先脱敏"的代码。这个思路的问题在于——凡是新增一个写入的地方，就要记得再加一次脱敏调用，一旦某处漏加，这个隐患就会悄悄潜伏下来，直到某天真的有敏感信息落盘才被发现。

`RedactingBackend`用的是完全不同的思路——"代理模式"（Proxy Pattern）：**造一个"看起来和原始backend一模一样"的包装对象，所有写入类的方法调用先经过脱敏处理再转发给真正的backend，其余方法原样转发**。调用方拿到这个代理对象之后，用起来和用原始backend几乎没有任何区别，唯一的区别是"写进去的内容已经被自动脱敏过了"——不需要在每一处写入调用之前手动记得加一行脱敏代码。

## 代码怎么写：`__getattr__`实现"其余方法透传"

```python
class RedactingBackend:
    """包装任意"文件系统式"backend，拦截写入方法做脱敏，其余方法透传。"""

    def __init__(self, inner: Any, redact_fn: Callable[[str], str]) -> None:
        self._inner = inner   # 被包装的真实backend
        self._redact_fn = redact_fn   # 脱敏函数，接收字符串返回脱敏后的字符串

    # __getattr__——Python的"魔法方法"，只有在正常属性查找失败时才会
    # 被自动调用；这里让"找不到的属性/方法"都转发给self._inner去处理。
    def __getattr__(self, name: str) -> Any:
        return getattr(self._inner, name)
```

`inner`是被包装的原始backend（可能是一个本地文件系统实现，也可能是一个S3客户端封装），`redact_fn`是脱敏函数——这个类完全不关心脱敏规则具体是什么，只负责"在写入之前调用它一次"。

真正实现"透传"的关键是`__getattr__`这个方法。这是Python的一个"魔法方法"（特殊命名的内置钩子方法）——它有一个很特别的触发时机：**只有当"正常的属性/方法访问失败"时，Python才会自动调用它**。换句话说，如果你在`RedactingBackend`实例上访问一个属性或方法名，Python会先按正常流程去这个类（以及它的父类）里找有没有对应的定义；只有在"正常流程完全找不到"的情况下，才会退而求其次，调用`__getattr__`，把你访问的这个名字当参数传进去，让你自己决定该怎么处理。

`return getattr(self._inner, name)`这一行的意思是："去`self._inner`身上找一个叫`name`的属性/方法，把它返回给调用方"。效果就是：如果调用方在这个代理对象上调用了一个`RedactingBackend`自己没有显式定义的方法（比如`inner`独有的某个方法、或者读取某个属性），会被自动转发给`self._inner`去处理，代理对象本身看起来就像是"和`inner`完全一样，只是多了几个特殊方法"。这正是Proxy模式的经典实现方式：对外表现得像是同一个对象，实际内部把大部分工作转手交给被包装的对象去做。

## 只拦截四个真正执行写入的方法

`write`/`edit`/`awrite`/`aedit`这四个方法是被显式定义在`RedactingBackend`类里的，因此不会走到`__getattr__`那条透传路径——正常的属性查找会先找到这里定义的版本：

```python
# *args/**kwargs——收集调用时额外传入、这里没显式列出名字的参数，
# 原样转发给底层backend，代理不需要知道具体每个backend还接受哪些参数。
def write(self, file_path: str, content: str, *args: Any, **kwargs: Any) -> Any:
    # 真正写入之前，先用redact_fn把content脱敏一遍。
    return self._inner.write(file_path, self._redact_fn(content), *args, **kwargs)

def edit(self, file_path: str, old_string: str, new_string: str, *args: Any, **kwargs: Any) -> Any:
    # 只脱敏new_string（将要写入的新内容），old_string原样传递（用来精确匹配磁盘上的旧内容）。
    return self._inner.edit(file_path, old_string, self._redact_fn(new_string), *args, **kwargs)

# async def——异步版本，需要await等待底层backend真正完成写入。
async def awrite(self, file_path: str, content: str, *args: Any, **kwargs: Any) -> Any:
    return await self._inner.awrite(file_path, self._redact_fn(content), *args, **kwargs)

async def aedit(self, file_path: str, old_string: str, new_string: str, *args: Any, **kwargs: Any) -> Any:
    return await self._inner.aedit(file_path, old_string, self._redact_fn(new_string), *args, **kwargs)
```

每一个方法的核心逻辑都只有一行：把真正要落盘的文本内容（`content`或`new_string`）先丢给`self._redact_fn`处理一遍，再把脱敏后的结果转发给`self._inner`真正执行写入。`awrite`/`aedit`是`write`/`edit`的异步版本（方法名前缀`a`是"async"的常见简写约定），逻辑完全一致，只是需要`await`等待底层backend的异步操作真正完成。

`*args: Any, **kwargs: Any`这两个参数收集的是"调用时额外传入、这里没有显式列出名字的参数"——`*args`收集额外的位置参数打包成元组，`**kwargs`收集额外的"参数名=值"关键字参数打包成字典。这么写的原因是：不同的底层backend实现，除了`file_path`/`content`这两个核心参数之外，可能还接受一些额外的参数（比如某种编码方式、某个可选的元数据），代理类不需要逐一知道这些参数具体叫什么名字，只要原样把它们转发给`self._inner`对应的方法就行。

## 一个容易忽略的细节：`edit()`为什么只脱敏`new_string`

`edit()`方法的实现有一处很容易看漏但很重要的细节——它只对`new_string`（将要写入的新内容）调用脱敏函数，`old_string`（用于在文件里定位"要替换的旧内容"）完全不做任何处理。模块docstring解释了原因：

> `edit()`方法只脱敏`new_string`，不脱敏`old_string`——因为`old_string`是从磁盘读回的、可能已经脱敏过的旧内容，必须原样传回才能让底层backend正确定位替换点；脱敏函数本身是幂等的（对已脱敏文本再脱敏一次无害），所以`new_string`整体脱敏是安全的。

想象一下如果`old_string`也被脱敏会发生什么：`edit()`这类操作的典型工作方式是"在文件里找到和`old_string`完全匹配的一段文本，把它替换成`new_string`"。如果磁盘上这份文件本来就是之前经过脱敏写入的（比如原本的手机号已经被替换成了`[REDACTED_PHONE]`），而调用方传进来的`old_string`是脱敏之前的原始文本（真实手机号），如果代理在转发之前把这个`old_string`也脱敏了一遍——脱敏之后的`old_string`固然和磁盘上的内容能对上，但如果调用方传进来的`old_string`本身就是"读磁盘读出来、还没脱敏"的原始旧内容，两次脱敏路径不一致，就可能出现"文件里根本找不到匹配的旧内容，替换直接失败"的情况。用最简单的话说：**`old_string`的职责是"帮你在磁盘里对上号"，脱敏它反而会让"对号"这件事失去意义**；而`new_string`的职责是"即将被真正写进磁盘的新内容"，这才是脱敏真正需要发挥作用的地方。

docstring里顺带提到"脱敏函数本身是幂等的（对已脱敏文本再脱敏一次无害）"——这是一个很实用的设计前提：意味着即使调用方不小心把已经脱敏过的文本又传进来脱敏了一次，也不会因为"重复脱敏"而把内容改坏（比如把已经是`[REDACTED_PHONE]`的文本，第二次脱敏时不会再动它，或者动了也还是它自己）。有了这个前提，`new_string`可以放心地"整体"脱敏，不用费心去区分这段文本里哪部分是新加的、哪部分可能已经脱敏过。

## 工厂函数：一行代码包一层

```python
# 这个工厂函数不做任何额外逻辑，纯粹是让调用方代码的意图更清晰——
# 一看函数名就知道"这是在给摘要落盘场景包一层脱敏代理"。
def wrap_summarization_backend(backend: Any, redact_fn: Callable[[str], str]) -> RedactingBackend:
    return RedactingBackend(backend, redact_fn)
```

这个函数本身不做任何额外工作，只是把两个参数原样转发给`RedactingBackend`的构造函数。它存在的意义纯粹是让调用方代码读起来更贴近"我想要一个脱敏代理"这个意图——写`wrap_summarization_backend(real_backend, redact_fn=redact)`比直接写`RedactingBackend(real_backend, redact)`更能一眼看出这行代码在干什么，这是一种很值得模仿的小习惯：**给一个更底层的类包一层语义更清晰的工厂函数，让调用方代码本身就是一种文档**。

## 关键架构约束：不要包错了对象

这一章最重要的一条提醒，藏在模块docstring里，而且用了加粗强调：

> **关键架构约束（必须遵守，否则会误伤业务文件读写）**：这个代理只应该传给"负责摘要溢出持久化"的组件（如`SummarizationMiddleware(backend=...)`），绝不能传给"模型自身文件读写工具"用的backend（如`FilesystemMiddleware`）——同一个原始backend实例通常会被两处同时使用，调用方必须持有两个独立引用：原始backend给文件读写工具，`wrap_summarization_backend()`包过的代理给摘要持久化组件。

这句话在提醒一个很容易踩的坑：真实系统里，同一个底层文件系统backend实例，往往会被两个完全不同的组件共用——一个是"模型自己调用的文件读写工具"（比如AI要读一份代码文件、要写一份用户要求生成的报告），另一个是"摘要溢出落盘"这个内部机制。如果图省事，把包过脱敏代理的这个对象，当成"通用的backend"到处传，结果就是**AI原本想写进一份正常业务文件里的内容，也被这道脱敏关卡拦截、悄悄改写了**——比如AI想在报告里如实引用用户提供的联系电话，脱敏逻辑却把它替换成了`[REDACTED_PHONE]`，而这本来是用户希望被保留在报告里的合法内容，不是需要被隐藏的隐私泄露。

正确的用法是保留两个独立的引用：原始的、未包装的`backend`继续交给"模型文件读写工具"使用；只有`wrap_summarization_backend()`包出来的这个代理，专门交给负责摘要持久化的组件（比如`SummarizationMiddleware(backend=...)`）使用。这条架构约束提醒我们一个更普遍的道理：**"给某个组件加一层横切逻辑"这件事的影响范围，必须严格限定在它真正该覆盖的场景，而不是图省事把同一个包装对象散播到所有用到"文件系统"这个概念的地方**——代理模式本身是无辜的，用错了地方才会造成"误伤"。

## 本章小结

- Proxy模式解决的是"给某个对象的部分方法加一层横切逻辑（这里是脱敏），又不想改动调用方现有代码"这个问题：包一层看起来一样的对象，拦截你关心的方法，其余透传。
- `__getattr__`是Python的魔法方法，只有在"正常属性查找失败"时才会被调用，是实现"透传"最经典的写法。
- `edit()`只脱敏`new_string`不脱敏`old_string`——`old_string`要原样传回去精确匹配磁盘上的旧内容，脱敏它反而会导致替换定位失败；脱敏函数本身幂等，所以`new_string`整体脱敏是安全的。
- 一条必须遵守的架构约束：这个脱敏代理只应该传给"摘要落盘"组件，绝不能传给"模型自身文件读写工具"的backend——否则会误伤本该原样保留的正常业务写入内容；同一个原始backend实例要拆成两个独立引用分别使用。
- 工厂函数（`wrap_summarization_backend`）本身不做额外工作，只是让调用方代码的意图更清晰，是一个值得模仿的小习惯。

## 动手做

```python
from ainative_memory.redacting_backend import wrap_summarization_backend

# 一个最简单的"假backend"，用内存字典模拟文件系统，只需要有write方法。
class FakeBackend:
    def __init__(self):
        self.files = {}   # 模拟"文件路径 -> 文件内容"的存储

    def write(self, file_path, content):
        self.files[file_path] = content
        return f"写入 {file_path} 成功"

def redact(text: str) -> str:
    # 一个最简单的脱敏函数：把这个固定的手机号替换成占位符。
    return text.replace("13800138000", "[REDACTED_PHONE]")

real_backend = FakeBackend()
safe_backend = wrap_summarization_backend(real_backend, redact_fn=redact)

safe_backend.write("summary.md", "用户联系电话是13800138000，偏好深色主题")
print(real_backend.files["summary.md"])
# 用户联系电话是[REDACTED_PHONE]，偏好深色主题
```

试着再调用`safe_backend.files`（一个`RedactingBackend`没有显式定义的属性），观察它是否能正常透传到`real_backend.files`，验证`__getattr__`确实生效了。

## 面试可能会问

**问：如果你要给一个已有的文件写入组件加一层"写入前自动脱敏"的逻辑，但不想改动所有调用写入的代码，你会怎么设计？**

答题思路：介绍代理模式（Proxy Pattern）——包一层和原始对象接口一致的包装类，只显式拦截真正需要处理的方法（这里是`write`/`edit`等写入类方法），其余方法通过`__getattr__`透传给被包装的原始对象，调用方无需感知这层包装的存在。再补充两个体现设计深度的细节：一是像`edit()`这种"定位+替换"的操作，只应该脱敏"将要写入的新内容"，不能脱敏"用于在原文件里定位旧内容"的部分，否则会导致匹配失败；二是要明确这层包装只应该套在"真正需要脱敏的那条路径"上（比如摘要落盘），不能图省事套在通用backend上到处传，否则会误伤本该原样保留的正常业务写入。
