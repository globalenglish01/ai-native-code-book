## 一份手册切错了，答案就会"卡在缝里"

假设知识库里有一份很长的产品手册，其中有这样一段话："如果设备连续三次校验失败，"（第一段结尾）"则应立即停止使用并联系售后。"（下一段开头）。如果分块系统简单粗暴地"每500个字硬切一刀"，恰好在"失败，"和"则应立即"中间切开——检索到前半段的人会看到"连续三次校验失败"却读不到后果，检索到后半段的人会看到"则应立即停止使用"却不知道触发条件是什么。这份手册里最关键的一条安全提示，就这样被切成了两个各自都不完整的碎片，永远也凑不齐。

这一章要看的两个模块，分别解决"怎么切文档"（分块）和"怎么把多种检索算法的结果合并成一份排序"（混合检索融合）这两个问题。

## 分块：重叠是为了不让答案卡在切分边界上

`chunking.py`的docstring点出了应对这个问题的第一个手段——**相邻片段之间要保留合理的重叠**（行业惯例10%-20%）：

```python
DEFAULT_OVERLAP_RATIO = 0.15
```

这样即使切分点恰好落在一句话中间，重叠区域也能保证"临界点附近的内容"同时出现在前后两个片段里，不至于被硬切丢失——这不是为了让文档"看起来完整"，而是实实在在提高了检索命中率。

## 一个真实bug：参数设错了，切分器会"安静地"什么都不产出

```python
def chunk_by_token_estimate(
    text: str, *, chunk_size: int = 1000, overlap_ratio: float = DEFAULT_OVERLAP_RATIO,
) -> list[Chunk]:
    # 校验1：重叠比例必须落在[0, 1)——1或以上意味着"重叠掉整段甚至更多"，
    # 会导致下面算出的step（每次向前推进的字符数）变成0或负数。
    if not (0.0 <= overlap_ratio < 1.0):
        raise InvalidChunkingParametersError(
            f"overlap_ratio must be in [0, 1), got {overlap_ratio} "
            f"(a ratio >= 1 makes the step size <= 0, silently producing zero chunks)"
        )
    if chunk_size <= 0:   # 校验2：片段大小必须是正数
        raise InvalidChunkingParametersError(f"chunk_size must be positive, got {chunk_size}")

    chunk_chars = chunk_size * 4   # 约4个字符算1个token的粗略估算比例
    overlap_chars = int(chunk_chars * overlap_ratio)
    step = chunk_chars - overlap_chars
    # step是"步长"：每切完一个片段，下一个片段的起点要往前推进多少字符。
    # 前面两处校验正是为了保证这个step永远是正数。
    ...
```

docstring里记录了这处校验存在的真实原因：如果调用方把`overlap_size`设置得比`chunk_size`还大或者相近，切分每次向前推进的"步长"（`step = chunk_chars - overlap_chars`）会变成0甚至负数。Python的`range(0, n, step)`在`step`不是正数时，**不会报错，而是静默返回一个空序列**——也就是说，整个分块函数会"运行成功"，返回一个空的片段列表，日志里没有任何异常，但这份文档实际上一个片段都没切出来、永远不会被检索到。

这是一类特别值得警惕的失败模式：**代码没有崩溃，甚至没有打印任何警告，但产出的结果是完全错误的（这里是"应该有几十个片段，实际一个都没有"）**。这种bug往往要等到有人发现"某份文档明明存在，却怎么都搜不到"时才会被追查出来，排查成本远高于"参数一传错就直接报错"。所以这个模块选择在参数刚传进来的那一刻，就主动校验`overlap_ratio`必须落在`[0, 1)`区间、`chunk_size`必须是正数——把"未来可能悄悄产生空结果"的组合，直接在源头堵死。

## 语义边界优先，但必须有明确的兜底

```python
def chunk_by_semantic_boundary(
    text: str, *, separator: str = "\n\n", chunk_size: int = 1000, overlap_ratio: float = DEFAULT_OVERLAP_RATIO,
) -> list[Chunk]:
    paragraphs = text.split(separator)   # 按段落分隔符切开，分隔符本身不出现在结果里
    ...
    for paragraph in paragraphs:
        ...
        if len(paragraph) <= chunk_chars:
            # 这个段落本身没超出目标大小——整段作为一个片段，保留最完整的语义单元。
            chunks.append(Chunk(text=paragraph, ...))
        else:
            # 语义边界切分帮不上忙——退回机械切分做二次兜底，不允许超限片段被悄悄产出。
            for sub in chunk_by_token_estimate(paragraph, chunk_size=chunk_size, overlap_ratio=overlap_ratio):
                # sub.start是相对段落内部的位置，加上para_start换算回相对整篇原文的绝对位置。
                chunks.append(Chunk(text=sub.text, start=para_start + sub.start, end=para_start + sub.end, ...))
```

比起"每隔固定字符数硬切一刀"，按段落（`\n\n`）这种文本天然的语义边界切分，通常能保留更完整的意思单元，检索命中时上下文也更连贯。但这种切法有一个明显的短板：如果某一段本身就特别长（比如一整段没有任何换行的大段文字），单纯按段落切分会切出一个远超`chunk_size`限制的"超大片段"。

这个模块的处理方式是：**语义边界切分帮不上忙的段落，退回去调用上面那个按字符数机械切分的函数做二次兜底**，而不是放任一个超限的片段被悄悄产出。这是一个值得记住的通用设计模式——**当"理想的处理方式"在某些边界情况下失效时，必须有一条明确的兜底路径，而不能让那部分数据直接绕过所有处理逻辑**。

细节上，二次切分出来的子片段位置是"相对段落内部"的（因为`chunk_by_token_estimate`并不知道这个段落在整篇原文里从哪个位置开始），所以代码里用`para_start + sub.start`把相对位置换算回"相对整篇原文"的绝对位置——这一步换算容易被遗漏，但对"引用溯源"（上一章讲的`RetrievedChunk`要能精确定位回原文哪个位置）来说是必需的。

## 混合检索融合：为什么不能直接比较两种算法的原始分数

假设你的系统同时用了两种检索算法：BM25（一种基于关键词精确匹配的经典算法）和向量检索（把文字转成数字向量、比较语义相似度）。BM25打出来的分数可能是0到20之间的任意正数，向量检索的余弦相似度通常在0到1之间——如果简单地把两边的分数直接相加或者加权平均，会出现什么问题？

想象BM25给某篇文档打了15分（这个算法的"高分"），向量检索给另一篇文档打了0.95分（这个算法的"满分"）——如果直接相加或加权，前者几乎必然会碾压后者，不是因为它真的更相关，只是因为两种算法的"分数量纲"完全不可比。`hybrid_search.py`的docstring把这一点说得很直接：

> 融合多种不同标准算出来的排序结果时，必须用基于"排名"而不是直接比较"原始分数"的融合方式——不同算法的分数量纲完全不可比，直接相加/加权平均会产生失真的排序结果。

## RRF（Reciprocal Rank Fusion）：只关心排第几名，不关心具体打了多少分

```python
DEFAULT_RRF_K = 60   # RRF公式里的平滑常数，业界惯用默认值（出自RRF原始论文）

def rrf_fuse(*result_lists: list[RankedResult], k: int = DEFAULT_RRF_K) -> list[tuple[str, float]]:
    # *result_lists——可变参数，调用方可以传入任意数量路的检索结果。
    scores: dict[str, float] = {}
    for results in result_lists:   # 依次遍历每一路检索结果
        for result in results:     # 再遍历这一路里的每一条命中
            # 只在出现过的那一路才累加分数——没被召回的那一路不参与计算，
            # 不会被当成"排名垫底"强行打分。
            scores[result.doc_id] = scores.get(result.doc_id, 0.0) + 1.0 / (k + result.rank)
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)   # 按分数降序排列
```

RRF的核心思路是：不管某篇文档在BM25里具体打了多少分、在向量检索里具体打了多少分，只关心"它在这一路结果里排第几名"。公式`1/(k+rank)`把"排名"转换成一个可以跨算法累加的分数——排名越靠前（`rank`越小），贡献的分数越高，一篇文档如果在多路检索结果里都排名靠前，会自然累加出更高的总分。因为所有输入都统一成了"排名"这个共同的度量单位，不同算法之间的量纲差异被完全消除了。

`k=60`这个常数的作用是"拉平"排名差距——如果没有这个常数，排名第1的文档贡献`1/1=1.0`分，排名第2的贡献`1/2=0.5`分，差距被放得很大；加上`k=60`后变成`1/61`和`1/62`，差距被大幅拉平，避免一篇文档仅仅因为在某一路检索里"运气好"排到第1名，就获得压倒性的优势。

值得留意的还有一个容易被忽略的细节——**只在某一路结果里出现的文档，另一路没出现的部分不参与计算**，而不是把"没被召回"当作"排名垫底"强行参与打分。这两种情况的语义完全不同："这篇文档BM25没检索到"和"这篇文档BM25检索到了但排在最后一名"应该被区别对待，前者是"完全没被这一路算法考虑过"，后者是"被考虑过，只是相关性判断偏低"。

## `rank`必须从1开始：又一处"参数错了会静默产生错误结果"的校验

```python
@dataclass(frozen=True)
class RankedResult:
    doc_id: str
    rank: int   # 从1开始的排名（1表示这一路检索里最相关的结果）

    def __post_init__(self) -> None:
        # 构造完成的那一刻就校验——防止enumerate()默认从0计数这类
        # off-by-one错误，静默传导进下面rrf_fuse的1/(k+rank)公式。
        if self.rank < 1:
            raise InvalidRankError(
                f"rank must be >= 1 (ranks start from 1), got {self.rank} for doc_id={self.doc_id!r} — "
                f"an off-by-one upstream (e.g. enumerate() starting at 0) would otherwise silently "
                f"cause rrf_fuse's `1/(k+rank)` to divide by zero or produce a negative denominator"
            )
```

这处校验背后的真实场景是：Python的`enumerate()`默认从0开始计数，如果上游代码在把"检索结果列表"转换成排名时忘记显式指定`start=1`，很容易传出`rank=0`的结果。这个0一旦流入`rrf_fuse`的`1/(k+rank)`公式——如果`k`恰好也是0，就是直接除以0崩溃；如果`k`不是0（这个模块默认是60，所以不会真的除以0），则会算出一个虽然不会报错、但在数学意义上不完全符合"排名倒数"设计初衷的分数，且没有任何报错提示。

`__post_init__`是`@dataclass`提供的钩子方法，会在所有字段赋值完毕后自动调用，这里用它在对象刚构造完成的那一刻就拒绝不合法的`rank`值——这和`chunking.py`里`overlap_ratio`校验是同一类思路：**与其让一个隐蔽的off-by-one错误一路传导到几层之外的计算公式里、产生一个"看起来正常但实际有偏差"的结果，不如在数据刚刚被构造出来的最早时机就直接拒绝它。**

## 本章小结

- 分块时保留10%-20%的重叠区间，是为了让恰好落在切分边界上的关键信息，依然能完整出现在至少一个片段里，不会被硬切丢失。
- `overlap_ratio`必须校验落在`[0, 1)`区间，否则切分步长会退化成0或负数，导致`range()`静默产出空结果——这是一类"运行不报错但结果全错"的典型陷阱，必须在参数入口就拦截。
- 语义边界切分能保留更完整的语义单元，但必须有"某一段本身超长"时的明确兜底（退回机械切分），不能让超限片段悄悄溜过去。
- 融合多路检索结果时必须基于"排名"而不是直接比较"原始分数"——不同算法的分数量纲不可比，RRF用`1/(k+rank)`把排名统一转换成可累加的分数，从根源上避开这个问题。
- `RankedResult.rank`必须校验从1开始，防止`enumerate()`默认从0计数这类常见的上游off-by-one错误，悄悄影响到RRF融合公式的计算结果。

## 动手做

```python
from ainative_rag.chunking import chunk_by_semantic_boundary, chunk_by_token_estimate, InvalidChunkingParametersError
from ainative_rag.hybrid_search import rrf_fuse, ranked_results_from_scores

# 分块：观察超长段落触发二次机械切分
text = "第一段较短。\n\n" + "这是一段非常非常长、没有任何换行符的文字……" * 100
chunks = chunk_by_semantic_boundary(text, chunk_size=50)
print(f"共切出 {len(chunks)} 个片段")

try:
    chunk_by_token_estimate("任意文本", overlap_ratio=1.0)
except InvalidChunkingParametersError as exc:
    print("非法重叠比例被正确拒绝：", exc)

# 混合检索融合：BM25分数和向量相似度量纲完全不同，但RRF只看排名
bm25_scores = {"doc-a": 18.2, "doc-b": 5.1, "doc-c": 12.7}
vector_scores = {"doc-a": 0.62, "doc-b": 0.91, "doc-c": 0.55}

bm25_ranked = ranked_results_from_scores(bm25_scores)
vector_ranked = ranked_results_from_scores(vector_scores)

fused = rrf_fuse(bm25_ranked, vector_ranked)
print("融合后排序：", fused)
```

## 面试可能会问

**问：你的系统同时用了关键词检索和向量检索，怎么把两边的结果合并成一份最终排序？**

答题思路：先指出最容易犯的错误——直接把两边的原始分数相加或加权平均，因为不同算法的分数量纲完全不可比（比如BM25可能是两位数、余弦相似度是0到1之间），直接混算会让某一路算法的结果不合理地压过另一路。正确做法是用基于"排名"的融合方式（如RRF，Reciprocal Rank Fusion）：只关心一篇文档在每一路结果里排第几名，用`1/(k+rank)`这样的公式把排名统一转换成可以跨算法累加的分数，`k`这个平滑常数用来避免排名第一的文档获得过度夸张的权重。如果能补充"只在某一路里出现的文档不该被当作在另一路排名垫底,而是完全不参与那一路的计算"这个细节，会显得对这个问题理解得更深入。
