## 客服机器人不应该只靠对话历史回答问题

前两章搭好的客服平台，能处理常规对话、能把复杂案例升级给专家——但它现在还不能回答"退货政策是什么"、"这个产品支持哪些付款方式"这类需要查阅公司知识库文档的问题。如果没有真正检索一份权威文档就凭空回答，很容易出现第38章开头讲过的那种场景：编造一个听起来合理、实际上完全错误的答案。

这一章要看的`rag_knowledge_base_service.py`，把`ainative-rag`包里第38-41章讲过的全部六个子模块——分块、混合检索、RRF融合、重排序、新鲜度感知缓存、embedding批量处理——组装成一条完整的"摄入→检索→融合→重排序→生成→缓存"流水线。这正是本章想让你看到的：**前面四章分别学的每一个独立环节，合在一起构成的是一条什么样的完整链路**。

## 摄入阶段：分块存储，为将来的检索做准备

```python
def ingest(self, doc_id: str, text: str, *, version: str) -> int:
    """摄入一份文档：按重叠比例分块存储，返回产生的片段数。"""
    chunks = chunk_by_token_estimate(text, chunk_size=50, overlap_ratio=0.15)   # 切成带重叠的片段
    # 只存文本本身（c.text），版本号单独记录，后面缓存那一步会用到它。
    self._documents[doc_id] = IngestedDocument(doc_id=doc_id, version=version, chunks=[c.text for c in chunks])
    return len(chunks)   # 返回切出了多少个片段
```

第39章讲过的`chunk_by_token_estimate`在这里被直接调用——注意`version`这个参数从摄入阶段起就被记录了下来，这不是随手加的字段，后面缓存那一步会看到它的关键作用。

## 检索阶段：两路独立打分，一路融合

```python
def _keyword_search(self, query: str) -> dict[str, float]:
    """按词汇集合精确匹配打分——用词而不是子字符串匹配，避免"a"/"is"
    这类常见短词因为作为子字符串出现在几乎任何文本里而造成误判命中。"""
    query_terms = set(query.lower().split())   # 查询文本按空格切成词集合
    scores = {}
    for doc_id, doc in self._documents.items():
        doc_terms = set(" ".join(doc.chunks).lower().split())   # 文档所有片段拼起来再切词
        matched = query_terms & doc_terms   # 集合交集运算：两边都出现的词
        if matched:
            scores[doc_id] = float(len(matched))   # 匹配到几个词就是几分，没有上限
    return scores

def _vector_search(self, query: str) -> dict[str, float]:
    """demo用的"向量相似度"模拟——按词汇集合的Jaccard相似度打分。"""
    query_terms = set(query.lower().split())
    scores = {}
    for doc_id, doc in self._documents.items():
        doc_terms = set(" ".join(doc.chunks).lower().split())
        intersection = query_terms & doc_terms   # 交集：两边都有的词
        union = query_terms | doc_terms   # 并集：两边加起来一共出现过的词
        if intersection:
            scores[doc_id] = len(intersection) / len(union)   # Jaccard相似度，永远在0到1之间
    return scores
```

这两个方法故意用了两种**分数量纲完全不同**的打分方式——`_keyword_search`返回的是"匹配到几个词"这个整数（可能是1、2、5……没有上限），`_vector_search`返回的是Jaccard相似度（永远落在0到1之间）。这不是疏忽，而是刻意设计成这样，为了让下一步的融合逻辑有真正的意义可讲：

```python
# 先把两边的原始分数各自转换成"排名"，再用RRF按排名融合，
# 而不是直接把两组量纲不同的分数加在一起。
fused = rrf_fuse(ranked_results_from_scores(keyword_scores), ranked_results_from_scores(vector_scores))
```

第39章讲过的`rrf_fuse`在这里发挥作用——如果试图直接把"匹配到3个词"和"Jaccard相似度0.8"相加，这两个数字根本不在同一个量纲上，加权平均出来的结果没有任何数学意义。`rrf_fuse`只关心每个文档在各自那一路结果里排第几名，天然规避了这个问题。这也是为什么这个demo特意选了两种打分范围差异很大的方式来模拟"关键词检索"和"向量检索"——真实场景里BM25和余弦相似度的量纲差异，正是这个道理的写照。

## 重排序：故意让一个文档"评分失败"，验证聚合逻辑不会把它错当成满分

```python
def _rerank(self, doc_ids: list[str], query: str) -> dict[str, float]:
    scored_chunks = []
    for doc_id in doc_ids:
        if doc_id == "doc-unscored":
            # 故意模拟"这份文档的重排序请求失败了"——rerank_score=None
            scored_chunks.append(ScoredChunk(chunk_id=f"{doc_id}-0", doc_id=doc_id, rerank_score=None))
        else:
            relevance = len(set(query.lower()) & set(doc_id.lower())) + 1
            scored_chunks.append(ScoredChunk(chunk_id=f"{doc_id}-0", doc_id=doc_id, rerank_score=relevance / 10))
    return aggregate_chunk_scores(scored_chunks)   # None会被当作最低分,不会被误判成满分
```

这一段代码里藏着一个很用心的教学设计——`doc_id == "doc-unscored"`这个特殊分支，故意模拟"这份文档的重排序请求失败了，完全没打上分"的情况，构造`ScoredChunk(..., rerank_score=None)`。第40章讲过的真实bug（打分失败时错误地默认给满分1.0，导致完全没被评估过的内容反而被优待）在这里能被直接验证——`aggregate_chunk_scores`会把这份"没打分"的文档当作最低分处理，而不会让它意外挤占本该属于真正高相关文档的位置。如果你在这一章末尾的"动手做"里加入这份`doc-unscored`文档，会亲眼看到它不会被误判为最相关结果。

## 检索的最后一步：新鲜度感知的缓存

```python
async def query(self, query: str) -> RagAnswer:
    # 字典推导式：实时读取当前知识库里每份文档的版本号，不是摄入时的快照。
    doc_versions = {doc_id: doc.version for doc_id, doc in self._documents.items()}
    cache_key = build_freshness_aware_cache_key(query, doc_versions=doc_versions)
    if cache_key in self._answer_cache:
        return self._answer_cache[cache_key]   # 缓存命中，直接返回，不重新跑一遍检索
    ...
```

这里就是摄入阶段那个`version`字段真正派上用场的地方。第41章讲过的`build_freshness_aware_cache_key`在这里把"查询文本"和"当前知识库里每份文档的版本号"一起哈希成缓存键——注意`doc_versions`是从`self._documents`**实时**读取出来的当前状态，不是摄入时固定下来的快照。这意味着：

```python
# 版本号从v1改成v2——即使查询文本完全一样，缓存键也会因为版本号
# 变化而不同，旧缓存条目自然失效，不会被这次查询命中。
service.ingest("doc-python", "Python is a versatile, high-level language used in AI and web development.", version="v2")
await service.query("what is python")
print(f"after document update -> cache size grew (new key): {service.cache_size() == 2}")
```

一旦某份文档被重新摄入、版本号变成了`"v2"`，即使查询文本完全没变（还是"what is python"），算出来的缓存键也会因为`doc_versions`里这份文档的版本变化而变得不同——旧的缓存条目依然留在`self._answer_cache`里，但再也不会被这个新的缓存键命中，等价于"自然过期"，不需要额外写一段"文档更新时遍历缓存、找出相关条目删除"的清理逻辑。

## 检索无结果时，走的是诚实拒答这条路

```python
if not keyword_scores and not vector_scores:   # 两路检索都完全没有命中任何内容
    answer = RagAnswer(text="I don't have enough information in the knowledge base to answer this question.",
                        citations=[], grounded=False)   # 诚实拒答，而不是让生成模型编答案
    self._answer_cache[cache_key] = answer   # 拒答结果同样被缓存，享有缓存带来的好处
    return answer
```

第38章讲过的"诚实拒答"原则在这里同样适用——如果两路检索都完全没有命中任何内容，直接返回`grounded=False`的拒答提示，而且**这个拒答结果本身也会被写入缓存**（同样的无关查询下次再问，也不需要重新跑一遍两路检索）。这提醒我们：诚实拒答不是"检索管线里的一个例外分支"，而是这套系统需要像对待正常回答一样认真对待的一种输出结果——包括让它也享有缓存带来的性能优势。

## 本章小结

- 一条完整的RAG流水线，是把"摄入分块"、"多路独立检索"、"基于排名的融合"、"重排序聚合"、"新鲜度感知缓存"、"诚实拒答"这几个各自独立的环节，按正确的顺序和数据依赖关系串联起来的结果——理解每个环节本身重要，理解它们如何咬合在一起同样重要。
- 演示两路检索时故意使用量纲完全不同的打分方式（整数计数 vs. 0-1相似度），是为了让"用RRF按排名融合、而不是直接比较原始分数"这个设计原则有真正可验证的意义。
- 重排序聚合逻辑必须能正确处理"某份文档打分失败"的情况，让它被当作最低分而不是被误判为满分——这是第40章讲过的真实bug在完整流水线里的具体体现。
- 缓存键必须基于知识库当前的实时状态（每份文档的版本号）计算，而不是摄入时的某个快照——这样文档更新后，旧缓存自然失效，不需要额外的清理逻辑。
- 诚实拒答本身也是一种需要被同等对待的输出结果，包括让它同样享有缓存带来的好处，而不是被当作检索流程里的一个"例外情况"特殊处理。

## 动手做

```python
import asyncio
from products.rag_knowledge_base_service import RagKnowledgeBaseService

async def main():
    service = RagKnowledgeBaseService()
    service.ingest("doc-python", "Python is a high-level programming language known for readability.", version="v1")
    service.ingest("doc-unscored", "This document mentions python too but reranking will fail to score it.", version="v1")
    service.ingest("doc-unrelated", "The weather today is sunny with a light breeze.", version="v1")

    answer1 = await service.query("what is python")
    print(f"查询1 -> grounded={answer1.grounded}, text={answer1.text}")

    # 相同查询再次发起——应该命中新鲜度感知缓存
    answer2 = await service.query("what is python")
    print(f"重复查询命中缓存: {answer1.text == answer2.text}, 缓存大小: {service.cache_size()}")

    # 更新文档版本——缓存键随之改变，不会返回基于旧内容的过时答案
    service.ingest("doc-python", "Python is a versatile, high-level language used in AI and web development.", version="v2")
    await service.query("what is python")
    print(f"文档更新后缓存条目增加: {service.cache_size() == 2}")

    # 完全不相关的查询，应该诚实拒答而不是编造答案
    answer4 = await service.query("quantum physics equations")
    print(f"\n不相关查询 -> grounded={answer4.grounded}, text={answer4.text}")

asyncio.run(main())   # 启动事件循环，真正执行这个协程
```

## 面试可能会问

**问：如果让你把关键词检索和向量检索的结果合并成一份最终排序，同时还要接一层重排序、加一层缓存，你会怎么设计这条流水线，需要注意哪些环节容易出错？**

答题思路：按顺序讲清楚每个环节的关键设计点——两路检索的分数量纲不可比，必须用基于排名的融合方式（如RRF）而不是直接相加；重排序阶段，某些内容可能因为请求失败而没打上分，这种"缺失"必须被当作低分处理而不是意外获得满分优待；缓存键必须能感知到"背后依据的知识库内容是否发生了变化"，通常做法是把涉及文档的版本号也纳入缓存键的计算，这样内容更新后旧缓存自然失效；最后强调"完全没有检索到相关内容"时应该诚实拒答而不是编造答案，而且这个拒答结果本身也值得被缓存。可以总结说，这套流水线体现的是"每个环节各自负责一类容易出错的边界情况，组合在一起才能构成一个真正可信的知识库问答系统"。
