# 第41章 —— 缓存与新鲜度

代码位置：`packages/ainative-rag/src/ainative_rag/freshness.py`、`embedding_batch.py`

## 一份已经删除的文档，却在三周后又"复活"了一次

设想这样一个场景：知识库里有一份文档说"退货期限是30天"，某位用户问了"退货期限是多久"，系统检索到这份文档、生成了回答，并把这次问答存进了缓存（避免同一个问题被反复计算）。三周后，公司把政策改成了"退货期限延长到60天"，运营同事更新了知识库里的这份文档。又过了几天，另一位用户问了同样的问题"退货期限是多久"——如果缓存键只由"查询文本本身"决定，系统会直接从缓存里取出三周前那份"30天"的旧答案返回给用户，而这份文档实际上早就被更新过了。

这一章要看的`freshness.py`要解决的正是这个问题：**缓存键必须能感知到"背后依据的文档是否发生了变化"**，而不是只盯着"问题文本有没有变"。

## 缓存键必须显式包含文档版本，而不是只哈希查询文本

```python
def build_freshness_aware_cache_key(query: str, *, doc_versions: dict[str, str]) -> str:
    payload = json.dumps({"query": query, "doc_versions": doc_versions}, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

模块docstring讲清楚了这个设计的意义：

> 缓存键必须显式包含"参与生成这份答案的每份文档当前的版本标识"，而不是只哈希查询文本本身——文档版本变化时，同样的查询文本会自然产生不同的缓存键，旧缓存条目不会被错误复用，也天然具备"按doc_id关联清理"的能力（不需要额外的删除时清理机制）。

这里的思路很巧妙：**不需要额外写一套"文档更新时主动清理相关缓存"的逻辑**。只要`doc_versions`这个字典里任何一份文档的版本标识（可以是版本号、内容哈希、或者最后更新时间戳）发生了变化，同一个查询文本算出来的缓存键就会自然而然地变成一个全新的字符串——旧的缓存条目虽然依然存在于缓存系统里，但再也不会被命中，因为没有任何后续请求会再算出那个旧的键。这是一种"用键本身的设计消解掉清理问题"的思路，比"每次文档变更时遍历缓存、手动删除相关条目"更简单，也更不容易漏删。

## 一个真实的哈希碰撞bug：拼字符串远不如结构化序列化安全

docstring里记录了这个模块曾经修复过的一处真实bug：

> 早期实现用`"|".join(f"{k}:{v}")`这类手工拼接分隔符的方式构造哈希输入，如果`doc_id`或版本值本身含有`:`/`|`这类分隔符字符（真实场景下doc_id经常是路径/哈希/带命名空间的字符串，并不罕见），两组完全不同的`doc_versions`会拼接出一模一样的字符串，产生哈希碰撞。

用一个具体例子把这个bug讲透：假设有两组完全不同的文档版本信息——

- 第一组：`{"a": "1", "b": "2"}`（文档a是版本1，文档b是版本2）
- 第二组：`{"a": "1|b:2"}`（文档a的版本号本身恰好是字符串`"1|b:2"`）

如果用`"|".join(f"{k}:{v}" for k, v in doc_versions.items())`这种手工拼接方式，第一组会拼出`"a:1|b:2"`，第二组也会拼出`"a:1|b:2"`——**两组语义完全不同的数据，拼接出了一模一样的字符串**，算出来的哈希值自然也完全相同，导致本该互不相关的两次查询共享了同一个缓存键。

修复方式是改用`json.dumps`做结构化序列化：

```python
payload = json.dumps({"query": query, "doc_versions": doc_versions}, sort_keys=True, ensure_ascii=False)
```

JSON格式会给每一个字符串值正确地加上引号、并对字符串内部出现的特殊字符（包括`:`和`|`）做转义处理，所以`{"a": "1|b:2"}`和`{"a": "1", "b": "2"}`序列化出来的JSON文本**必然不同**，不可能再像手工拼接那样意外产生完全相同的字符串。

这个教训可以推广成一个通用原则：**任何时候需要把一份结构化数据（字典、多个字段的组合）转换成一个用于比较/哈希的字符串，都应该使用目标格式官方提供的序列化工具（如`json.dumps`），而不是手工拼接分隔符**——这和第32章讲的"用户输入拼进TOML文件"是同一类问题的不同表现形式：手工拼接字符串，本质上永远无法完全避免"内容本身恰好包含你用作分隔符的那个字符"这种边界情况。

`sort_keys=True`这个参数同样值得注意——它保证字典的key会按字母顺序排序后再输出，这样`{"a": "1", "b": "2"}`和`{"b": "2", "a": "1"}`（内容完全相同，只是构造时传入的顺序不同）会序列化成完全一样的JSON文本，进而算出相同的哈希值。如果不加这个参数，同一组文档仅仅因为调用方传参的顺序不同，就会被误判成"不同的一组文档"，产生两个本该合并成一个的缓存键。

## Embedding批量请求：数量对不上，绝不能只是"记一条日志然后返回None"

`embedding_batch.py`要处理的是另一类真实发生过的问题。"Embedding"（嵌入向量）是把一段文字转换成一串固定长度的数字，检索系统靠比较这些数字串的相似度来判断"意思是否相近"，这个转换过程通常支持"批量提交"——一次请求提交多段文字，一次性拿回对应的多个向量。

docstring记录的真实bug背景是：

> 批量获取向量时，如果供应商返回的向量数量和请求的文字数量对不上，原版只记一条错误日志、函数隐式返回`None`，调用方（全代码库几十处调用点）都没有检查返回值，导致这批文档的实体/关系数据静默丢失、且完全无法被感知。

这是一处教科书式的"错误被吞掉"案例：向量数量不匹配，说明这批数据在处理过程中已经出了问题（比如供应商那边丢了几条、或者多返回了几条，具体原因不重要），但"记一条日志"这个动作本身几乎不会被任何人实时看到，而"隐式返回`None`"更是把责任完全推给了调用方——而**全代码库几十处调用点都没有检查这个返回值是不是`None`**，于是这批文档的数据就这样在没有任何人注意到的情况下彻底丢失了。

## 修复：数量对不上就是硬错误，必须真正传导出去

```python
class EmbeddingCountMismatchError(RuntimeError):
    def __init__(self, *, requested: int, received: int) -> None:
        super().__init__(
            f"embedding count mismatch: requested {requested} texts but received {received} vectors — "
            f"this batch's data would be silently lost if not treated as a hard error"
        )
        self.requested = requested
        self.received = received
```

```python
async def embed_batch_with_accounting(
    texts: list[str],
    *,
    embed_fn: Callable[[list[str]], Awaitable[list[list[float]]]],
    max_chars_per_text: int = DEFAULT_MAX_CHARS_PER_TEXT,
) -> EmbeddingBatchResult:
    ...
    vectors = await embed_fn(prepared_texts)

    if len(vectors) != len(prepared_texts):
        raise EmbeddingCountMismatchError(requested=len(prepared_texts), received=len(vectors))

    return EmbeddingBatchResult(vectors=vectors, truncated_count=truncated_count)
```

修复的核心思路很直接：**数量对不上就直接抛出一个明确的硬错误**，而不是记日志后返回`None`。这个改动看起来简单，但背后是一个值得记住的设计原则——**"记日志"不能替代"让错误真正被处理"**。日志是给事后排查用的，它不会主动阻止一个错误的调用流程继续往下走；而抛出异常会强制调用方要么捕获处理、要么让程序在这里明确地失败，两种结果都比"悄悄返回一个调用方压根没检查的`None`"要可靠得多。

`EmbeddingCountMismatchError`把`requested`和`received`保存成异常对象自己的属性（而不是只写进异常消息的文本里），这样调用方捕获到异常后，可以用`exc.requested`、`exc.received`直接拿到具体数字用于监控上报，不需要去解析异常消息字符串——这是一个在本书里反复出现的小细节：**自定义异常应该把关键的诊断信息存成结构化的属性，而不是只塞进一段人类可读的文本里**。

## 超长文本：主动截断，而不是等供应商报错

```python
DEFAULT_MAX_CHARS_PER_TEXT = 32_000

for text in texts:
    if len(text) > max_chars_per_text:
        truncated_count += 1
        prepared_texts.append(text[:max_chars_per_text])
    else:
        prepared_texts.append(text)
```

docstring里的第二条设计原则是：单段文字长度超过embedding模型能处理的上限时，必须在真正调用API之前就主动截断，而不是等供应商那边因为超出限制而报错。这是一个很朴素但容易被忽视的思路——**如果你已经知道某个输入必然会导致下游报错，与其让这次调用失败后再处理异常，不如在发起调用之前就先把输入处理成一定会被接受的形态**。`truncated_count`记录了这一批里有多少段文字被截断过，让调用方能够感知"这些文档可能因为过长、被截掉了一部分内容"，从而决定要不要对它们做进一步处理（比如换用支持更长上下文的模型重新处理一遍）。

## 本章小结

- 缓存键如果只由查询文本决定，文档更新后旧的缓存答案会持续被提供给完全不知情的用户——正确做法是让缓存键显式纳入"参与生成这份答案的每份文档当前的版本标识"，文档变化时同一查询文本自然产生不同的键，不需要额外的删除时清理逻辑。
- 用手工拼接分隔符字符串来构造哈希输入是危险的——如果被拼接的内容本身恰好包含你用作分隔符的字符，两组完全不同的数据可能拼出一模一样的字符串，产生哈希碰撞；应该用`json.dumps`这类结构化序列化工具，并加上`sort_keys=True`保证字典顺序不影响结果。
- "记一条错误日志然后返回`None`"不等于"这个错误被正确处理了"——如果调用方普遍不检查返回值，数据会在没有任何人注意到的情况下静默丢失；对于"数量对不上"这类明确表示批次处理出了问题的情况，应该直接抛出携带具体诊断信息的硬错误。
- 已知会导致下游报错的输入（比如超长文本），应该在发起调用之前就主动处理（截断），而不是让调用失败后再去处理异常；处理过的数量应该被记录下来，让调用方能感知到"哪些内容被打了折扣"。

## 动手做

```python
import asyncio
from ainative_rag.freshness import build_freshness_aware_cache_key
from ainative_rag.embedding_batch import embed_batch_with_accounting, EmbeddingCountMismatchError

# 场景一：文档版本变化后，同一查询自然产生不同的缓存键
key_v1 = build_freshness_aware_cache_key("退货期限是多久", doc_versions={"policy-doc": "v1-30days"})
key_v2 = build_freshness_aware_cache_key("退货期限是多久", doc_versions={"policy-doc": "v2-60days"})
print("文档更新后缓存键是否改变：", key_v1 != key_v2)

# 场景二：embedding数量对不上时必须硬失败，而不是静默返回None
async def broken_embed_fn(texts):
    return [[0.1, 0.2]]  # 故意只返回1个向量，不管传入了多少段文字

async def main():
    try:
        await embed_batch_with_accounting(["文本A", "文本B", "文本C"], embed_fn=broken_embed_fn)
    except EmbeddingCountMismatchError as exc:
        print(f"数量不匹配被正确拦截：请求{exc.requested}条，实际收到{exc.received}条")

asyncio.run(main())
```

## 面试可能会问

**问：如果你的问答系统给结果加了缓存，知识库文档更新之后，你怎么保证用户不会看到基于旧文档生成的过时答案？**

答题思路：先指出常见的错误做法——缓存键只哈希查询文本本身,这样文档更新后旧缓存依然会命中,持续返回过时答案。正确思路是让缓存键显式纳入"参与生成这份答案的每份文档当前的版本标识",文档变化时同一查询文本自然产生不同的缓存键,旧缓存条目不会再被命中,也不需要额外写一套"文档更新时主动遍历删除相关缓存"的清理逻辑。如果能补充"构造缓存键时应该用JSON等结构化序列化工具而不是手工拼接分隔符字符串,否则不同的输入数据可能因为恰好包含分隔符字符而拼出相同的字符串、产生哈希碰撞",会展现出对这类问题更细致的考虑。
