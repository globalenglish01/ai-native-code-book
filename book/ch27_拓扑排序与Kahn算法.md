# 第27章 —— 拓扑排序与Kahn算法

代码位置：`packages/ainative-workflow/src/ainative_workflow/graph.py`（`_topological_order`函数）

## 穿衣服问题

在讲代码之前，先想一个每天都会遇到的小问题：早上穿衣服，你必须先穿袜子再穿鞋，必须先穿内衣再穿外套，但"先穿袜子还是先穿内衣"完全不重要，谁先谁后都行。如果把"必须先做A再做B"这种关系画成箭头（A → B），你会得到一张"图"——不是地图的图，是由一堆点和箭头组成的示意图。

现在的问题是：给你这样一张图，你要排出一个"我从头到尾按这个顺序做，绝对不会违反任何一条箭头约束"的先后顺序。这个问题在计算机科学里有个正式名字，叫**拓扑排序**（topological sort）。上一章我们看到`Workflow`要求节点声明`depends_on`（"我依赖谁"），拓扑排序就是把这些"谁依赖谁"的声明，转换成一份"实际按什么顺序执行"的计划表——这正是`_topological_order`这个函数要做的事。

如果你从没听过"拓扑排序"这个词，完全不用担心，本章会带你从零推导出它最经典的一种解法：**Kahn算法**，而且全程对照`ainative-workflow`里真实的生产代码，不是伪代码。

## 先建立一个直觉：什么节点"现在就能做"

回到穿衣服的例子。你不需要先想好"整个顺序"，你只需要每次问自己一个简单的问题："现在，有哪些还没穿的衣服，它依赖的东西我已经都穿好了？"——每次都从这些"当前可以做"的选项里挑一个做掉，做完之后重新问一遍这个问题，如此反复，直到所有衣服都穿完。

这就是Kahn算法的全部直觉：**不断找出"当前所有依赖都已满足"的节点，取走它，然后看这个动作有没有让其他节点也变得"可以做了"，重复这个过程**。

要把这个直觉变成代码，需要引入一个关键概念：**入度**（in-degree）。一个节点的入度，就是"这个节点依赖了多少个别的节点"（注意方向：是"我依赖了几个人"，不是"几个人依赖我"）。如果某个节点的入度是0，意味着它谁都不依赖，可以立刻执行。每当一个节点被"取走"（执行完），它下游那些依赖它的节点，入度就应该各自减1——因为它们依赖的东西，又有一个被满足了。当某个节点的入度被减到0，它就从"还在等"变成了"现在可以做"。

## 逐行拆解真实代码

有了这个直觉，我们来看`_topological_order`函数的完整实现，逐段理解：

```python
def _topological_order(nodes: dict[str, WorkflowNode]) -> list[str]:
    """Kahn算法拓扑排序；检测到环时抛出`ValueError`。"""
```

函数的输入是一个字典：key是节点名字，value是`WorkflowNode`对象。输出是一个`list[str]`——一份排好顺序的节点名字列表，按这个顺序执行，绝对不会出现"还没轮到的依赖被先执行"的情况。

**第一步：计算每个节点的入度。**

```python
    # 字典推导式：给每个节点名建一个entry，初始入度都是0。
    in_degree = {name: 0 for name in nodes}
    for node in nodes.values():   # 遍历每一个节点
        for dep in node.depends_on:   # 遍历这个节点声明依赖的每一个上游
            if dep not in nodes:
                # 依赖了一个压根不存在的节点名——这是定义本身的错误，立刻报错。
                raise ValueError(f"node '{node.name}' depends on unknown node '{dep}'")
            in_degree[node.name] += 1   # 每发现一条依赖关系，入度加1
```

先给每个节点的入度都初始化成0（`{name: 0 for name in nodes}`是一个字典推导式，等价于对每个节点名建一个entry，值都是0）。然后遍历一遍所有节点，看它声明了哪些`depends_on`——每发现一条"A依赖B"的关系，就把A的入度加1。

这里插入了一个防御性检查：`if dep not in nodes`——如果某个节点声明依赖了一个压根不存在的节点名（比如打错了字符串，写成了`"validte"`而不是`"validate"`），必须立刻报错。这是工作流**定义本身**的错误，必须尽早暴露出来，而不是让它悄悄通过、等到真正执行到一半才发现"依赖的东西根本不存在"。这是一个值得学习的工程习惯：**能在构造阶段发现的错误，就不要拖到运行阶段**——我们下一章会看到，`Workflow`的构造函数正是在`__init__`里就调用了这个排序函数，图有问题会在你刚创建`Workflow`对象的那一刻就报错，而不是等跑到一半才炸。

**第二步：建立反向索引。**

```python
    # 反向索引：key是"我"，value是"依赖了我的那些节点名字组成的列表"。
    dependents: dict[str, list[str]] = {name: [] for name in nodes}
    for node in nodes.values():
        for dep in node.depends_on:
            # dep是node依赖的上游——把node.name记录进dep的下游列表里。
            dependents[dep].append(node.name)
```

`in_degree`回答的是"我依赖谁"，`dependents`回答的是反过来的问题："谁依赖我"（也就是"谁的执行需要等我完成"）。为什么需要单独建这样一份反向索引？因为在下面的主循环里，每当一个节点被取走，我们需要去把它的下游节点的入度都减1——如果没有这份`dependents`索引，每次都得重新扫一遍全部节点的`depends_on`才能找到"谁依赖了我"，那样每取走一个节点都要扫全图一遍，整个算法会慢很多。提前把这份"反向关系"建好，取走一个节点后可以直接`dependents[current]`拿到它的下游列表，效率高得多。这也是一个常见的算法技巧：**用一份额外的、方向相反的索引，换取后续查找的速度**。

**第三步：核心循环——反复取走入度为0的节点。**

```python
    # 生成器表达式+sorted——找出所有入度已经是0的节点名，按字母序排好，
    # 保证同一份定义每次跑出的顺序都一样，不依赖字典遍历的随机性。
    ready = sorted(name for name, deg in in_degree.items() if deg == 0)
    order: list[str] = []   # 最终排好序的执行顺序
    while ready:   # 只要还有"可以立刻执行"的节点，就继续循环
        current = ready.pop(0)   # 取出最前面一个（先进先出）
        order.append(current)   # 加入最终结果，代表"这个节点排序意义上处理完了"
        for dependent in sorted(dependents[current]):   # 遍历它的每一个下游节点
            in_degree[dependent] -= 1   # 下游的入度减1，因为它依赖的这一个已经满足
            if in_degree[dependent] == 0:
                ready.append(dependent)   # 减到0了，加入下一轮候选队列
```

`ready`是"当前入度为0、可以立刻执行"的节点名列表。初始值是所有入度本来就是0的节点（这些节点谁都不依赖，从一开始就可以执行）。

主循环每一轮做三件事：

1. `ready.pop(0)`从`ready`列表最前面取出一个节点（"先进先出"），加入最终的`order`结果列表——这个节点在排序意义上"已经处理完"了。
2. 遍历它的所有下游节点（`dependents[current]`），把它们的入度各减1——表示"你依赖的节点里，又有一个刚刚满足了"。
3. 如果某个下游节点被减到入度为0，说明它现在所有依赖都已满足，把它加进`ready`，留给下一轮循环取走。

这个循环会一直进行，直到`ready`变空——要么是所有节点都处理完了，要么是卡住了（下面马上讲这种情况）。

这里有个细节值得注意：无论是最初的`ready = sorted(...)`，还是循环里的`for dependent in sorted(dependents[current])`，代码都特意加了`sorted(...)`。这不是排序算法本身需要的（Kahn算法对"同一批入度归零的节点先处理哪个"并没有硬性要求），而是为了让结果**具有确定性**——如果不排序，直接遍历字典或列表，"入度同时归零的几个节点谁先谁后"就取决于Python字典/列表的遍历顺序细节，同一份工作流定义，理论上每次跑出来的顺序可能有细微差异。这对写单元测试、排查问题都是麻烦事——"为什么这次跑的顺序和上次不一样"是一个很难调试的问题。加上`sorted(...)`之后，同一份工作流定义永远排出同一个顺序，字母序在前的先被取走，这是一个很小但很重要的工程细节：**当算法本身允许多种"同样正确"的结果时，主动选择一种确定性的规则，会为后续调试省下大量时间**。

## 环检测：为什么"取不完"就一定是有环

```python
    if len(order) != len(nodes):   # 排好序的节点数和总节点数对不上——说明有节点永远没能入度归零
        # 集合差集运算：算出"在原始节点集合里、但没出现在order里"的那些，
        # 这些就是被卡在环里（或依赖了环上节点）的节点。
        remaining = set(nodes) - set(order)
        raise ValueError(f"workflow graph has a cycle involving: {sorted(remaining)}")
    return order
```

循环结束之后，检查一件事：`order`里收集到的节点数量，是不是等于总节点数`nodes`。

想一想什么情况下这两个数字会不相等。每一轮循环，我们只能取走"入度为0"的节点；一个节点的入度只有在它依赖的所有上游节点都被取走之后，才会变成0。如果图里存在一个"环"——比如A依赖B、B又依赖A——那么A的入度要等B先被取走才能减到0，但B的入度又要等A先被取走才能减到0，这就是一个死锁：谁都无法成为"第一个"被取走的那个，因为谁都在等对方先完成。这两个节点永远不会进入`ready`列表，永远不会被加进`order`。

所以：**`len(order) != len(nodes)`当且仅当图里存在环**——这是Kahn算法一个很优雅的副产品，你不需要额外写一个"检测环"的算法，拓扑排序本身跑完之后，只要看一眼"有没有全部取完"，就自动知道图里有没有环。

`remaining = set(nodes) - set(order)`用集合的差集运算，算出"哪些节点在原始集合里、但没有出现在排好序的`order`里"——这些就是被卡在环里（或者依赖了环上节点、间接被卡住）的那些节点，把它们的名字报出来，方便调用方一眼看出问题出在哪几个节点之间，而不是只告诉你"有环"却不说是谁。

## 为什么"检测环"对工作流引擎特别重要

对一般的拓扑排序算法而言，环检测只是一个附加功能。但对`Workflow`这个具体场景，环检测几乎是**生死攸关**的——想象一下如果没有这个检查，一个不小心写出的循环依赖（比如"审批"依赖"复核"、"复核"又依赖"审批"）被传进`Workflow`的构造函数，会发生什么？`_execute`的主循环是按`self._order`（也就是这个函数算出来的顺序）遍历的，如果排序阶段没有及时报错，这两个互相依赖的节点根本不会出现在`order`里，执行时会直接"静默地"漏掉它们，既不报错、也不执行，`WorkflowRun`最终会显示"完成"，但审批和复核这两个关键节点压根没跑过——这是一种比程序崩溃更危险的故障模式：**没有任何报错、看起来一切正常，但关键逻辑悄悄地没有执行**。

而现在的实现选择在排序阶段就`raise ValueError`，而且是在`Workflow.__init__`构造对象的那一刻就会触发（下一章会看到`Workflow.__init__`里调用了`_topological_order`）——这意味着一个包含循环依赖的工作流定义，根本无法被构造出来，问题在写代码、写测试的阶段就会暴露，而不是留到某次真实运行时才被发现。这正呼应了上一章讲的"能在构造阶段发现的错误，就不要拖到运行阶段"这条原则，在这里体现得非常具体。

## 本章小结

- 拓扑排序解决的问题是：给定一堆"谁必须在谁之前"的依赖约束，算出一个满足所有约束的合法执行顺序。
- Kahn算法的核心直觉：反复找出"入度为0"（当前所有依赖都已满足）的节点取走，取走后把它的下游节点入度各减1，如果减到0就加入下一轮的候选队列，直到没有节点可取。
- 需要维护两份索引：`in_degree`（我依赖了多少人）和`dependents`（谁依赖了我，反向索引），后者是为了避免每轮都重新扫描全图去寻找下游节点。
- 排序前对`ready`列表和下游节点遍历顺序做`sorted(...)`，是为了让结果具有确定性，避免"同一份定义每次跑出不同顺序"这种难以调试的问题。
- `len(order) != len(nodes)`是检测环的判据：环上的节点的入度永远无法归零，会被永久卡在`ready`队列之外；对工作流引擎而言，环检测必须在构造阶段就报错，否则会出现"关键节点被静默跳过、却显示执行成功"这种比崩溃更危险的故障。

## 动手做

自己构造一个有环的工作流定义，验证`Workflow`会在构造阶段就报错，而不是等到`run()`才出问题：

```python
from ainative_workflow import Workflow, WorkflowNode


def noop(ctx: dict) -> None:
    return None   # 一个什么都不做的占位函数，这个演示只关心结构本身


try:
    # a依赖b、b又依赖a——一个明显的循环依赖，构造Workflow时就应该报错。
    wf = Workflow([
        WorkflowNode(name="a", fn=noop, depends_on=("b",)),
        WorkflowNode(name="b", fn=noop, depends_on=("a",)),
    ])
except ValueError as exc:
    print("构造阶段就报错了：", exc)   # workflow graph has a cycle involving: ['a', 'b']
```

## 面试可能会问

**问：什么是拓扑排序？请说说Kahn算法的实现思路，以及怎么检测图中的环。**

答题思路：先给出精确定义（给定一组"先后依赖"约束，求一个满足所有约束的线性顺序），然后讲清楚Kahn算法的两个核心数据结构——入度数组和反向的邻接（dependents）索引，再讲主循环"反复取走入度为0的节点、更新下游入度"这个过程。环检测部分是加分项：讲清楚"环上的节点入度永远无法归零，因此永远不会被加入结果列表"，所以只需要比较"最终排序结果的长度"和"总节点数"是否相等，就能判断是否有环，不需要单独写一个检测环的算法。如果能进一步提到"为什么这个检测要在构造阶段而不是执行阶段做"（避免关键节点被静默跳过却显示成功这类比崩溃更危险的故障），会显著体现你不只是背了算法本身，还理解它在真实系统里为什么重要。
