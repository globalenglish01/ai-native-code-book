# 第32章 —— 项目名校验与模板系统

代码位置：`packages/ainative-cli/src/ainative_cli/scaffold.py`、`templates.py`

## 一个真实复现过的bug：不校验输入会生成"坏"文件

这一章要讲的第一个知识点，来自`scaffold.py`里一段特别值得注意的注释：

```python
_VALID_PROJECT_NAME_RE = re.compile(r"^[A-Za-z0-9][A-Za-z0-9._-]*$")
"""与PyPI包名规则一致的安全字符集——`project_name`会被原样拼进生成的
`pyproject.toml`（TOML字符串字面量）和`README.md`里，不做校验的话，
一个含双引号/换行符的项目名会生成语法错误、`uv sync`直接失败的
`pyproject.toml`（已用真实输入复现过）。"""
```

注释里的"已用真实输入复现过"这句话很关键——这不是一个假设性的担忧，而是一个**真实测试出来的bug**。想象一下：如果用户执行`ainative new 'my"project'`（项目名里带了一个双引号），而生成`pyproject.toml`的代码是这样写的：

```python
f'name = "{project_name}"\n'
```

`project_name`如果本身包含双引号，被原样拼进这个f-string里，最终生成的文件内容会变成`name = "my"project""`——这在TOML格式里是**语法错误**的字符串，因为多出来的双引号提前"结束"了字符串字面量。用户拿到这个新生成的项目，第一步执行`uv sync`就会直接报错，而且报错信息是"TOML解析失败"，跟"项目名不合法"这个真正的根源完全对不上——用户很可能一头雾水，不知道问题出在自己敲的项目名上。

这就是`_VALID_PROJECT_NAME_RE`存在的意义：**任何会被原样拼接进生成文件里的用户输入，都必须提前校验它不包含会破坏目标文件格式的字符**。这是一个可以推广到任何"代码生成"场景的通用原则——不只是`pyproject.toml`，任何"把用户输入直接嵌入某种结构化格式（HTML、SQL、JSON、YAML……）"的地方，都需要考虑"如果输入恰好包含这种格式的特殊字符，会不会破坏整体结构"这个问题（这和SQL注入、XSS攻击背后的原理其实是同一类问题的不同表现形式，只是这里的后果是"生成一个语法错误的文件"而不是"安全漏洞"，但根源都是"没有对将被嵌入结构化格式的输入做校验/转义"）。

## 两种不同的异常类型，对应两种不同的失败原因

```python
class ProjectAlreadyExistsError(RuntimeError):
    """目标目录已存在且非空时抛出"""

class InvalidProjectNameError(ValueError):
    """`project_name`包含会破坏生成文件格式的字符时抛出"""
```

注意这两个异常继承自不同的基类——`ProjectAlreadyExistsError`继承`RuntimeError`，`InvalidProjectNameError`继承`ValueError`。这不是随意的选择：**`ValueError`是Python里"参数值本身不符合预期"这类错误的标准基类**（比如"用户输错了项目名"），而**`RuntimeError`更适合"当前的运行时状态导致操作无法继续"这类错误**（比如"目标目录已经有内容了，不能贸然覆盖"）。这个区分让调用方可以更精确地判断"这次失败是因为我传错了参数，还是因为环境状态不允许这么做"——两者需要的应对方式完全不同（前者应该提示用户"改一下项目名重试"，后者应该提示"要不要用`--force`覆盖，或者换个目录"）。

## `force`参数：默认拒绝覆盖，显式选择才能覆盖

```python
if target_dir.exists() and any(target_dir.iterdir()) and not force:
    raise ProjectAlreadyExistsError(...)
```

三个条件都满足才报错：目录存在、目录非空、调用方没有传`force=True`。**默认行为是"拒绝"，只有调用方明确传了`force=True`才允许覆盖**——这是一种很常见也很稳妥的设计取向："默认安全，需要显式选择才能执行有风险的操作"，比"默认允许覆盖，需要显式传参数才能保护"更不容易造成意外的数据丢失（想象一下反过来的设计：默认允许覆盖，用户一不小心把新项目生成到了一个已经有其他工作内容的目录里，原有文件被悄悄覆盖，这个后果比"报错提示要不要加`--force`"严重得多）。

`any(target_dir.iterdir())`这一行也值得留意：`target_dir.iterdir()`返回的是一个"生成器"（一边遍历一边产出结果，而不是一次性把整个目录内容读进一个列表），`any(...)`只需要"看到第一项"就能判断"非空"，不需要把整个目录内容都读完——对一个可能包含大量文件的目录来说，这样判断"是否非空"比`len(list(target_dir.iterdir())) > 0`更高效（后者需要先把所有内容都读进一个列表才能计算长度）。

## 模板系统：把"生成什么"和"怎么生成"分开

`scaffold_project`函数本身不知道"minimal类型的项目具体应该包含哪些依赖包、main.py长什么样"——这些信息由一个独立的`ProjectTemplate`对象提供，`scaffold.py`只负责"把这份模板信息，正确地渲染成磁盘上的文件"：

```python
files = {
    target_dir / "pyproject.toml": render_pyproject_toml(project_name, template),
    target_dir / "README.md": render_readme(project_name, template),
    target_dir / "main.py": template.main_py,
    target_dir / ".env.example": render_env_example(),
}
```

这种"内容渲染逻辑"和"具体模板数据"分离的设计，让新增一种项目类型（比如"多智能体客服平台"模板）不需要改动`scaffold.py`里的任何一行代码——只需要在`templates.py`里定义一份新的`ProjectTemplate`数据，注册进`TEMPLATES`字典即可。**"通用的处理逻辑"和"具体的数据/配置"分离，是让系统易于扩展的一个基本原则**，这个包虽然规模不大，但完整地体现了这个原则。

## 本章小结

- 任何会被原样拼接进生成文件（TOML/JSON/HTML等结构化格式）的用户输入，都必须提前校验，防止特殊字符破坏目标文件的语法结构——这是本章讲的真实bug的教训，也是SQL注入/XSS类问题背后同样的原理。
- 自定义异常应该按"参数本身不合法"（继承`ValueError`）和"运行时状态不允许"（继承`RuntimeError`）分开设计，让调用方可以精确区分失败原因、采取不同的应对方式。
- 有风险的覆盖类操作应该默认拒绝，只有调用方显式传参数（如`force=True`）才允许执行——"默认安全"比"默认宽松"更不容易造成意外损失。
- 把"通用处理逻辑"和"具体模板数据"分离，能让系统在不修改核心代码的前提下方便地扩展新类型。

## 动手做

```python
from ainative_cli.scaffold import scaffold_project, InvalidProjectNameError
from ainative_cli.templates import get_template
from pathlib import Path
import tempfile

template = get_template("minimal")

try:
    with tempfile.TemporaryDirectory() as tmpdir:
        scaffold_project(Path(tmpdir) / "bad", 'my"project', template)
except InvalidProjectNameError as exc:
    print("被正确拦截：", exc)
```

## 面试可能会问

**问：如果你的系统需要把用户输入的一段文字，动态拼接进生成的配置文件（比如YAML/TOML/JSON）里，你会注意什么？**

答题思路：直接点明核心风险——用户输入如果恰好包含目标格式的特殊字符（引号、换行符、控制字符等），会破坏生成文件的语法结构，轻则生成文件无法被正确解析，重则可能引发注入类安全问题。给出具体的应对方式：要么严格校验输入只允许安全字符集（比如这里"类似PyPI包名规则"的正则），要么使用目标格式官方提供的转义/序列化工具（比如用`json.dumps`而不是手动拼接JSON字符串）。如果能提到"这个具体的bug曾经被真实复现过，而不是理论上的担忧"，会让回答更有说服力。
