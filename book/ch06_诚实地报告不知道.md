# 第6章 —— 诚实地报告"不知道"

代码位置：`packages/ainative-core/src/ainative_core/usage_tracking.py`

## 一个容易被忽视的成本核算陷阱

假设你的公司同时用云端API（Anthropic/OpenAI）和自建的开源模型服务（比如用vLLM/SGLang自己部署的开源模型）。你写了一个"用量采集"功能，每次模型调用结束后，把消耗的token数记下来，用来算成本、画看板。

云端API的响应里通常都带着精确的用量信息（`input_tokens`/`output_tokens`），但**自建的推理服务经常不返回这个字段**。如果你的采集代码写成这样：

```python
def extract_usage(response) -> tuple[int, int]:
    # getattr(对象, 属性名, 默认值)——尝试读取response.usage_metadata这个
    # 属性，如果这个属性根本不存在，就返回一个空字典{}兜底，不会报错。
    usage = getattr(response, "usage_metadata", {})
    # dict.get(key, 默认值)——查不到input_tokens/output_tokens这两个key
    # 时，各自用0填充；问题就出在这里：0既可能是"真实测出来是0"，
    # 也可能是"压根没查到、随便填的占位数字"，两种情况被混在了一起。
    return usage.get("input_tokens", 0), usage.get("output_tokens", 0)
```

看起来很合理——拿不到就当作0。但这里藏着一个后果严重的陷阱：**"这次调用真的消耗了0个token"和"这次调用消耗了多少token我们根本不知道"，是两件完全不同的事，但上面这段代码把它们混成了同一个值：0**。你的成本看板会把所有走自建推理服务的调用都记成"免费"，造成一个**没有任何报错、也没有任何异常日志、却持续存在的系统性成本低估**——这种bug最难被发现，因为它不崩溃、不报错，只是安静地让数字变得不准确。

## `ainative-core`的解法：三元组，而不是二元组

`ainative_core.usage_tracking`里的`_extract_usage`函数，返回值不是`(input_tokens, output_tokens)`这样的二元组，而是`(input_tokens, output_tokens, usage_available)`这样的三元组：

```python
def _extract_usage(response: LLMResult) -> tuple[int, int, bool]:
    input_tokens = 0
    output_tokens = 0
    # 先假设"没有拿到任何用量数据"，只有真的读到了才会改成True。
    usage_available = False

    # response.generations是"一次调用可能生成多组结果"的嵌套列表结构，
    # 所以要用两层for循环——外层遍历每一组，内层遍历组内的每一条。
    for generation_list in response.generations:
        for generation in generation_list:
            # 分两步、每一步都用getattr加默认值兜底，防止某一层属性
            # 缺失时直接抛AttributeError中断整个函数。
            message = getattr(generation, "message", None)
            usage = getattr(message, "usage_metadata", None) if message is not None else None
            # isinstance(usage, dict)——确认usage真的是一个字典（而不是
            # None或者别的类型），只有这种情况才算"真的拿到了用量数据"。
            if isinstance(usage, dict):
                usage_available = True
                # usage.get("input_tokens") or 0——如果这个key存在但值
                # 是None，用or把它兜成0，避免后面相加时出现None+数字报错。
                input_tokens += usage.get("input_tokens") or 0
                output_tokens += usage.get("output_tokens") or 0

    # 返回三元组，而不是二元组——多出来的usage_available就是本章要讲的
    # "诚实的界线"。
    return input_tokens, output_tokens, usage_available
```

第三个返回值`usage_available`，就是这条"诚实的界线"：
- `(0, 0, True)`：确实拿到了用量数据，而且刚好就是0（理论上罕见，但不是不可能）。
- `(0, 0, False)`：根本没有拿到任何用量数据——这次调用的真实成本，是一个"未知数"，不是"零"。

这条信息最终会被写进用量事件里（[usage_tracking.py:162-178](../packages/ainative-core/src/ainative_core/usage_tracking.py#L162-L178)）：

```python
self._sink.record({
    "agent_name": self._agent_name,
    "provider": self._provider,
    # or——如果_extract_model_name(response)没解析出模型名（返回了
    # 假值，比如None或空字符串），就用self._model_id这个兜底值代替。
    "model": _extract_model_name(response) or self._model_id,
    "input_tokens": input_tokens,
    "output_tokens": output_tokens,
    # 把"这次到底有没有真的拿到用量数据"这个事实，原样记录下来，
    # 交给下游自己决定怎么处理，而不是在这一步就悄悄抹掉这个信息。
    "usage_available": usage_available,
    "timestamp": time.time(),  # 记录这条事件发生的时间戳
})
```

下游做成本核算、画看板的代码，现在**有能力**去区分"这条记录的0是真的0"还是"这条记录的0意味着我们压根不知道"——具体怎么处理这两种情况（比如给"不可见用量"的调用单独标红提醒运维、或者按供应商的公开定价做一个估算），是下游自己的决定，`usage_tracking`这一层的职责只是**如实提供这份区分度**，不替下游做决定，也不能悄悄把"未知"伪装成"零"。

## 一个更普遍的工程原则

这一章要传达的道理，其实比"多加一个字段"更普遍：**当你的系统"不知道"某件事的时候，诚实地说出"不知道"，永远好过用一个看起来合理的默认值去掩盖这个事实**。

这个原则在这本书后面还会反复出现：
- 第十三部分（RAG）里，检索不到相关内容时，正确的做法是"诚实拒绝回答"，而不是让模型编一个看起来像模板答案的假内容。
- 第五部分（治理门禁）里，`GateStatus`专门有一个`UNKNOWN`状态，区别于"检查通过"和"检查失败"——因为"这项检查这次没能真正执行"和"执行了、结果是失败"是完全不同的两件事。
- 第四十章（重排序）里，一个文档没能拿到重排序分数时，不该被当成"满分"（这会让它错误地排到最前面），而应该被当成"未知，保守处理"。

记住这个模式：**"0"、"False"、"通过"这类看起来干净利落的默认值，往往是在掩盖"我们其实不知道"这个更重要的事实**。下次你写一个"拿不到数据就返回默认值"的函数时，先问自己一句：这个默认值，会不会被下游误读成"一个真实、肯定的结果"？

## 本章小结

- 自建推理服务经常不返回用量信息，把"没有数据"偷懒地当成"0"会造成难以察觉的系统性成本核算错误。
- `_extract_usage`用一个额外的布尔值`usage_available`，明确区分"真的是0"和"压根不知道"，把决定权交还给下游。
- 更普遍的原则：系统"不知道"某件事时，应该诚实地表达"不知道"，而不是伪造一个看似合理的默认值去掩盖它——这个原则在RAG、治理门禁等多个模块里反复出现。

## 动手做

```python
from ainative_core.usage_tracking import UsageTrackingCallbackHandler
from ainative_core.memory_backends import InMemoryUsageSink

# InMemoryUsageSink——一个把用量事件存进内存列表的简单实现，
# 方便demo/测试时查看采集到的结果，不需要真的连数据库。
sink = InMemoryUsageSink()
handler = UsageTrackingCallbackHandler(sink, agent_name="demo", provider="self_hosted", model_id="vllm:my-model")

# 模拟一个"没有usage_metadata"的响应（自建推理服务的典型情况）
class FakeMessage:
    pass  # 没有usage_metadata属性

class FakeGeneration:
    message = FakeMessage()   # 类属性，这个"假生成结果"自带一个FakeMessage实例

class FakeResponse:
    # 嵌套两层列表，模拟response.generations这种"多组结果"的结构。
    generations = [[FakeGeneration()]]
    llm_output = None

# 手动调用回调方法，模拟"一次模型调用结束"这个事件真正发生时的效果。
handler.on_llm_end(FakeResponse(), run_id=None)
print(sink.events())  # 观察usage_available字段是True还是False
```

## 面试可能会问

**问：如果你负责的系统里，某些数据源经常"缺失"某个字段，你会怎么设计这个字段的默认值？**

答题思路：不要直接说"给个默认值兜底就行"，而要强调"缺失"和"合法地为空/为零"是两种不同的语义，二者混为一谈会在下游造成误判。可以举这个框架里`usage_available`布尔标记的例子——用一个额外的字段/标记，把"数据缺失"这个事实显式表达出来，交给下游决定怎么处理，而不是在数据采集这一层就悄悄把"缺失"伪装成一个具体数值。这体现的是"诚实地暴露不确定性，而不是替别人做决定"这种更成熟的系统设计思维。
