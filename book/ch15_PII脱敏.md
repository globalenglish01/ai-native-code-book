# 第15章 —— PII脱敏

代码位置：`packages/ainative-security/src/ainative_security/pii_redaction.py`

## 为什么这是一个"绝不能出错"的模块

想象一下：一个客服Agent的对话记录需要被存进数据库用于后续分析和审计。如果用户在对话里说了自己的手机号，而这段记录里"脱敏"这一步的代码本身出了bug（比如抛了个异常），会发生什么？如果异常没有被妥善处理，整个"保存这条对话记录"的流程可能直接崩溃——**因为一个本该做"锦上添花的安全防护"的功能出错，反而让核心业务功能（保存对话）也无法正常工作**。这是一种本末倒置：安全防护本身不应该成为一个新的、更严重的故障来源。

这一章的模块只做一件很小的事——用正则表达式识别中国大陆的身份证号和手机号，把中间部分打码——但它体现了一种值得学习的"防御性设计"哲学。

## 核心原则："绝不抛异常"

看`redact_pii_text`函数的结构：

```python
def redact_pii_text(text: str) -> str:
    if not text or not isinstance(text, str):
        return text
    try:
        text = _CHINA_ID_CARD_RE.sub(_mask_id_card, text)
        text = _CHINA_MOBILE_RE.sub(_mask_mobile, text)
    except Exception:  # noqa: BLE001
        return text
    return text
```

两层防护：第一层，输入本身不是一个正常字符串（是`None`、空字符串或者根本不是字符串类型）时，直接原样返回，不尝试做任何处理；第二层，即使真正执行脱敏的逻辑出了任何未曾预料的错误，也统一捕获，**返回未处理的原始文本，而不是让异常继续往外传播**。

这里的取舍是明确的：**"这一次可能没能成功脱敏"，好过"这一次把整个保存对话的流程搞崩溃"**。宁可承担一次漏检的风险，也不能让防护本身变成新的故障源——这是很多安全/审计类模块都应该遵循的设计原则：**它们的失败模式应该是"退化成不做任何事"，而不是"把调用方一起拖下水"**。

## 正则表达式里的"零宽断言"：为什么不用`\b`

看身份证号的正则表达式：

```python
_CHINA_ID_CARD_RE = re.compile(r"(?<!\d)\d{17}[\dXx](?![\dXx])")
```

`(?<!\d)`和`(?![\dXx])`分别是"零宽负向后顾断言"和"零宽负向前瞻断言"——意思分别是"这个位置前面不能是一个数字"、"这个位置后面不能紧跟数字或X"。**这两个断言不会被算进最终匹配到的文字里**（"零宽"的含义），它们只是在匹配发生前后"看一眼"周围的字符，用来避免匹配到一个更长数字串的中间一段。

为什么不用更常见的`\b`（单词边界）？代码注释里给出了答案：**Python的正则引擎把CJK（中日韩）表意文字也算作"单词字符"（`\w`）**。这意味着如果身份证号前面紧跟着一个中文字符（比如"号是310101...1234"这种真实的书写方式），`\b`不会在"中文字符"和"数字"之间产生边界——因为两者都被算作`\w`——导致这类真实场景下的身份证号完全无法被正确匹配到。用`(?<!\d)`（明确判断"不是数字"，而不是"边界"）就避开了这个陷阱，这是一个很容易被忽视、但在处理中文文本时必须留意的正则表达式细节。

## 脱敏方式：保留业务可读性，而不是整段抹去

```python
def _mask_id_card(m: re.Match[str]) -> str:
    s = m.group(0)
    return f"{s[:6]}********{s[-4:]}"

def _mask_mobile(m: re.Match[str]) -> str:
    s = m.group(0)
    return f"{s[:3]}****{s[-4:]}"
```

脱敏不是把整段数字替换成一个不透明的占位符（比如`[REDACTED]`），而是**保留首尾一小段，只涂黑中间部分**——`138****1234`这种格式仍然能让人一眼看出"这是一个手机号"，方便审计/排查问题时保留业务上下文，同时又不暴露完整号码。这是一种在"完全不脱敏"和"完全抹去信息"之间的折中，具体选择哪种折中方式，取决于你的业务到底需要保留多少可读性——这个模块的选择（保留能辨认类型的首尾片段）是一个很常见、也很实用的默认策略。

## 一个诚实的边界声明

模块docstring明确写出了自己**没有**覆盖的范围：

> 明确未覆盖、留待后续评估：人名、地址、银行卡号等无固定格式规律、需要上下文理解才能识别的PII类型，通常需要专门的NER模型/服务，超出"规则匹配"这个第一阶段的范围。

这不是缺陷，而是一种诚实——**正则表达式只能识别"有固定格式规律"的信息**（身份证号有固定的18位数字结构，手机号有固定的11位数字加特定开头），像人名、地址这类没有统一格式、需要理解上下文才能识别的信息，天然超出了正则匹配这种方法能覆盖的范围，需要专门的NER（命名实体识别）模型来处理。**明确写出"我们目前不覆盖什么"，和写出"我们覆盖什么"同样重要**——否则使用方可能会误以为"用了这个模块，所有PII都安全了"，从而在人名、地址泄露这类问题上放松警惕。

## 本章小结

- 安全/审计类模块的失败模式应该是"退化成不做任何事"，而不是拖垮调用方的核心业务流程——两层防护（输入类型检查+`try/except`兜底）确保这一点。
- 处理中文文本时，正则表达式的`\b`（单词边界）可能因为CJK字符也被算作"单词字符"而失效，需要用`(?<!\d)`/`(?!\d)`这类显式的零宽断言代替。
- 脱敏应该在"完全暴露"和"完全抹去"之间找到平衡——保留能辨认信息类型的首尾片段，兼顾安全和可读性。
- 诚实地声明模块的覆盖边界（"哪些类型的PII我们不处理"），比只强调"我们处理什么"更重要，避免使用方产生错误的安全感。

## 动手做

```python
from ainative_security.pii_redaction import redact_pii_text

print(redact_pii_text("我的手机号是13812345678，身份证号是110101199001011234"))
print(redact_pii_text(None))       # 应该原样返回None，不报错
print(redact_pii_text(12345))      # 应该原样返回12345，不报错

# 验证幂等性：对已经脱敏过的文本再脱敏一次，应该不会有变化
once = redact_pii_text("13812345678")
twice = redact_pii_text(once)
print(once == twice)
```

## 面试可能会问

**问：设计一个PII脱敏模块时，你会怎么处理"脱敏逻辑本身出错"这种情况？**

答题思路：强调"安全/审计类功能不应该成为新的故障源"这个原则——脱敏失败时应该优雅降级（原样返回或跳过这条记录），而不是让异常向上传播、拖垮调用它的核心业务逻辑。可以进一步提到"输入校验+异常兜底"这两层防护的具体做法，以及"明确声明覆盖边界"这个容易被忽视但很重要的实践——展示你不仅会写正则表达式，还理解一个防护性模块该有的整体设计姿态。
