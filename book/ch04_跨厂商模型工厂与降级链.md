# 第4章 —— 跨厂商模型工厂与降级链

代码位置：`packages/ainative-core/src/ainative_core/model_factory.py`

## 场景：凌晨三点，Anthropic的API挂了

你的Agent系统全部依赖Anthropic的Claude模型。某天凌晨，Anthropic服务出现区域性故障，你的Agent开始大面积报错。如果这时候有一套"自动切换到备用供应商（比如OpenAI或DeepSeek）"的机制，值班同事根本不需要被叫醒——系统会自己完成降级。这一章要讲的，就是`ainative-core`里这套"跨厂商模型工厂"的设计，以及它背后一次真实踩过的坑。

## 先建立一个概念：`model_id`长什么样

这个框架约定模型标识的格式是`"供应商:具体模型名"`，比如`"anthropic:claude-sonnet-4-5"`、`"openai:gpt-4o"`。[`_provider_of`](../packages/ainative-core/src/ainative_core/model_factory.py#L119)这个函数负责从这个字符串里解析出供应商：

```python
def _provider_of(model_id: str) -> ModelProvider:
    # model_id.split(":", 1)——按冒号切一刀，最多切成2段，取第0段
    # （也就是冒号前面的部分）。"if ':' in model_id else ''"是一个
    # 条件表达式：如果字符串里根本没有冒号，就直接给prefix一个空字符串，
    # 避免split出来的结果跟预期不一样。
    prefix = model_id.split(":", 1)[0] if ":" in model_id else ""
    try:
        # ModelProvider(prefix)——尝试把这个字符串转换成对应的枚举值，
        # 比如"anthropic"会变成ModelProvider.ANTHROPIC。
        return ModelProvider(prefix)
    except ValueError:
        # 转换失败（字符串不在枚举定义范围内，比如拼错了或者没冒号）——
        # 不让程序崩溃，退回到一个默认的"自动判断"选项。
        return ModelProvider.AUTO
```

这里有个值得学的小技巧：`ModelProvider(prefix)`——把一个字符串传给一个`StrEnum`枚举类，Python会尝试把它转换成对应的枚举成员，如果字符串不在枚举定义的范围内（比如拼写打错了，或者压根没有冒号），会抛出`ValueError`。这段代码用`try/except`把这种"转换失败"的情况优雅地兜底为`ModelProvider.AUTO`，而不是让整个流程直接崩溃。

## `build_model`：先看最基础的构建函数

```python
def build_model(
    model_id: str,
    *,
    # config: ProviderConfig | None = None——这个参数默认是None，
    # 表示"调用方不传的话，就用某种默认方式自己构造一份配置"。
    config: ProviderConfig | None = None,
    temperature: float = STRUCTURED_AGENT_TEMPERATURE,
    ...
) -> BaseChatModel:
    # config or ProviderConfig.from_env()——如果调用方传了config就用它，
    # 否则调用ProviderConfig.from_env()从环境变量里读取配置构造一份。
    cfg = config or ProviderConfig.from_env()
    # dict(...)把temperature_kwargs函数算出来的结果转换成一个普通字典。
    kwargs = dict(temperature_kwargs(model_id, temperature))
    ...
    # **kwargs——把字典kwargs里的每一对key:value，展开成
    # "key=value"的形式传给函数，等价于把字典"拆包"成一堆具名参数。
    return init_chat_model(model_id, **kwargs)
```

这个函数做的事情很朴素：根据`model_id`判断供应商，从配置里取出对应的API密钥，拼好参数字典，交给LangChain的`init_chat_model`去真正构造模型客户端。值得注意的细节是`temperature_kwargs`——有些"推理模型"（模型名字里带`reasoner`/`o1`/`o3`/`o4`这类关键词的）根本不支持自定义`temperature`参数，传了反而会报错，这个函数会提前判断、跳过不该传的参数。这是一种很典型的"防御性工程"：与其让下游因为传错参数而崩溃，不如提前判断清楚。

## 真正的重点：为什么不能用`.with_fallbacks()`

这一节要讲这一章、乃至这本书里最值得记住的一个真实bug教训。

如果你去查LangChain的官方文档，你会发现它自带一个"降级"方法：`primary_model.with_fallbacks([backup_model])`——听起来很方便，直接调用就能加上自动降级。**但这个框架里明确禁止使用这个写法**，原因写在模块开头的docstring里：

> `.with_fallbacks()`返回的`RunnableWithFallbacks`不是`BaseChatModel`的子类，如果把这个对象直接传给`create_agent(model=...)`，凡是内部会对`model`做`BaseChatModel | str`类型检查（比如尝试把它当字符串spec处理、调用`.count(":")`之类）的框架代码都会直接抛`AttributeError`，导致agent 100%创建失败。

翻译成人话：`with_fallbacks()`返回的东西"看起来像"一个模型，但它的**类型**其实是另一种东西（`RunnableWithFallbacks`）。而框架里创建Agent的代码，在某些地方会检查"你传进来的这个`model`参数，到底是不是一个真正的`BaseChatModel`"——如果类型对不上，即使这个对象表面上"能用"，也会在某个意想不到的地方直接崩溃报错。这是一个**只有在真正跑起来才会暴露、代码审查时很容易被忽略**的坑，因为`.with_fallbacks()`这行代码本身语法完全正确，逻辑上"看起来"也没问题。

正确的做法是什么？用`ModelFallbackMiddleware`——把降级逻辑放到"中间件"这一层，而不是直接改变模型对象本身的类型：

```python
# 返回值类型是一个tuple（元组，固定长度、按位置区分的一组值）：
# 第一项是真正的模型对象，第二项是可能为None的降级中间件。
def build_agent_model_with_fallback(...) -> tuple[BaseChatModel, ModelFallbackMiddleware | None]:
    # 先构造好"主力模型"——这一步之后primary的类型始终是BaseChatModel。
    primary = build_agent_model(config=cfg, model_id=model_id, ...)

    # 用来收集"备用模型"的空列表，类型注解表示"里面每个元素都是
    # BaseChatModel"。
    fallbacks: list[BaseChatModel] = []
    if cfg.openai_api_key:
        # 只有配置里真的填了openai的密钥，才把它作为备用选项加进来。
        fallbacks.append(build_model("openai:gpt-4o", config=cfg, ...))
    if cfg.deepseek_api_key and cfg.preferred_language not in ("ja", "zh"):
        # and连接两个条件，两个都满足才会加入这个备用模型；
        # not in (...)判断"不在这个元组列出的几个值当中"。
        fallbacks.append(build_model("deepseek:deepseek-chat", config=cfg, ...))

    if not fallbacks:
        # 一个都没配置——没有任何备用模型，第二项返回None。
        return primary, None

    # *fallbacks——把列表"拆开"，逐个作为独立参数传给
    # ModelFallbackMiddleware的构造函数（相当于fallbacks有几个元素，
    # 就相当于写了几个位置参数）。
    return primary, ModelFallbackMiddleware(*fallbacks)
```

关键在于：`primary`这个变量，从头到尾都是一个货真价实的`BaseChatModel`，类型从未被"污染"过。降级的逻辑（"主模型调用失败时，换成备用模型重试"）被搬到了`ModelFallbackMiddleware`这个独立的中间件对象里，调用方使用的时候是这样组合的：

```python
# middleware是一个列表，可以同时放好几个中间件——fallback_mw只是
# 其中一个，它在真正调用模型失败时才会介入，负责临时换一个模型重试。
create_agent(model=primary, middleware=[..., fallback_mw])
```

`model=primary`永远拿到一个类型正确的对象，而"要不要降级、降级到谁"这件事完全由`middleware`列表里的`fallback_mw`在实际调用失败时接管——它会调用`request.override(model=...)`，在请求层面临时换一个模型重试，而不是在对象层面"伪装成"另一种类型。

## 这个bug教会我们什么

这类bug有一个共同特征：**它不会在"写代码的时候"报错，只会在"某条特定路径被真正触发时"报错**。如果你从来没有测试过"主力模型调用失败、触发降级"这条路径，你可能永远不会发现`.with_fallbacks()`这个坑。这提醒我们一件事：**类型系统能帮你在写代码时发现很多问题，但类型系统本身也可能被绕过（比如一个方法返回了"看起来能用但类型不对"的对象）——测试真实的失败路径，永远是补充类型检查之外必不可少的一环**。

## 本章小结

- 模型工厂的核心职责是"给定一个`model_id`，正确地构造出对应供应商的模型客户端，并且正确处理API密钥/temperature这些细节差异"。
- 跨厂商降级绝对不能通过改变模型对象本身的类型来实现（`.with_fallbacks()`的坑），而应该用中间件模式，让降级逻辑独立于模型对象存在。
- 这是一个"表面上语法正确、逻辑上看起来也没问题，但会在特定路径下导致100%失败"的真实生产事故，值得当作案例记住。

## 动手做

```python
from ainative_core.model_factory import build_agent_model_with_fallback
from ainative_core.config import ProviderConfig

# 构造一份最简单的配置，只填了anthropic这一个供应商的（假）密钥。
cfg = ProviderConfig(anthropic_api_key="fake-key-for-demo")
# 函数返回一个元组，这里用"解包"语法同时接收两个返回值：
# 第一个赋给primary，第二个赋给fallback_mw。
primary, fallback_mw = build_agent_model_with_fallback(config=cfg)
print(type(primary))       # 应该是一个真正的BaseChatModel子类
print(fallback_mw)          # 因为没配置任何备用供应商密钥，应该是None
```

## 面试可能会问

**问：你怎么设计一个"跨厂商大模型自动降级"的机制？**

答题思路：先明确"降级"要解决的问题（主力供应商故障/限流时自动切换备用供应商），再强调一个容易被忽略的坑——降级逻辑不应该改变"模型对象"本身的类型（用组合、用中间件模式，而不是包装/继承出一个新类型），并举出这个框架里`.with_fallbacks()`的真实教训。这个回答的亮点在于，它展示了你不仅知道"要做降级"，还知道"降级实现方式本身可能引入新的、隐蔽的bug"，这是更高一层的工程判断力。
