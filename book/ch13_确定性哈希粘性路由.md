# 第13章 —— 确定性哈希粘性路由（进阶：存储层怎么配合）

代码位置：`packages/ainative-prompt/src/ainative_prompt/store.py`

上一章讲了"确定性哈希"这个核心算法本身。这一章往上走一层，看`InMemoryPromptStore`这个具体的存储实现，是怎么和这个算法配合，构成一套完整的、可以在真实项目里直接使用的A/B路由系统的。

## 两层嵌套字典：为什么要设计成这个形状

```python
class InMemoryPromptStore:
    def __init__(self) -> None:
        # 外层key是(agent_name, prompt_key)这个元组（"这是哪个Agent的
        # 哪个Prompt位置"），value又是一个字典（key是变体名，
        # value是具体的PromptVariant对象）——两层嵌套。
        self._variants: dict[tuple[str, str], dict[str, PromptVariant]] = {}
        # 记录粘性路由决策：key是(agent_name, prompt_key, thread_id)
        # 三元组，value是曾经给这个会话选中过的变体名字符串。
        self._sticky: dict[tuple[str, str, str], str] = {}
```

`_variants`的key是`(agent_name, prompt_key)`这个二元组，value又是一个字典（key是变体标识，value是`PromptVariant`对象）。为什么要设计成"两层嵌套"，而不是直接用`(agent_name, prompt_key, variant)`三元组做一层扁平字典的key？

答案在于`save_variant`和`get_active_variants`的使用模式：

```python
async def save_variant(self, agent_name, prompt_key, variant):
    # setdefault见下方详细解释——拿到（或创建）这个位置对应的内层字典。
    bucket = self._variants.setdefault((agent_name, prompt_key), {})
    bucket[variant.variant] = variant   # 按变体名存进这个内层字典

async def get_active_variants(self, agent_name, prompt_key):
    # .get(key, {})——查不到这个位置就返回空字典兜底，不会报KeyError。
    bucket = self._variants.get((agent_name, prompt_key), {})
    # 列表推导式：遍历bucket里所有的PromptVariant对象，只保留
    # is_active为True的那些，组成一个新列表返回。
    return [v for v in bucket.values() if v.is_active]
```

`get_active_variants`需要的是"这个位置下**所有**变体"，如果用扁平的三元组key，就没法直接"按前两个字段做前缀查询"——字典本身不支持这种"部分匹配key"的查询方式，你得遍历整个字典手动过滤。用两层嵌套后，`self._variants[(agent_name, prompt_key)]`直接就是"这个位置下所有变体"的字典，一步到位。**这是一个很实用的经验：设计字典的key结构时，应该优先考虑"你最常见的查询模式需要按哪些字段分组"，而不是简单地把所有能标识一条记录的字段拼成一个大key**。

## `dict.setdefault`：一个反复出现的小技巧

```python
# setdefault(key, {})——key存在就返回它已有的值；不存在就先存入
# 一个空字典{}，再返回这个刚创建的空字典。
bucket = self._variants.setdefault((agent_name, prompt_key), {})
```

`setdefault(key, 默认值)`的行为是："如果key已经存在，直接返回它当前对应的value；如果key不存在，先把`key: 默认值`这一对存进去，再返回这个默认值"。这一行代码等价于（但比下面这种写法更简洁）：

```python
# not in——先判断这个key是不是压根不存在于字典里。
if (agent_name, prompt_key) not in self._variants:
    self._variants[(agent_name, prompt_key)] = {}   # 不存在就手动初始化一个空字典
bucket = self._variants[(agent_name, prompt_key)]   # 再取出来使用
```

"第一次遇到某个key时自动初始化一个空容器，之后直接复用"，是这个框架里出现频率很高的模式（前面`ainative-a2a`的`InMemoryAgentRegistry.register`也用了同样的写法）——值得作为一个通用工具记在脑子里。

## 粘性决策失效时的降级：`sticky_variant_name in active_names`

真正把两层逻辑（哈希算法 + 存储）串起来的是`load_prompt`函数里的这一段判断：

```python
# 条件表达式：只有thread_id存在时才去查历史粘性决策，
# 匿名调用（thread_id为空）直接得到None，不用浪费一次查询。
sticky_variant_name = (
    await store.get_sticky_decision(agent_name, prompt_key, thread_id) if thread_id else None
)
# and连接两个条件：既要"确实查到了历史记录"，又要"这个记录指向的
# 变体现在仍然生效"，两者都满足才会信任并复用这份历史记录。
if sticky_variant_name is not None and sticky_variant_name in active_names:
    # next(生成器表达式)——在variants里找到第一个variant字段等于
    # sticky_variant_name的对象并返回，找不到会抛StopIteration。
    selected = next(v for v in variants if v.variant == sticky_variant_name)
else:
    # 没有可信的历史记录——重新走一遍确定性哈希分流。
    selected = ab_select_deterministic(variants, thread_id)
    if thread_id:
        # 非匿名调用才把这次的决策记录下来，供未来的请求复用。
        await store.record_decision(agent_name, prompt_key, thread_id, selected.variant)
```

这里有两个判断条件，都必须满足才会信任历史记录：`sticky_variant_name is not None`（确实查到了历史记录）**并且**`sticky_variant_name in active_names`（这个记录指向的变体现在仍然生效）。第二个条件容易被遗漏——如果只判断"有没有历史记录"，一旦运营下线了某个变体，所有之前被分到这个变体的用户，会一直尝试去读取一个已经不存在的`PromptVariant`，要么报错，要么（如果实现得不小心）返回一个陈旧的、本不该再被使用的内容。

`in active_names`这个检查，本质上是**每次读取缓存/历史记录时，都验证一下这份记录在"当前时刻"是否仍然有效**，而不是无条件信任"曾经写入过"这件事本身。这是一种很值得记住的防御性模式：**历史记录的有效性会随时间衰减，读取时需要重新验证，而不能假设它永远正确**。

## 本章小结

- 存储层的数据结构设计，应该服务于"最常见的查询模式"——这里是"给定一个位置，查它下面所有变体"，因此选择两层嵌套字典而不是扁平大key。
- `dict.setdefault(key, 默认值)`是"没有就初始化、有就直接用"这个模式的标准写法，在这个框架里反复出现。
- 复用历史决策（缓存）之前，必须验证它在"当前时刻"仍然有效，而不是无条件信任"曾经被记录过"——这个原则不只适用于Prompt路由，也适用于任何带缓存的系统。

## 动手做

```python
import asyncio
from ainative_prompt.store import InMemoryPromptStore, load_prompt
from ainative_core.protocols import PromptVariant

# async def main()——把整个演示流程包装成一个协程函数，因为里面用到
# 的store方法都是异步的，需要用await等待它们真正执行完。
async def main():
    store = InMemoryPromptStore()
    # 先保存一个"默认"变体，流量占比100%（也就是唯一的选项）。
    await store.save_variant("support_bot", "system_prompt", PromptVariant(
        variant="default", content="你是一个客服助手", traffic_pct=100, version=1))

    result = await load_prompt(store, "support_bot", "system_prompt", thread_id="thread-1")
    print(result)

# asyncio.run(...)——启动一个事件循环，真正执行这个协程函数，
# 是从"普通同步代码"进入"异步世界"的标准入口。
asyncio.run(main())
```

尝试再保存一个`variant="v2", traffic_pct=50`（并把`default`调成50），观察多个不同`thread_id`分别落在哪个变体上。

## 面试可能会问

**问：如果一份缓存/历史决策记录指向的数据后来被删除或下线了，你会怎么处理读取这份缓存的请求？**

答题思路：强调"缓存的有效性需要在读取时重新验证，不能假设写入时的状态会一直保持"，具体做法是"读取缓存后，检查它指向的实体在当前时刻是否仍然存在/生效，无效则走正常的重新计算路径"。可以直接引用这个框架里`sticky_variant_name in active_names`这个具体检查作为例子，展示你不只是知道"要验证"，还理解"验证的时机应该在每次读取时，而不是写入时一次性检查"。
