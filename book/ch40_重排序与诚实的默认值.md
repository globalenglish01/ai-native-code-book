# 第40章 —— 重排序与诚实的默认值

代码位置：`packages/ainative-rag/src/ainative_rag/reranking.py`

## 一个逻辑完全颠倒的真实bug

这一章要讲的是`ainative-rag`这个包里，文档记录最详细的一处真实bug——而且这个bug的性质相当微妙，一旦出现几乎不会被轻易察觉。

先说清楚"重排序"（reranking）在做什么：检索阶段（比如上一章的BM25、向量检索、混合检索）追求的是"速度快、能从海量文档里快速筛出一批候选"，但打分精细度有限。重排序则是拿到这一小批候选之后，用一个更精细（但更慢，跑不动全量文档）的模型对它们重新打分、重新排序，取长补短。

真实项目里发生过这样一件事：重排序模型没能给某个片段打分（比如那一批打分请求本身失败了），代码里给这种"没打上分"的情况设置的默认值是**1.0（满分）**。听起来好像没什么问题——"没打分就先给个中性值"？但仔细想想：这个默认值意味着"评估环节本身出了故障、完全不知道这段内容是否相关"的片段，反而会被当成"最相关的内容"排到最前面，通过任何"最低分数过滤"的筛选；而那些真正被认真评估过、被模型给出低分的片段，却会因为分数确实低而被过滤掉——**逻辑完全颠倒了**：出故障的内容被优待,认真评估过的低质量内容反而被正确过滤。这种bug极其隐蔽,因为它不会让系统报错或崩溃,只会让"重排序恰好失败的那批内容"莫名其妙地变得更容易出现在结果里。

## 缺失分数不能默认成满分

这个模块修复后的设计原则写在docstring里：

> 缺失分数不能默认成满分——本模块默认给缺失分数最低值（0.0），语义上准确对应"这份内容没有被验证过相关性，不应该被优先展示"，而不是碰巧混进"最相关"的结果里。

```python
DEFAULT_MISSING_SCORE = 0.0
```

这里的关键思考方式是：**"没有被打分"和"打了很高的分"绝不能用同一个默认值来表示**。反过来想，`DEFAULT_MISSING_SCORE`到底该设成什么，取决于你希望"没被评估过的内容"在下游流程里获得什么样的对待——如果希望它保守地排到后面（而不是意外抢占"最相关"的位置），默认值就应该是这个评分体系里的最低值，而不是随手选一个"看起来中性"的数字。

## `ScoredChunk`：`None`和`0.0`是两种不同的情况，但要小心处理

```python
@dataclass(frozen=True)
class ScoredChunk:
    chunk_id: str
    doc_id: str
    rerank_score: float | None
```

`rerank_score: float | None`这个类型注解里,`None`承载着明确的业务含义——"这个片段完全没有被重排序模型打分过",这和"打分打出来正好是0.0（模型认为它确实毫不相关）"是两种完全不同的情况。虽然下面聚合逻辑里,这两种情况最终都会被当作`DEFAULT_MISSING_SCORE`处理,但保留这个区分很有意义:它让需要的调用方(比如做数据质量监控的代码)能够单独统计"这批内容里到底有多少比例压根没有被重排序覆盖到",这个覆盖率本身就是一个值得追踪的运维指标。

## 又一处"必须在源头拒绝、不能让非法值流入计算"的校验

```python
def __post_init__(self) -> None:
    if self.rerank_score is not None and (math.isnan(self.rerank_score) or math.isinf(self.rerank_score)):
        raise InvalidRerankScoreError(
            f"rerank_score must be a finite number or None, got {self.rerank_score} "
            f"for chunk_id={self.chunk_id!r}"
        )
```

这里校验的是`rerank_score`不能是`NaN`（Not a Number，由0/0之类未定义运算产生的特殊浮点值）或者无穷大。为什么要单独校验这个？因为`aggregate_chunk_scores`（下面马上要看）里取"最高分"的比较逻辑是`score > current_best`——而**在IEEE浮点数标准里，NaN和任何数（包括它自己）比较，结果永远是`False`**。这意味着如果`current_best`不幸变成了`NaN`，之后不管来多少个真实的、正常的高分，`score > current_best`永远判定为`False`，这份文档的最高分会永久卡在`NaN`上，`sorted()`也不会报错，只会把这份文档静默排到一个不确定的位置。

这和上一章`overlap_ratio`、`rank`的校验是同一类思路的第三次出现——**把"某个非法输入会导致后续某个计算逻辑永久失效、且不会报错"这件事，提前到数据刚被构造出来的那一刻就直接拒绝**，而不是让它潜伏到几层调用之后才在某个意想不到的地方"发作"。

## `aggregate_chunk_scores`：跳过和"当作低分"是两种完全不同的选择

```python
def aggregate_chunk_scores(
    chunks: list[ScoredChunk], *, missing_score: float = DEFAULT_MISSING_SCORE,
) -> dict[str, float]:
    doc_best_scores: dict[str, float] = {}
    for chunk in chunks:
        score = chunk.rerank_score if chunk.rerank_score is not None else missing_score
        current_best = doc_best_scores.get(chunk.doc_id)
        if current_best is None or score > current_best:
            doc_best_scores[chunk.doc_id] = score
    return doc_best_scores
```

这个函数按`doc_id`把同一份文档下多个片段的重排序分数汇总起来，取最高分作为这份文档的代表分数（因为重排序通常是对更细粒度的"片段"打分，但最终展示/过滤经常是按"文档"这个粒度做的）。

docstring里特别强调了一处容易被忽视的设计选择：

> 未打分的片段（`rerank_score is None`）用`missing_score`兜底参与汇总，而不是被`if not scores: continue`这类写法直接跳过——跳过会让整份文档完全从汇总结果里消失，等价于"当作从未存在过"，比"当作低分处理"更容易造成数据静默丢失。

想象一下如果代码写成"遇到`None`就直接`continue`跳过这个片段"：如果一份文档**所有**片段都恰好没打上分（比如那一批打分请求整体失败），这份文档会彻底从`doc_best_scores`这个返回结果里消失——调用方拿到结果字典后，根本不会意识到"这份文档存在过，只是重排序没覆盖到它"，而是直接观察不到它的存在，这和"这份文档确实被评估过，就是分数很低"是完全不同的两种情况,但"跳过"这种写法会把它们混淆成同一种结果(都是"看不到这份文档")。现在的写法是**让它带着`missing_score`（最低分）继续参与聚合**——这份文档依然会出现在最终结果里,只是分数很低、大概率排到靠后的位置,这才是"诚实地反映现状"应有的行为。

## `apply_rerank_if_enabled`：三种不同的"不可用"情况，必须导向同一种行为

```python
def apply_rerank_if_enabled(
    doc_ids_in_original_order: list[str],
    *,
    enabled: bool,
    rerank_fn: Callable[[list[str]], dict[str, float]] | None,
) -> list[str]:
    if not enabled or rerank_fn is None:
        return list(doc_ids_in_original_order)
    try:
        scores = rerank_fn(doc_ids_in_original_order)
    except Exception:
        return list(doc_ids_in_original_order)
    return sorted(
        doc_ids_in_original_order,
        key=lambda doc_id: scores.get(doc_id, DEFAULT_MISSING_SCORE),
        reverse=True,
    )
```

这个函数要处理三种性质不同、但docstring要求"必须统一处理"的情况：

1. **重排序被明确关闭**（`enabled=False`）
2. **压根没有配置重排序函数**（`rerank_fn is None`）
3. **重排序函数被调用了，但过程中抛出了异常**（网络失败、模型服务不可用等）

docstring里点出了为什么这三种情况要统一：

> 禁用/未配置/调用失败三种情况必须处理一致——统一退回到原始检索顺序，而不是三种情况各自产生不同的、不可预期的行为。

如果这三种情况各自有一套不同的应对逻辑（比如"关闭时返回空列表"、"未配置时抛异常"、"调用失败时返回一半结果"），调用方要针对每一种情况单独写处理代码，而且这些差异化的行为往往是"历史上逐个补丁堆出来的"，很难让人一眼看出规律。这里选择"不管出于哪种原因用不上重排序，都退回到原始检索顺序"——这是一个**单一、可预测、调用方不需要区分具体原因就能安全处理的兜底行为**。

`except Exception`这里同样是故意写得很宽泛，理由和上一章`freshness.py`、第34章`_ObservableSpanRecorder`是同一套逻辑：重排序是一个"锦上添花"的优化环节，出问题时优雅降级回原始顺序，比让整个检索请求直接报错崩溃更符合它在整个系统里的定位——检索请求本身应该始终能返回一个结果（哪怕排序质量打了折扣），而不能因为重排序这个增强步骤出故障就让用户完全拿不到任何答案。

最后`scores.get(doc_id, DEFAULT_MISSING_SCORE)`这一行也值得注意：正常路径下，重排序函数可能只对部分文档成功打了分（比如批量请求里有一部分超时了），对于"压根不在`scores`字典里的`doc_id`"，同样用`DEFAULT_MISSING_SCORE`兜底，而不是让`.get()`因为找不到key而出问题——这和上面`aggregate_chunk_scores`的处理原则是完全一致的，让"部分未覆盖"这种情况在整个模块里得到统一、诚实的对待。

## 本章小结

- 一个真实发生过的逻辑颠倒bug：重排序打分失败时默认给满分（1.0），导致"评估本身出故障、完全不知道是否相关"的内容反而被优待、绕过了本该拦住它的最低分过滤；正确的默认值应该是这个评分体系里的最低值。
- `rerank_score: float | None`里`None`和`0.0`承载不同语义——前者是"完全没被评估过"，后者是"评估过，且分数确实是0"——虽然聚合时都按最低分处理，但保留这个区分能支持"统计重排序真实覆盖率"这类需求。
- `ScoredChunk`校验分数不能是NaN/无穷大，因为NaN和任何数比较都是`False`，会让"取最高分"的比较逻辑永久失效且不报错——必须在数据构造的那一刻就拒绝，而不是让它流入后续聚合计算。
- 聚合时用"兜底最低分继续参与汇总"而不是"直接跳过"，因为跳过会让整份文档从结果里完全消失，等价于"当作从未存在过"，比"当作低分处理"更容易造成数据静默丢失。
- 重排序"被禁用"、"未配置"、"调用失败"这三种性质不同的"不可用"情况，必须统一退回同一种兜底行为（原始检索顺序），而不是各自产生互不一致、难以预测的行为。

## 动手做

```python
from ainative_rag.reranking import (
    ScoredChunk, aggregate_chunk_scores, apply_rerank_if_enabled, InvalidRerankScoreError, DEFAULT_MISSING_SCORE,
)

chunks = [
    ScoredChunk(chunk_id="c1", doc_id="doc-a", rerank_score=0.92),
    ScoredChunk(chunk_id="c2", doc_id="doc-a", rerank_score=None),   # 这批打分请求失败了
    ScoredChunk(chunk_id="c3", doc_id="doc-b", rerank_score=0.15),   # 认真评估过，分数确实很低
]
scores = aggregate_chunk_scores(chunks)
print(scores)  # doc-a取0.92（最高分），doc-b是0.15——doc-b不会因为分数低就消失

try:
    ScoredChunk(chunk_id="bad", doc_id="doc-x", rerank_score=float("nan"))
except InvalidRerankScoreError as exc:
    print("非法分数被正确拒绝：", exc)

original_order = ["doc-a", "doc-b", "doc-c"]

def flaky_rerank(doc_ids):
    raise ConnectionError("重排序服务暂时不可用")

result = apply_rerank_if_enabled(original_order, enabled=True, rerank_fn=flaky_rerank)
print("重排序失败时退回原始顺序：", result == original_order)
```

## 面试可能会问

**问：如果重排序模型对某些内容打分失败了，你会怎么处理这批"没打上分"的数据？**

答题思路：先指出一个真实发生过的反面案例——把"打分失败"默认成满分，会导致"完全没被验证过相关性"的内容反而被优待、绕过本该过滤掉它的最低分检查，这是一处逻辑完全颠倒的bug。正确的思路是把缺失分数默认成这个评分体系里的最低值，语义上准确对应"未验证，不应该被优先展示"。同时要区分"跳过这条数据不参与汇总"和"让它带着最低分继续参与汇总"——前者会让整份文档从结果里完全消失,后者才是诚实地反映"这部分内容确实存在,只是没有被有效评估过"。可以再补充一点:重排序作为一个增强步骤,不管是被主动关闭、没配置、还是调用失败,都应该统一退回到同一种可预测的兜底行为(原始顺序),而不是让调用方去应付三种互不一致的边界情况。
