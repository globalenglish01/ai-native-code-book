# 第29章 —— 能力注册与发现

代码位置：`packages/ainative-a2a/src/ainative_a2a/registry.py`

## 一个组织架构的类比

想象一家公司里，"账单纠纷"这类问题需要转交给专门的账单专员处理，"技术故障"需要转交给技术支持团队。新来的员工怎么知道"这类问题该找谁"？公司通常会有一份内部通讯录，登记"谁负责什么"——这正是`ainative-a2a`的`InMemoryAgentRegistry`要解决的问题：**当一个系统里有多个分工不同的Agent时，某个Agent遇到自己不擅长的子任务，怎么知道该把它委派给谁**。

## 两层嵌套字典：能力注册表的核心结构

```python
class InMemoryAgentRegistry:
    def __init__(self) -> None:
        self._capabilities: dict[str, dict[str, AgentCapability]] = {}

    def register(self, agent_name: str, capability: AgentCapability) -> None:
        bucket = self._capabilities.setdefault(agent_name, {})
        bucket[capability.name] = copy.deepcopy(capability)

    def find_agents_for(self, capability_name: str) -> list[str]:
        return sorted(
            agent_name
            for agent_name, caps in self._capabilities.items()
            if capability_name in caps
        )
```

外层字典的key是agent名字，value又是一个字典（key是能力名字，value是具体的`AgentCapability`描述）——这和第13章讲的`InMemoryPromptStore`的存储结构是同一种思路："一个agent可能登记了好几项不同的能力，需要按能力名字分别存放"。

`find_agents_for`的实现值得细看：它是一个"生成器表达式包在`sorted()`里"的写法——遍历所有agent，检查"这个能力名是不是出现在它的能力字典的key里"（`capability_name in caps`对字典用`in`默认检查的就是key），符合条件的agent名字被收集起来，最后按字母顺序排序返回。为什么要排序？**因为集合/字典的遍历顺序在不同Python版本或不同运行时刻可能不完全稳定，如果不排序，同样的查询条件，两次调用可能返回顺序不同的结果**——对于测试和日志展示来说，这种"看起来随机"的顺序会造成困扰，排序保证了每次查询同样的条件都得到同样的顺序。

## 又一次"别名bug"，同一个家族的成员

如果你读过第5章，看到`register`方法里的`copy.deepcopy(capability)`，应该会立刻反应过来这是怎么回事——`AgentCapability`虽然是`frozen`的dataclass，但它的`input_schema`/`output_schema`字段是普通可变字典：

```python
@dataclass(frozen=True)
class AgentCapability:
    name: str
    description: str
    input_schema: dict[str, Any] = field(default_factory=dict)
    output_schema: dict[str, Any] = field(default_factory=dict)
```

`register`/`get_capability`/`capabilities_of`三个方法在存入和取出两端都做了深拷贝——如果调用方注册能力之后继续修改自己手上那份`input_schema`字典，或者拿到查询结果后修改它，都不应该影响到注册表内部真正存储的数据。这正是第5章讲的"别名bug大家族"的又一个真实案例——如果你还没读过第5章，建议先回去读一遍，这里不再重复讲深拷贝的原理。

## 为什么这是一个独立的包，而不是塞进`ainative-core`

值得留意的一点：`AgentRegistry`这个Protocol定义在`ainative-core`（第3章讲过的地基包），但`InMemoryAgentRegistry`这个具体实现放在了`ainative-a2a`这个独立的包里。这遵循的是整个框架的通用规则——`ainative-core`只定义"接口长什么样"，具体实现分散在各自的功能包里，`ainative-a2a`这个包专注于"Agent间协作"这一个主题，而不是把所有Protocol的默认实现都堆进地基包，让地基包变得臃肿。

## 本章小结

- 多Agent协作系统需要一个"能力注册表"，让某个Agent能够按"需要什么能力"而不是"硬编码目标Agent名字"来查找委派对象。
- `find_agents_for`对返回结果排序，是为了保证查询结果的顺序稳定、可预测，不受字典底层遍历顺序不稳定性的影响。
- `AgentCapability`虽然是frozen dataclass，它的schema字段依然是可变字典，注册表在存入/取出两端都做深拷贝防止别名污染——这是第5章讲过的同一类bug在另一个包里的真实案例。

## 动手做

```python
from ainative_a2a.registry import InMemoryAgentRegistry
from ainative_core.protocols import AgentCapability

registry = InMemoryAgentRegistry()
registry.register("billing_specialist", AgentCapability(
    name="resolve_billing_dispute", description="处理账单纠纷",
))
registry.register("tech_support", AgentCapability(
    name="fix_login_issue", description="处理登录问题",
))

print(registry.find_agents_for("resolve_billing_dispute"))
print(registry.all_agents())
print(registry.capabilities_of("billing_specialist"))
```

## 面试可能会问

**问：在一个多Agent系统里，你会怎么设计"任务应该委派给谁"这个决策机制？**

答题思路：介绍"能力注册与发现"这个模式——每个Agent声明自己具备哪些能力，需要委派任务时按能力名称查找，而不是在代码里硬编码"这类任务永远发给某个具体Agent"（那样扩展新Agent时需要改动大量已有代码）。可以补充"如果查到多个Agent都具备同一能力，应该由谁来决定选哪一个"这个更深入的问题，为下一章讲的委派逻辑埋一个伏笔。
