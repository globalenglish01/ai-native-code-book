# 第30章 —— 委派链路的死循环防护

代码位置：`packages/ainative-a2a/src/ainative_a2a/dispatcher.py`

## 一个会真实发生的死循环

假设Agent A遇到一个自己无法处理的问题，把它委派给Agent B；Agent B处理到一半，发现自己也需要一部分A的专长，又把任务委派回A——如果没有任何防护，A和B会开始互相踢皮球，永远做不完，还会一直消耗计算资源（每一次委派可能都涉及一次真实的模型调用，这意味着真金白银的成本）。这一章讲`Dispatcher`类怎么用两道防线堵住这类风险。

## 防线一：委派深度上限

```python
DEFAULT_MAX_DELEGATION_DEPTH = 5

async def delegate(self, *, capability, payload, sender_agent, target_agent=None, delegation_chain=()):
    chain = (*delegation_chain, sender_agent)
    if len(chain) > self._max_delegation_depth:
        raise DelegationLimitExceededError(
            f"delegation chain depth {len(chain)} exceeds max_delegation_depth={self._max_delegation_depth}: {chain}"
        )
```

`(*delegation_chain, sender_agent)`——用星号把已有的`delegation_chain`元组"展开"，再把这次发起委派的`sender_agent`追加到末尾，组成一个新的、更长一步的元组。这是"不修改原始数据、而是生成一份新数据"的写法——元组本身是不可变的，压根没法"修改"，只能重新组合出一个新的。

如果委派链条已经超过了允许的最大深度（默认5层），直接拒绝——**即使这一次委派还没有真的形成一个循环，链条特别长也可能是设计上出了问题**（正常合理的委派场景不太可能需要链条特别长，比如一个真实的客服问题一般不需要连续转手5次以上还没解决），这是一道"额外的安全网"，即使循环检测（下面第二道防线）因为某种原因没能生效，深度上限也能兜底防止无限膨胀。

## 防线二：循环检测——不等深度耗尽就直接拦下

```python
resolved_target = target_agent or self._resolve_target(capability)
if resolved_target in chain:
    raise DelegationLimitExceededError(
        f"cyclic delegation detected: '{resolved_target}' already appears in chain {chain}"
    )
```

这一步检查"这次要委派的目标agent，是不是已经出现在当前委派链条里了"——如果是，说明马上就要形成一个循环（比如A委派给B，B又想委派回A，而"A"已经在链条里了）。**这里的设计哲学值得注意：不依赖"链条早晚会因为深度限制被截断"这种间接、迟来的保护，而是在第一时间就把循环直接挡住**。想象一个真实的循环场景——A委派给B，B委派回A，A又委派给B……如果只靠深度上限，这个循环要经过5轮往返（10次委派）才会被拦截，期间产生了大量不必要的调用开销；而循环检测能在**第二次**尝试委派回已经出现过的agent时，就立刻发现问题。这是"越早发现问题，浪费的资源越少"这个原则的具体体现。

## `_resolve_target`：自动发现能力的边界情况处理

```python
def _resolve_target(self, capability: str) -> str:
    candidates = self._registry.find_agents_for(capability)
    if not candidates:
        raise LookupError(f"no agent registered for capability '{capability}'")
    if len(candidates) > 1:
        raise LookupError(
            f"multiple agents registered for capability '{capability}': {candidates}; "
            f"pass target_agent explicitly to disambiguate"
        )
    return candidates[0]
```

这个函数处理了"按能力名称自动查找目标Agent"这件事的两种边界情况：一个候选都没找到——直接报错，而不是返回一个`None`让后续代码在别处出现更难排查的错误；找到了不止一个候选——这里的选择很值得学习，**这个函数没有"自动挑一个"（比如按名字排序取第一个），而是直接报错，要求调用方显式指定到底想委派给哪一个**。为什么不干脆自动选一个？因为"哪个候选更合适"这个判断，往往依赖业务上下文（比如两个客服Agent都能处理账单问题，但一个更擅长退款、另一个更擅长发票——`Dispatcher`本身不知道这类业务细节），**让系统在"信息不足以做出正确判断"时明确报错，比自己瞎猜一个然后悄悄做出错误决策，更安全**。

## 每一次委派都有一个独一无二的编号

```python
task = A2ATask(
    task_id=str(uuid.uuid4()),
    capability=capability,
    payload=payload,
    sender_agent=sender_agent,
    delegation_chain=chain,
)
```

`uuid.uuid4()`生成一个几乎不可能重复的随机编号，`str(...)`转换成字符串形式，作为这次任务的唯一标识。为什么需要这个？想象一个真实场景——一个委派链条里出了问题需要排查，如果没有唯一编号，你很难在日志/审计记录里准确地把"这一次具体的委派"和"另一次恰好委派了同样能力、同样参数"的不同调用区分开。**给"一次具体的操作"分配一个独一无二的标识，是贯穿这整个框架的一个通用模式**——第10章讲的幂等键、这一章讲的`task_id`，本质上都是同一类需求：需要能唯一地追溯"这一次具体发生的事情"。

## 本章小结

- 多智能体委派系统需要两道防线：委派深度上限（兜底）+ 循环检测（越早发现越好，不依赖深度上限"迟早会截断"这种间接保护）。
- 元组展开语法`(*chain, item)`是"基于已有不可变数据，生成一份追加了新元素的新数据"的标准写法。
- 当"自动选择"缺乏足够的业务上下文信息去做出正确判断时，明确报错、要求调用方显式指定，比自己瞎猜一个更安全——这是"诚实地报告不知道"（第6章）原则在另一个场景里的体现。
- 每一次具体的委派都应该有一个唯一标识（`uuid.uuid4()`），方便日后排查问题时准确追溯。

## 动手做

```python
import asyncio
from ainative_a2a.registry import InMemoryAgentRegistry
from ainative_a2a.transport import InProcessTransport
from ainative_a2a.dispatcher import Dispatcher, DelegationLimitExceededError
from ainative_core.protocols import AgentCapability

async def main():
    registry = InMemoryAgentRegistry()
    registry.register("agent_a", AgentCapability(name="task_x", description="..."))
    transport = InProcessTransport()

    async def handler(task):
        return {"done": True}
    transport.register_handler("agent_a", handler)

    dispatcher = Dispatcher(registry, transport, max_delegation_depth=3)

    # 正常委派
    result = await dispatcher.delegate(capability="task_x", payload={}, sender_agent="coordinator")
    print(result.status)

    # 模拟循环委派
    try:
        await dispatcher.delegate(
            capability="task_x", payload={}, sender_agent="agent_a",
            delegation_chain=("agent_a", "agent_b"),
        )
    except DelegationLimitExceededError as exc:
        print("被拦截：", exc)

asyncio.run(main())
```

## 面试可能会问

**问：如何防止多个Agent之间互相委派任务时形成死循环？**

答题思路：讲清楚两道独立的防线——委派深度上限（简单粗暴但能兜底）和循环检测（检查目标是否已经出现在当前链条里，能在循环刚要形成时就立刻拦截，而不必等到深度耗尽）。强调"循环检测应该在第一次就命中，而不是依赖深度限制这种间接、迟来的保护"，这体现了"越早发现问题越省资源"的工程直觉。如果能进一步提到"当自动路由无法唯一确定目标时应该报错而不是瞎猜"，会让回答更完整。
