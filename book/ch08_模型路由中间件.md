# 第8章 —— 模型路由中间件

代码位置：`packages/ainative-guardrail/src/ainative_guardrail/model_router.py`

## 一个简单的成本优化思路

大模型不是只有一档——同一个供应商往往同时提供"旗舰款"（贵、聪明）和"轻量款"（便宜、够用）两种档位的模型。如果一次对话里，80%的轮次其实都是"帮我列一下文件"、"确认一下状态"这类简单指令，却每次都用旗舰模型去处理，等于是把大部分预算花在了不需要的地方。

`ModelRouterMiddleware`要做的事情很朴素：**给每一轮对话打一个"复杂度分数"，分数低于阈值就换成便宜模型，分数高就维持原本的主力模型**。这一章重点讲两件事：这个打分机制怎么设计得"讲道理"，以及"按次替换模型"这个操作在技术上是怎么实现的。

## 打分：一堆信号累加起来

来看`_score`方法里判断的几类信号（[model_router.py:176-276](../packages/ainative-guardrail/src/ainative_guardrail/model_router.py#L176-L276)）：

```python
n = len(msgs)
if n <= 3:
    score -= 2          # 对话刚开始，大概率简单
elif n >= 10:
    score += 2          # 对话已经很长，可能是个棘手任务

if isinstance(last, ToolMessage):
    if getattr(last, "status", None) == "error":
        score += 3       # 上一次工具调用失败了，需要更强模型排查
    if tname in _ANALYTICAL_TOOLS:
        score += 3       # 用了"分析类"工具（比如查看浏览器控制台日志）
    elif tname in _PRIMITIVE_TOOLS:
        score -= 1       # 用了"基础操作类"工具（比如点击、读文件）

if any(k in txt for k in _COMPLEX_KEYWORDS):   # "debug"/"fix"/"why"等关键词
    score += 4
elif len(txt) < 200 and any(k in txt for k in _SIMPLE_KEYWORDS):  # "list"/"ok"等
    score -= 2
```

这里没有用一个单一的、"聪明"的判断（比如再调用一次大模型去判断"这轮对话难不难"——那样反而增加了成本和延迟），而是用几个**便宜、可解释、可累加**的规则信号组合出一个总分。这是一种很实用的工程取舍：判断"要不要用贵模型"这件事本身，不应该消耗和贵模型同一个量级的成本。

## `signals`字典：可解释性不是事后补的

注意`_score`方法不只返回一个分数，还返回一个`signals`字典，记录"具体是哪些信号各自贡献了多少分"：

```python
signals["complex_keywords"] = 4
signals["history_long"] = 2
```

这个字典唯一的用途是写进日志：

```python
logger.info("[ModelRouter:%s] score=%d → cheap model. signals=%s", self._parent_name, score, signals)
```

为什么要专门留这么一份"调试信息"？因为路由决策一旦出了问题（比如某次对话明明很复杂，却被错误地路由到了便宜模型，导致回复质量下降），运维/开发者需要知道**具体是哪几条规则的加权结果导致了这个判断**，而不是面对一个孤零零的数字摸不着头脑。**任何"自动做决策"的系统，都应该在设计阶段就考虑好"决策依据怎么被追溯"这件事**，而不是等出了问题才临时加日志。

## 按次替换模型：`request.override(model=...)`

这一章另一个值得学的技术细节，是"路由"具体是怎么落地的：

```python
def wrap_model_call(self, request: ModelRequest, handler) -> ModelResponse:
    override, score, signals = self._route(request)
    if override is not None:
        return handler(request.override(model=override))
    return handler(request)
```

`request.override(model=override)`——基于原始的`request`对象，生成一份"只是把`model`字段换成了便宜模型、其余字段完全不变"的**新**request，再交给`handler`继续走下去。这不是"修改原始request"（原始对象保持不变），而是"基于原对象生成一个局部修改过的新对象"——这是一种常见的、安全的处理方式：调用方（LangChain框架内部的其他逻辑）如果还持有原始`request`的引用，不会被这里的替换意外影响。

这个技巧在第4章讲跨厂商降级链时也出现过（`ModelFallbackMiddleware`同样是用这个机制换模型）——**"用同一套机制做主动优化（省钱）和被动容错（供应商故障降级），而不是各写一套"**，是这个框架里一个反复出现的设计取向。

## 本章小结

- 模型路由用一组便宜、可累加、可解释的规则信号打分，而不是用一次额外的大模型调用来判断"这轮复杂不复杂"。
- 记录"每个信号各自贡献了多少分"，是为了让路由决策在出问题时可以被追溯，而不是一个无法解释的黑盒数字。
- "按次替换模型"通过`request.override(model=...)`实现——基于原对象生成一份局部修改的新对象，不改动原始对象本身；这套机制同时被用于主动的成本路由和被动的故障降级。

## 动手做

```python
from ainative_guardrail.model_router import ModelRouterMiddleware
from ainative_core.config import ProviderConfig
from langchain_core.messages import HumanMessage

router = ModelRouterMiddleware("demo_agent", config=ProviderConfig(anthropic_api_key="fake"))

class FakeRequest:
    messages = [HumanMessage(content="list all files in this directory")]

score, signals = router._score(FakeRequest())
print(score, signals)   # 应该是负分，命中simple_keywords
```

## 面试可能会问

**问：如果要给一个多模型系统做成本优化，你会怎么决定"这次请求该用哪个档位的模型"？**

答题思路：强调"决策本身的成本要远低于被决策对象的成本差异"，避免用"额外调用一次大模型来判断复杂度"这种本末倒置的方案；描述一个可累加、可解释的规则打分机制，并说明为什么要保留"每个信号贡献了多少分"这份可追溯性——这是很多候选人只会说"用规则判断"、却说不清楚"规则出错了怎么排查"的地方，能讲清楚这一点会显得更成熟。
