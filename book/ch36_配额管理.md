## 数据隔离做对了，不代表资源隔离也做对了

上一章讲的是"A公司看不到B公司的数据"——这是"数据隔离"。这一章要讲一个经常被忽视、但同样重要的维度：**"资源/容量隔离"**。模块docstring里提出了一个很值得记住的观点：

> 一个系统即使已经具备"按用户限流"和"按组织设置成本预算"两层意图，如果底层真正共享的计算资源（任务队列、数据库连接池）完全不区分租户，一个任务量大的租户仍然可以不成比例地挤占共享资源、拖慢其他租户——"数据隔离"和"资源/容量隔离"是两个必须分别评估的不同维度，不能因为做好了前者就默认后者也已经解决。

想象一个具体场景：你的SaaS产品对每个租户都做了严格的数据隔离（A公司永远查不到B公司的数据），业务上看起来"多租户安全"已经做好了。但如果所有租户的后台任务都挤在同一条共享队列里，同一个数据库连接池里——某个租户突然发起了大量任务（可能是一次批量导入，也可能是恶意攻击），会挤占掉队列和连接池的容量，**导致其他完全无辜的租户的正常请求被拖慢甚至超时**。这和"数据泄露"是完全不同性质的问题，但同样是"多租户隔离"没有做到位的表现。

## 先检查、再占用，而不是相反

```python
class TenantResourceTracker:
    def acquire_job_slot(self, tenant_id: str) -> None:
        quota = self._quota_for(tenant_id)
        current = self._active_jobs.get(tenant_id, 0)
        if current >= quota.max_concurrent_jobs:
            raise QuotaExceededError(
                f"tenant '{tenant_id}' has reached its concurrent job quota "
                f"({current}/{quota.max_concurrent_jobs})"
            )
        self._active_jobs[tenant_id] = current + 1
```

`acquire_job_slot`的文档明确写着"超出该租户配额时抛`QuotaExceededError`，不静默排队等待"。这背后的设计选择值得留意：**在真正开始占用资源之前做检查，而不是先占用、事后才发现超配额**。如果反过来做——先无条件接受任务、塞进队列，事后再发现某个租户超额了——这个任务已经真实占用了共享资源、可能已经开始执行，"发现超额"这件事本身没有任何意义了，无法真正阻止资源被挤占。**限流类检查必须发生在"资源真正被占用之前"，这样"拒绝"才是一个真正有效的动作，而不是马后炮**。

## `register_quota`的返回值：诚实地报告一个尴尬的真相

```python
def register_quota(self, tenant_id, *, max_concurrent_jobs=..., max_pool_connections=...) -> bool:
    self._quotas[tenant_id] = TenantQuota(...)
    return (
        self._active_jobs.get(tenant_id, 0) > max_concurrent_jobs
        or self._active_connections.get(tenant_id, 0) > max_pool_connections
    )
```

这个方法的返回值设计得很讲究——文档里解释了原因：**如果一个租户已经占用了3个任务名额，管理员在事故处置期间把它的配额临时调低到1，这次调整本身不会强制打断已经在跑的3个任务**（强行打断正在执行的工作是不合理的），**但调用方必须能明确知道"这次调低配额没有立刻生效"**，而不是得到一个"配额已经生效"的假象。所以`register_quota`会返回一个布尔值，告诉调用方"这个租户目前已占用的资源，是不是已经超过了刚设置的新配额"——这正是第6章讲过的"诚实地报告不知道"这个原则的又一个变体：**当一个操作没有完全达到"表面上看起来应该达到"的效果时，明确地告知调用方这一点，而不是让它误以为一切都已按预期生效**。

`usage_report()`方法进一步把这个"是否超配额"的状态，做成了一份持续可查的快照：

```python
report[tenant_id] = {
    "active_jobs": active_jobs,
    "active_connections": active_connections,
    "is_over_quota": (
        active_jobs > quota.max_concurrent_jobs or active_connections > quota.max_pool_connections
    ),
}
```

这样即使运维人员没有恰好在`register_quota()`调用的那一刻查看结果，事后通过巡检脚本/仪表盘查看这份快照，也依然能发现"这个租户目前处于超配额状态"，而不是这个信息只在调用的那一瞬间才可见、之后就彻底消失了。

## `max(0, ...)`：一个熟悉的防御性写法

```python
def release_job_slot(self, tenant_id: str) -> None:
    self._active_jobs[tenant_id] = max(0, self._active_jobs.get(tenant_id, 0) - 1)
```

如果你读过第9章讲`ConsecutiveCallGuardMiddleware`时提到的`max(0, count)`，这里应该很眼熟——即使调用方多调用了一次`release`、没有对应的`acquire`（比如代码里的`try/finally`写得有疏漏），占用计数减1之后也不会变成一个没有物理意义的负数。**这种"用`max(0, ...)`兜底防止计数器变成负数"的模式，在这个框架里反复出现，值得当作一个通用的防御性编程小技巧记下来**。

## 本章小结

- "数据隔离"（谁能看到谁的数据）和"资源/容量隔离"（谁能占用多少共享资源）是两个必须分别评估的维度，做好了前者不代表后者也自动解决。
- 配额检查必须发生在"资源真正被占用之前"，事后才发现超配额没有实际意义，无法阻止资源已经被挤占的既成事实。
- 当一次操作没能完全达到表面上的预期效果时（比如调低配额没有让已占用资源立刻合规），应该诚实地告知调用方，并且让这个状态可以被持续、事后地查询到，而不只是在操作发生的那一刻可见。
- `max(0, count - 1)`是防止计数器因为调用方疏漏（多释放一次）而变成负数的通用防御写法。

## 动手做

```python
from ainative_tenancy.quota import TenantResourceTracker, QuotaExceededError

tracker = TenantResourceTracker()
tracker.register_quota("tenant-a", max_concurrent_jobs=2)

tracker.acquire_job_slot("tenant-a")
tracker.acquire_job_slot("tenant-a")
try:
    tracker.acquire_job_slot("tenant-a")   # 第3次应该被拒绝
except QuotaExceededError as exc:
    print("配额已满：", exc)

# 现在把配额调低到1，观察register_quota的返回值
is_already_over = tracker.register_quota("tenant-a", max_concurrent_jobs=1)
print("调低配额后是否已超额：", is_already_over)   # 应该是True（当前占用2 > 新配额1）
print(tracker.usage_report())
```

## 面试可能会问

**问：一个多租户系统已经做好了数据层面的隔离（每个租户只能查到自己的数据），你觉得还需要考虑什么？**

答题思路：指出"数据隔离"和"资源/容量隔离"是两个不同的维度——即使数据完全隔离，共享的计算资源（任务队列、数据库连接池、API调用配额）如果不按租户限制，一个高负载租户依然可以拖累其他租户的正常使用。可以举"配额检查必须在资源占用前而不是占用后进行"这个具体设计作为支撑，展示你不只停留在"多租户=数据隔离"这种表面理解上。
