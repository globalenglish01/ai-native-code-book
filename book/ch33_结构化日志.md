# 第33章 —— 结构化日志

代码位置：`packages/ainative-observability/src/ainative_observability/structured_logging.py`

## 凌晨三点，你要在十万行日志里找一个密码泄露事件

设想一个场景：安全团队半夜发来一条消息——"生产日志里疑似出现了一条用户密码的明文"，让你在两小时内确认范围、锁定是哪次请求、然后证明这个漏洞已经被堵上。你打开日志文件，看到的是这样一行行文本：

```
2026-07-24 03:12:07 INFO [auth-service] User login attempt: user_id=u1029, password=hunter2, ip=10.0.0.4
```

如果全公司的服务都是这种"一行文本，字段全靠肉眼数逗号分割"的日志风格，你能做的事情非常有限：`grep`关键词、祈祷格式没有意外换行、祈祷没有别的地方也不小心把"password="这几个字拼进了消息里但字段名换了个写法。你没法"按字段查询"——没法直接问日志系统"给我所有`level=ERROR`且`user_id=u1029`的记录"，因为对日志系统来说，这整行只是一坨没有结构的字符串。

这一章要看的`structured_logging.py`要解决两件事：**第一，把日志变成可以按字段查询的JSON**，而不是靠字符串拼接;**第二，把"敏感信息脱敏"做成一个无差别生效、挂在处理链路最底层的过滤器**，而不是指望每个写日志的人自己记得脱敏。这两件事合在一起，才能让上面那种"凌晨三点排查密码泄露"的场景，变成"查一条JSON字段过滤条件"这么简单，而且从设计上尽量杜绝这类泄露从一开始就不会发生。

模块开头的docstring直接点出了真实事故的教训：

> 用f-string等字符串拼接方式直接写日志消息，会把本该是独立字段的数据（如请求头/请求体）压缩进消息文本，绕过结构化字段与字段级脱敏。"调试模式开关"（如某个环境变量）一旦打开，容易让原本受保护的敏感数据未经脱敏流向日志文件——脱敏过滤器必须挂在Handler层面、对所有日志级别和所有debug开关状态都无差别生效，而不是只在"正常路径"生效。

这两句话分别对应下面要讲的`JsonFormatter`和`SensitiveDataFilter`。

## `JsonFormatter`：把一条日志变成一行JSON

Python标准库的`logging`模块把"记录一条日志"这件事拆成了几个角色：你调用`logger.info(...)`产生一个`LogRecord`对象，这个对象要经过`Filter`（决定要不要输出/要不要篡改内容）和`Formatter`（决定最终输出成什么样的文本）处理，才会真正落地成一行你看到的日志。`JsonFormatter`继承`logging.Formatter`，重写它的`format`方法：

```python
class JsonFormatter(logging.Formatter):
    """把日志record格式化成单行JSON——可以按字段查询/过滤的结构化数据。

    默认字段：`timestamp`（ISO-ish epoch秒，不受系统时间被人为调整影响，
    用`time.time()`而非`datetime.now()`格式化字符串）、`level`、`logger`、
    `message`，外加所有非标准`LogRecord`属性的`extra=`字段。
    """

    _STANDARD_ATTRS = frozenset(vars(logging.LogRecord("", 0, "", 0, "", (), None)).keys())

    def format(self, record: logging.LogRecord) -> str:
        payload: dict[str, Any] = {
            "timestamp": time.time(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        for key, value in vars(record).items():
            if key not in self._STANDARD_ATTRS and key not in payload:
                payload[key] = value
        if record.exc_info:
            payload["exc_info"] = self.formatException(record.exc_info)
        try:
            return json.dumps(payload, default=str, ensure_ascii=False)
        except Exception as exc:
            ...
```

几个值得停下来看的细节：

**`timestamp`用`time.time()`，而不是格式化过的日期字符串。** docstring里解释了原因——数字时间戳（从1970年到现在的秒数）不依赖"当前系统时区/日期格式设置"。如果你用`datetime.now().strftime(...)`这类写法，服务器时区配置不一致、或者有人手动调整过系统时钟，都可能让不同机器打出来的日志时间戳互相对不上，排查跨服务问题时这种"时间轴对不齐"是很致命的。纯数字时间戳把这个隐患从根上消掉了——需要展示给人看的时候，任何一个时区都能从这同一个数字精确还原。

**`_STANDARD_ATTRS`这个类属性怎么来的**：`logging.LogRecord("", 0, "", 0, "", (), None)`手动构造一个"空白"的`LogRecord`，`vars(...)`把它的所有属性转成字典，取出所有属性名。这份集合的作用是区分"`LogRecord`自带的标准字段"（比如`levelname`、`pathname`、`lineno`这些日志模块内部使用的属性）和"调用方通过`extra={...}`额外塞进来的自定义字段"——只有后者才需要被单独加进JSON输出。这行代码写在类体里、不在任何方法内部，所以只在类被定义时执行一次，不会每格式化一条日志就重新构造一遍——这是一个值得留意的小优化：**凡是"每次调用结果都一样"的初始化工作，能提到类级别就不要放进每次都会被调用的方法体里**。

**为什么`for key, value in vars(record).items()`要额外判断`key not in payload`？** 万一某个自定义字段名恰好和`timestamp`/`level`/`logger`/`message`这几个手动填好的key重名，这个判断能防止它意外覆盖标准字段——虽然这种撞车概率不高，但防御性检查的成本几乎为零，值得写。

## 一个真实的设计决策：为什么`json.dumps`外面还要包一层`try/except`

这是这一章最值得记住的部分。看`format`方法的`except`分支：

```python
        try:
            return json.dumps(payload, default=str, ensure_ascii=False)
        except Exception as exc:
            # `default=str` only helps when json.dumps itself doesn't know a
            # type — it does NOT protect against a value's own __str__/__repr__
            # raising, which would otherwise make json.dumps raise and the
            # entire log line get silently dropped by logging's default
            # error handling (or, worse, escape into the caller's real
            # business logic if a non-standard Handler doesn't catch it).
            # A structured logging module's core promise is "never silently
            # lose a log line" — fall back to a minimal payload that is
            # guaranteed to serialize, rather than propagating the failure.
            return json.dumps({
                "timestamp": time.time(), "level": record.levelname, "logger": record.name,
                "message": record.getMessage(), "logging_error": f"failed to serialize log record: {exc}",
            }, ensure_ascii=False)
```

先说`default=str`本身在做什么：`json.dumps`默认只认识Python的基础类型（字符串、数字、布尔值、列表、字典……），如果`extra={}`里塞进去一个自定义类的实例，`json`模块不知道该怎么把它变成JSON，正常情况下会直接报错。`default=str`告诉它："遇到不认识的类型，别报错，调用`str(...)`把它转成字符串再放进去。"这样即使调用方往日志里塞了个奇怪的对象，也大概率能兜底生成合法JSON。

但这里有一个`default=str`自己解决不了的漏洞：**如果这个对象的`__str__`方法本身在执行时就抛出了异常呢？** 也就是说，不是"json不认识这个类型"，而是"连把它转成字符串这一步都失败了"。`default=str`对这种情况完全无能为力——它的兜底逻辑是"调用`str(value)`"，如果`str(value)`这一步本身就抛异常，`json.dumps`照样会向外抛出异常，不会被`default=str`拦下。

对应的测试用例`test_format_never_silently_drops_a_log_line_when_a_field_cannot_be_stringified`专门构造了这样一个"调皮"的类来验证这个场景：

```python
class _Unstringable:
    def __str__(self) -> str:
        raise RuntimeError("cannot stringify me")

record = logging.LogRecord("test.unstringable", logging.INFO, "", 0, "hello", (), None)
record.bad_field = _Unstringable()

result = JsonFormatter().format(record)  # must not raise

payload = json.loads(result)
assert payload["message"] == "hello"
assert "logging_error" in payload
```

如果`format`方法不接住这个异常，会发生什么？`logging`模块默认的错误处理机制，在格式化失败时通常会让**这一整条日志记录悄无声息地消失**——你完全不知道曾经有这么一条日志尝试被写下来过。更糟的情况是：如果这条日志经过的不是标准的`Handler`（比如某些自定义handler没有做异常防护），这个异常甚至可能直接从日志系统里"逃逸"出去，打断调用方原本正常运行的业务代码——这就本末倒置了：**记日志这个本该完全"旁路"的动作，反而让主业务逻辑崩溃了**。

所以`format`方法的设计选择是：**结构化日志系统唯一不能妥协的承诺，是"绝不无声无息丢失一整条日志记录"，这个承诺的优先级高于"尽量记录完整信息"**。当"完整但可能失败"和"不完整但绝对安全"两者只能选一个的时候，退而求其次，构造一份只包含最基础字段（时间戳、级别、logger名字、消息本身）外加一条`logging_error`说明具体是哪里序列化失败的最小payload——这份最小payload保证只用得到"永远安全"的数据（都是字符串/数字，不涉及任何"来路不明"的调用方对象），必定能被`json.dumps`成功序列化。这是一种"两层兜底"的设计：第一层`default=str`兜住"类型不认识"，第二层`try/except`兜住"第一层兜底本身也失败了"的情况，两层叠加才能真正做到"绝不丢失"。

这个设计思路值得推广到任何"基础设施代码"（日志、监控、埋点）：**基础设施代码的失败模式，永远不应该比它想要防护的业务代码本身更严重**。哪怕基础设施自己出了故障，也应该优雅降级，而不是把故障传染给它原本要保护的东西。

## `SensitiveDataFilter`：脱敏必须无差别，不能靠自觉

日志变成结构化JSON只是第一步，第二步是脱敏。这里的核心设计思路，模块docstring里说得很直接：

> 敏感信息脱敏必须是一个独立、统一挂载在日志处理链路（`Handler.addFilter`）上的过滤器，对所有日志无差别生效，而不是指望每个调用点自己记得脱敏。

为什么强调"无差别"？因为脱敏这件事如果依赖"每个写`logger.info(...)`的人自己记得脱敏"，就一定会有人漏掉——尤其是在"调试模式"打开的时候：一个环境变量一开，为了方便排查问题打印出完整的请求体/响应体，这时候如果脱敏逻辑只覆盖"正常路径"，敏感数据就会原样流进日志文件。所以脱敏必须挂在Python `logging`模块的`Filter`这一层，处于所有具体业务代码触碰不到的位置，对DEBUG/INFO/WARNING/ERROR所有级别都无差别生效。

来看`SensitiveDataFilter`处理"字段名黑名单"的部分：

```python
DEFAULT_SENSITIVE_KEYS: frozenset[str] = frozenset({
    "password", "passwd", "pwd", "token", "api_key", "apikey", "secret",
    "authorization", "auth", "access_token", "refresh_token", "session_id",
    "cookie", "private_key", "credit_card", "ssn",
})

class SensitiveDataFilter(logging.Filter):
    def __init__(
        self, *, sensitive_keys: frozenset[str] = DEFAULT_SENSITIVE_KEYS,
        value_patterns: tuple[re.Pattern[str], ...] = _DEFAULT_VALUE_PATTERNS,
    ) -> None:
        super().__init__()
        self._sensitive_keys = {k.lower() for k in sensitive_keys}
        self._value_patterns = value_patterns

    def filter(self, record: logging.LogRecord) -> bool:
        try:
            record.msg = self._redact_text(str(record.msg))
            record.args = ()  # msg已经是最终字符串，避免%%格式化再次拼回原始参数
            for key in list(vars(record).keys()):
                if key.lower() in self._sensitive_keys:
                    setattr(record, key, "[REDACTED]")
        except Exception:
            pass
        return True
```

几个设计细节值得拆开讲：

**返回值永远是`True`。** `Filter.filter()`的返回值本来是用来决定"这条日志到底要不要被输出"的，但这个类的职责只是"篡改"日志内容（把敏感值替换掉），而不是决定日志的去留——所以不管处理成功与否，都返回`True`，绝不会让这个过滤器意外把整条日志拦下来不输出。

**`except Exception: pass`是故意的，而且理由很明确**：这个方法唯一不能容忍的后果，是"脱敏逻辑本身出bug，导致日志因此丢失或者让调用方程序崩溃"。万一处理过程中遇到某个奇怪的属性类型出了问题，宁可这条日志脱敏不完整，也要保证`filter`能正常返回、日志继续走完输出流程——这和上面`JsonFormatter`那个"绝不丢失"的设计原则是同一个思路的两次不同体现。

**`record.args = ()`这一行容易被忽略，但很关键。** Python日志模块支持`logger.info("hello %s", name)`这种带占位符的写法，`args`就是用来填充`%s`的原始参数。上一行已经把`record.msg`重写成"脱敏后的最终字符串"了，如果不清空`args`，日志模块之后格式化输出时还会尝试对`record.msg`再做一次`%`格式化，这样反而会把原始（未脱敏）的参数重新拼接回消息里——刚做的脱敏工作就白费了。这是一个具体又容易被忽视的坑：**修改了`msg`之后，必须同时处理掉还会二次作用于`msg`的`args`，否则等于没改。**

**`{k.lower() for k in sensitive_keys}`**——这是一个集合推导式，把字段名统一转成小写存起来，判断时也把待比较的字段名转成小写，这样"Password"、"PASSWORD"、"password"都能命中同一条规则，不用在黑名单里把每种大小写变体都列一遍。

## 正则表达式兜底：调用方图省事用f-string时怎么办

字段名黑名单只能覆盖`extra={...}`这种"结构化字段"的场景。但docstring里提到的真实事故是"用f-string把敏感数据拼进了消息文本本身"——这种情况下根本没有独立的字段名可以匹配，只能去正则匹配消息文本内容：

```python
_DEFAULT_VALUE_PATTERNS: tuple[re.Pattern[str], ...] = (
    re.compile(r'(?i)(api[_\-]?key|apikey|token|secret|password|passwd|pwd)\s*[:=]\s*"([^"]{1,200})"'),
    re.compile(r"(?i)(api[_\-]?key|apikey|token|secret|password|passwd|pwd)\s*[:=]\s*'([^']{1,200})'"),
    re.compile(r'(?i)(api[_\-]?key|apikey|token|secret|password|passwd|pwd)\s*[:=]\s*([^\s,;"\']{1,200})'),
    re.compile(r'(?i)bearer\s+([A-Za-z0-9\-._~+/]{1,200})'),
)
```

这四条正则表达式分别对应四种常见写法：带双引号的`key="value"`、带单引号的`key='value'`、不带引号的`key=value`、以及HTTP里常见的`Authorization: Bearer xxxxx`格式。`(?i)`表示不区分大小写；括号包起来的部分是"捕获组"，用来记住"具体匹配到的是哪一段文本"，方便之后单独取出来处理。

代码注释里记录了两个真实的历史漏检（都能在测试文件里找到对应的用例）：

**最短长度曾经要求6个字符，但真实短密码/PIN会漏检**——比如`pwd=abc12`这种5-6位的真实场景，如果正则要求"值至少6个字符"，"abc12"（5位）会被判定为"太短所以不算敏感信息"而放过。修复后最短长度降到1，代价是"宁可误伤几个字符很短的非敏感值，也不能放过真实存在的短密钥"。

**不带引号的正则曾经在遇到空格时就提前截断**——真实密码/密钥可能内部包含空格（比如一句人类可读的passphrase），如果正则用`[^\s"']`这种排除空格的字符类去匹配"带引号"的值，第一个空格之后的内容就会被当成"值已经结束"，漏掉了空格后面本该一起脱敏的部分。修复后带引号的两条正则改成"允许值内部出现空格，只在遇到闭合引号时才停止"。

这两处都是同一类教训：**正则表达式设计时，"匹配范围过窄导致漏检"往往比"匹配范围过宽导致误伤"更危险**——对于安全相关的过滤逻辑，宁可牺牲一点精确度，也要优先保证不遗漏。

替换逻辑本身也有一个值得学的小技巧，在`_replace_value_group`里：

```python
@staticmethod
def _replace_value_group(match: re.Match[str]) -> str:
    """只替换捕获组里的"值"部分，保留匹配到的其余前缀（如key名/`bearer `），
    用span偏移量定位value在整个match里的精确位置，而不是靠字符串内容
    搜索——避免value本身的内容恰好在match别处重复出现时定位错误。"""
    full = match.group(0)
    value_group_index = 2 if match.lastindex and match.lastindex >= 2 else 1
    start, end = match.span(value_group_index)
    match_start = match.start(0)
    return full[: start - match_start] + "[REDACTED]" + full[end - match_start :]
```

这里没有用"字符串内容搜索"（比如"找到这个值文本再替换掉它"），而是用`match.span(...)`拿到捕获组在原文里的精确起止下标，再做数字层面的切片拼接。docstring解释了原因：**如果用内容搜索去定位要替换的部分，一旦"值"本身的文本恰好在整段匹配文字里的别的位置也出现过一次，替换就可能替换错位置**。用精确的数字下标定位，从根本上避免了这种"内容恰好重复导致误替换"的边界情况——这也是一个值得记住的通用原则：**能用位置信息精确定位的场景，尽量不要退化成用内容去反查位置。**

## `install_structured_logging`：把三件事捆成一个函数调用

最后这个函数把"JSON格式化"和"脱敏过滤"这两个必须同时具备的能力，捆绑成一步到位的安装函数：

```python
def install_structured_logging(
    logger: logging.Logger,
    *,
    sensitive_keys: frozenset[str] = DEFAULT_SENSITIVE_KEYS,
    handler_factory: Callable[[], logging.Handler] = logging.StreamHandler,
) -> logging.Handler:
    handler = handler_factory()
    handler.setFormatter(JsonFormatter())
    handler.addFilter(SensitiveDataFilter(sensitive_keys=sensitive_keys))
    logger.addHandler(handler)
    return handler
```

`handler_factory`的类型注解是`Callable[[], logging.Handler]`——"一个不接收参数、返回`logging.Handler`实例的函数"，默认值直接就是`logging.StreamHandler`这个类本身（在Python里类名本身就是"可调用、调用后创建实例"的东西，天然满足这个类型要求）。这样设计的好处是调用方不需要自己先创建好一个具体的handler实例再传进来，而是把"怎么创建"这件事整体传进来——真实项目想换成"写文件"或者"发到远程日志收集系统"的handler时，只需要传一个不同的工厂函数，`install_structured_logging`内部的"必须同时具备JSON格式化+脱敏过滤"这个组合约束不用重复。这也是这个模块反复强调的设计哲学的一个缩影：**把"必须同时成立的两件事"打包成一个不可拆分的安装步骤，比指望调用方分别记得做两件事更可靠。**

## 本章小结

- 结构化JSON日志能让日志变成"可以按字段查询/过滤的数据"，而不是只能靠肉眼`grep`的纯文本；`timestamp`用纯数字时间戳而不是格式化字符串，是为了不受服务器时区/时钟配置影响。
- `JsonFormatter`是"双重兜底"设计的真实案例：`default=str`只能兜住"json不认识的类型"，但兜不住"值的`__str__`自己抛异常"的情况——外层再包一层`try/except`，失败时退化成只含基础字段+`logging_error`说明的最小payload，保证"结构化日志绝不无声无息丢失一整条记录"这个承诺不被打破。
- 脱敏过滤器必须无差别地挂在`Handler`层面，对所有日志级别和调试开关状态统一生效，不能指望每个调用点自觉脱敏——真实事故正是"调试模式打开后完整请求体绕过脱敏流入日志"。
- 正则表达式类的安全过滤逻辑，历史上出现过"最短长度过严"和"遇空格提前截断"两处真实漏检，修复思路都是"宁可误伤过宽，也不能漏检过窄"。
- `record.msg`被脱敏改写后必须同步清空`record.args`，否则日志模块之后的`%`格式化会把原始未脱敏参数重新拼回消息里，让脱敏白做。

## 动手做

```python
import logging
import io

from ainative_observability import install_structured_logging

logger = logging.getLogger("demo_service")
logger.setLevel(logging.DEBUG)
logger.handlers.clear()

stream = io.StringIO()
install_structured_logging(logger, handler_factory=lambda: logging.StreamHandler(stream))

# 场景一：结构化字段脱敏
logger.info("user logged in", extra={"user_id": "u1", "password": "hunter2"})

# 场景二：即使调用方偷懒用f-string把敏感信息拼进消息文本，也照样被拦下
logger.debug('api_key: "sk-abcdefghijklmnop123456" was used for this call')

print(stream.getvalue())
```

跑一遍观察输出的两行JSON——`password`字段会被整体替换成`"[REDACTED]"`，第二行消息文本里的`sk-abcdefghijklmnop123456`也会被替换掉，而`api_key: `这部分前缀原样保留。

## 面试可能会问

**问：为什么`json.dumps(payload, default=str)`还不够安全，你会怎么设计一个"绝不丢失日志"的格式化器？**

答题思路：先说明`default=str`只解决"json模块本身不认识的类型"，再指出它无法防护"某个值的`__str__`方法自己抛异常"这种情况——这时`json.dumps`本身会抛出异常，如果不接住，日志模块默认的错误处理会让整条日志静默消失，甚至可能在非标准Handler下让异常直接冒出去打断业务代码。给出实际的解法：外层再包一层`try/except`，失败时退化成只包含时间戳/级别/logger名/消息本身+一条`logging_error`说明的最小payload，这份payload必定能被安全序列化。可以点出这类设计背后的一般原则：**任何"基础设施代码"（日志/监控/埋点）的失败模式，都不应该比它想要防护的业务代码本身更严重**，遇到自己内部处理失败时应该优雅降级而不是把故障向外传染。
