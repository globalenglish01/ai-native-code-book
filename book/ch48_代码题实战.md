# 第48章 —— 代码题实战

## AI Native岗位的代码题，考的是"边界情况"，不是"算法难度"

传统后端面试的代码题，经常考"手写一个LRU缓存"、"反转一棵二叉树"这类算法/数据结构题——难度在于你是否掌握某个经典解法。AI Native岗位的代码题风格明显不同：**题目本身的逻辑通常很简单，真正的难度藏在"你有没有想到那个容易被忽略的边界情况"**。这正是本书前47章一直在训练的能力——本章挑三道贴近真实场景的代码题，带你按"先写出天真版本→找出它会在哪里悄悄出错→修复"这个过程走一遍，这也是面试现场你应该展示给面试官看的思考过程，而不是直接写出最终答案。

## 题目一："写一个函数，把长文本按固定大小分块，允许指定重叠比例"

**天真版本**：

```python
def naive_chunk(text: str, chunk_size: int, overlap_ratio: float) -> list[str]:
    chunk_chars = chunk_size * 4
    step = int(chunk_chars * (1 - overlap_ratio))
    chunks = []
    start = 0
    while start < len(text):
        chunks.append(text[start:start + chunk_chars])
        start += step
    return chunks
```

**这个版本会在哪里悄悄出错？**——如果调用方传入`overlap_ratio=1.0`甚至更大，`step`会变成0或者负数，`while start < len(text)`这个循环会**永远不会结束**（`start`不再增长，或者反而在往回走），程序直接卡死；就算你把`while`换成`for start in range(0, len(text), step)`，Python的`range()`在`step<=0`时会**静默返回空序列**，函数"运行成功"但产出一个空列表，一个bug被伪装成了正常结果。

**面试现场你应该主动提到的修复**（对应第39章）：

```python
def chunk_text(text: str, chunk_size: int, overlap_ratio: float) -> list[str]:
    if not (0.0 <= overlap_ratio < 1.0):
        raise ValueError(f"overlap_ratio must be in [0, 1), got {overlap_ratio}")
    if chunk_size <= 0:
        raise ValueError(f"chunk_size must be positive, got {chunk_size}")

    chunk_chars = chunk_size * 4
    step = chunk_chars - int(chunk_chars * overlap_ratio)
    chunks = []
    start = 0
    while start < len(text):
        end = min(start + chunk_chars, len(text))
        chunks.append(text[start:end])
        if end >= len(text):
            break
        start += step
    return chunks
```

在参数入口就拒绝会导致`step<=0`的组合，而不是让这个隐患一路带到循环体内部才发作——**这道题真正想考的，就是你会不会在写完"逻辑正确"的代码后，继续追问一句"如果调用方传了一个奇怪的参数组合，我这段代码会发生什么"**。

## 题目二："实现一个函数，把多路打分结果按排名融合成一份排序"（RRF）

**天真版本**：

```python
def naive_fuse(scores_a: dict, scores_b: dict) -> list:
    combined = {}
    for doc_id in set(scores_a) | set(scores_b):
        combined[doc_id] = scores_a.get(doc_id, 0) + scores_b.get(doc_id, 0)
    return sorted(combined.items(), key=lambda x: x[1], reverse=True)
```

**这个版本会在哪里悄悄出错？**——直接把两个来源的原始分数相加。如果面试官告诉你"`scores_a`是关键词匹配次数（可能是1到20的任意整数），`scores_b`是余弦相似度（0到1之间）"，这个函数几乎必然会让`scores_a`主导最终排序，因为它的数值范围大得多——这不是bug，代码能正常跑，但**这是一个逻辑上错误的结果**，因为两个分数的量纲根本不可比。另外`scores_a.get(doc_id, 0)`这个写法也值得追问：**如果一个文档压根没被这一路检索召回，用`0`分参与相加，和"这份文档确实被召回了、但分数很低"混为一谈了吗？**——这是个值得在面试时主动提出来讨论的细节，即使最终代码没有处理到这么精细。

**面试现场你应该主动提到的修复**（对应第39章）：改用基于排名的RRF融合，而不是直接比较原始分数：

```python
def rrf_fuse(*ranked_lists: list[tuple[str, int]], k: int = 60) -> list[tuple[str, float]]:
    """每个ranked_list是[(doc_id, rank), ...]，rank从1开始。"""
    scores: dict[str, float] = {}
    for ranked_list in ranked_lists:
        for doc_id, rank in ranked_list:
            if rank < 1:
                raise ValueError(f"rank must start from 1, got {rank}")
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

面试官很可能会追问"为什么要用`1/(k+rank)`而不是直接用`1/rank`？"——能答出"`k`是为了拉平排名差距、避免第一名和第二名之间差距过大"，这是第39章讲过的细节，也是这道题的加分点。

## 题目三："给一批文本做batch embedding请求，供应商接口一次最多处理N段文字，请实现批量调用逻辑"

**天真版本**：

```python
async def naive_embed_all(texts: list[str], embed_fn, batch_size: int = 100) -> list[list[float]]:
    all_vectors = []
    for i in range(0, len(texts), batch_size):
        batch = texts[i:i + batch_size]
        vectors = await embed_fn(batch)
        all_vectors.extend(vectors)
    return all_vectors
```

**这个版本会在哪里悄悄出错？**——这段代码完全没有检查`embed_fn(batch)`返回的向量数量，是不是等于这批传进去的文字数量。面试官这时候通常会追问："如果某一批请求，供应商因为网络问题只返回了一部分向量，你的`all_vectors`最终长度会跟`texts`对不上，之后如果你把这些向量按下标一一对应地存进数据库，会发生什么？"——正确答案是**这份数据的对应关系会全部错位**：第5段文字得到的可能是本该属于第7段文字的向量，而且这种错位不会让程序报错，只会让检索结果长期而悄悄地"驴唇不对马嘴"。

**面试现场你应该主动提到的修复**（对应第41章）：

```python
async def embed_all_with_accounting(texts: list[str], embed_fn, batch_size: int = 100) -> list[list[float]]:
    all_vectors = []
    for i in range(0, len(texts), batch_size):
        batch = texts[i:i + batch_size]
        vectors = await embed_fn(batch)
        if len(vectors) != len(batch):
            raise RuntimeError(
                f"embedding count mismatch: requested {len(batch)} texts but received {len(vectors)} vectors"
            )
        all_vectors.extend(vectors)
    return all_vectors
```

这道题的核心考察点不是"你会不会写批量循环"（这个几乎每个人都会），而是**"你会不会在拿到一个外部依赖的返回值之后，主动核实它是否符合预期，而不是想当然地信任它"**。

## 一个通用的做题节奏，帮你在面试现场留下好印象

这三道题共同的节奏是：**先快速写出一个逻辑正确的版本，再主动说出"这个版本在什么输入下会出问题"，最后给出修复**。这个节奏本身，比"一上来就写出无懈可击的最终版本"更能体现你的真实水平——面试官更想看到的是你的思考过程，而不是你背下了某个标准答案。如果你能在写完天真版本后，不等面试官提示，就主动说一句"等等，如果这里传入的参数是……"，这个主动性本身就是加分项。

## 本章小结

- AI Native岗位的代码题，难度通常不在算法本身，而在"边界情况的完整性"——参数校验、数量对账、量纲统一这类看似琐碎但决定结果正确性的细节。
- 训练自己的做题节奏：先写出逻辑正确的天真版本，主动指出它会在什么输入下悄悄产生错误结果，再给出针对性的修复——这个过程本身就是面试官想看到的。
- 三道具体题目（分块函数、RRF融合、批量embedding请求）分别对应第39、41章的真实设计原则，可以直接作为练习模板反复推演。
- 拿到任何一个外部依赖（供应商API、其他服务）的返回值时，主动核实它是否符合预期（数量、格式、取值范围），而不是想当然地信任它，是这类代码题反复出现的核心考察点。

## 面试可能会问

**问：如果你调用一个外部服务的批量接口，怎么确保返回结果和你的请求是完全对应的？**

答题思路：先给出最基础的检查——返回结果的数量必须等于请求的数量，数量不匹配时应该直接抛出携带具体数字（请求了多少、实际收到多少）的异常，而不是记一条日志后返回`None`或者部分结果，因为后者会导致下游代码在毫无察觉的情况下,把结果按下标错位关联,造成隐蔽的数据质量问题。如果面试官追问"那如果数量能对上，但顺序被打乱了呢"，可以进一步提出——如果供应商接口本身不保证返回顺序和请求顺序一致，还需要额外的机制（比如让每个请求携带一个原始索引，让返回结果能够精确对应回去），而不能仅仅依赖"数量相同"就认定顺序也一定正确。
