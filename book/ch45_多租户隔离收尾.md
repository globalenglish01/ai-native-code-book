## 从"一个客户"到"很多个互不信任的客户共用一套系统"

前三章搭的客服平台、接入的知识库，隐含的假设是"这套系统只服务一家公司自己的客户"。但如果你要把这套系统做成一个SaaS产品卖给多家不同的企业客户呢？酒店预订平台A和电商平台B可能都在用你的客服系统，它们的知识库、对话记录、账单数据必须严格隔离——A公司的客服人员，无论如何都不能查到B公司的任何一条数据，哪怕只是通过一次意外的检索请求。

这一章要看的`multi_tenant_saas_platform.py`，是这本书综合实战部分的最后一章——它把第35-37章讲过的`ainative-tenancy`（租户隔离+资源配额）和第33、34章讲过的`ainative-observability`（结构化日志+追踪span）组合起来，演示一个多租户SaaS后端最基础也最不能出错的部分：**查询必须从数据源头就携带租户限定条件，而不是先查询全部数据、再靠事后过滤**。

## 查询必须真的携带租户过滤条件发出去

```python
class InMemoryDocumentStore:
    def query(self, scoped_query: ScopedQuery) -> list[Document]:
        """真正在查询这一步就应用租户过滤——`build_filter()`产出的条件
        被用来筛选，而不是先返回全部文档、调用方自己事后再过滤。"""
        filters = scoped_query.build_filter()
        results = [d for d in self._docs if d.tenant_id == filters["tenant_id"]]
        for doc in results:
            assert_result_belongs_to_tenant(doc.tenant_id, scoped_query)
        return results
```

第37章讲过的`ScopedQuery`和`assert_result_belongs_to_tenant`在这里被组合使用——留意这个方法的两层防护：

1. **`filters = scoped_query.build_filter()`然后用它去过滤`self._docs`**——过滤条件是从查询请求本身构造出来的（`ScopedQuery`这个类型本身不允许构造出"不限定租户"的状态），这是真正在数据源头就生效的隔离，而不是先把全部文档取出来、事后再按`tenant_id`筛一遍。
2. **`assert_result_belongs_to_tenant(doc.tenant_id, scoped_query)`对每一条结果再做一次复核**——即使上一步的过滤条件本身写对了，这一行依然会对每条即将返回给调用方的结果做一次独立验证，一旦发现任何一条"归属租户不对"的结果，会立刻抛出异常，把这当作一次严重的、需要马上关注的系统性问题。

这正是第37章反复强调的"结构性禁止"思路在一个具体（哪怕是极简的demo）存储实现里的落地——**隔离的可靠性建立在"类型层面不允许构造出不安全的查询"和"结果返回前有独立复核"这两层结构性保障上，而不是依赖某个开发者在写查询代码时的细心程度**。

## 资源配额：数据隔离和资源隔离是两件不同的事

```python
def search(self, tenant_id: str, request_id: str) -> list[Document]:
    with self.tracer.span("search_documents", correlation_id=request_id, tenant_id=tenant_id):
        self.resource_tracker.acquire_job_slot(tenant_id)
        try:
            with tenant_scope(tenant_id):
                query = ScopedQuery(tenant_id=tenant_id)
                results = self.document_store.query(query)
            logger.info(
                "search completed", extra={"tenant_id": tenant_id, "request_id": request_id, "result_count": len(results)},
            )
            return results
        finally:
            self.resource_tracker.release_job_slot(tenant_id)
```

这个方法把本书讲过的好几个模块，在一次请求的生命周期内组合了起来，值得按执行顺序拆开看：

**第一层：追踪span包裹整个操作**——`self.tracer.span("search_documents", correlation_id=request_id, tenant_id=tenant_id)`用`with`语句包住了这次搜索的全过程，第34章讲过的"span必须无论成功失败都被导出"在这里保证了不管这次搜索最终是否成功，都会留下一条可追溯的记录，而且`tenant_id`作为附加属性被记录在span上，方便事后按租户筛选追踪数据。

**第二层：先占用资源名额，再真正执行查询**——`self.resource_tracker.acquire_job_slot(tenant_id)`是第36章讲过的"先检查、再占用"模式，且用`try/finally`包住实际查询逻辑，保证不管查询过程是否出错，`release_job_slot`一定会被调用，不会出现"占用了名额但忘记释放"的资源泄漏。

**第三层：`tenant_scope`+`ScopedQuery`双重确保这次查询只查到自己的数据**——第35章讲的`contextvars`驱动的身份传播，加上第37章讲的类型层面的租户限定，两者叠加在一起。

**第四层：日志记录时用了脱敏过滤器**——`self._log_handler.addFilter(SensitiveDataFilter())`（在`__init__`里注册），保证即使这里的`extra={"tenant_id": ...}`未来被不小心加入了什么敏感字段，也会在写入日志之前被自动脱敏。

这四层放在一起，恰好覆盖了本书后半部分反复强调的四个不同维度的"隔离"和"可观测性"关切，而且没有一个是多余的——**去掉任何一层，都会让这个方法出现一个前面章节讲过的具体真实弱点**（比如去掉`try/finally`会导致配额泄漏、去掉`assert_result_belongs_to_tenant`会失去复核防线）。

## 完整的验证：一个租户的行为，不能影响另一个租户

```python
async def main() -> None:
    platform = MultiTenantSaasPlatform()
    platform.onboard_tenant("acme-corp", max_concurrent_jobs=2)
    platform.onboard_tenant("globex-inc", max_concurrent_jobs=2)

    platform.ingest_document("acme-corp", "doc-1", "Acme's confidential Q3 roadmap")
    platform.ingest_document("globex-inc", "doc-2", "Globex's confidential merger plan")

    acme_results = platform.search("acme-corp", request_id="req-001")
    globex_results = platform.search("globex-inc", request_id="req-002")
```

这段代码验证的是最基本的数据隔离——两家公司的文档互相看不到彼此。但这个示例更进一步，验证了"资源隔离"这个经常被忽视的维度（第36章讲过的核心观点：数据隔离做对了，不代表资源隔离也做对了）：

```python
print("\nsimulating a burst of acme-corp searches exhausting its quota:")
platform.resource_tracker.acquire_job_slot("acme-corp")
platform.resource_tracker.acquire_job_slot("acme-corp")
try:
    platform.resource_tracker.acquire_job_slot("acme-corp")
except QuotaExceededError as exc:
    print(f"  acme-corp correctly throttled: {exc}")
globex_still_works = platform.search("globex-inc", request_id="req-003")
print(f"  globex-inc unaffected, search still works: {len(globex_still_works)} document(s)")
```

这一段模拟了`acme-corp`突然发起大量并发搜索、耗尽了自己的配额——**关键的验证点在于`globex_still_works`必须依然能成功执行**。如果这套系统的配额管理有问题（比如共享了同一个全局计数器、没有真正按租户区分），`acme-corp`的这波突发流量很可能会连带影响到完全无辜的`globex-inc`——这正是"数据隔离做得再好，资源层面共享计算资源不加区分，一个租户依然可以拖累其他租户"这个真实风险的具体演示。

## 本章小结

- 多租户系统的查询隔离，必须建立在"查询本身在数据源头就携带租户限定条件"之上，外加"返回结果前做一次独立复核"作为最后一道防线——而不是先查全部数据再事后过滤，后者的可靠性完全取决于过滤逻辑本身不出任何疏漏。
- 一次真实的多租户请求处理，往往需要同时叠加多层关切：追踪span记录整个操作、资源配额的获取与释放、租户身份的传播与限定、日志脱敏——这几层各自独立、缺一不可，去掉任何一层都会让某个具体的真实弱点重新暴露出来。
- "数据隔离"和"资源/容量隔离"是两个必须分别验证的维度——一个租户的突发流量耗尽了自己的配额后，另一个完全无关的租户的正常请求必须完全不受影响，这才是真正意义上的多租户隔离。
- 到这里，本书的13个包在4章综合实战里都已经以真实、可运行、有测试覆盖的代码形式被组合演示过——从最基础的护栏和记忆管理，到多智能体委派与人工审批，到检索增强生成，再到多租户隔离与可观测性，这条链路覆盖了一个真实AI Native系统在生产环境里需要认真对待的绝大部分维度。

## 面试可能会问

**问：设计一个多租户SaaS后端时，你觉得最容易被忽视、但一旦出问题后果很严重的环节是什么？**

答题思路：先讲清楚"数据隔离"（谁能看到谁的数据）本身就有一个隐蔽的失效模式——查询表面上带了租户过滤参数，但实际上是先不加区分地查询全部数据、再事后按租户筛选，这种方式的可靠性完全依赖过滤逻辑不出任何疏漏。正确做法是让查询从数据源头就携带租户限定条件，并且在真正返回结果前加一道独立的复核断言作为最后防线。然后指出一个经常被忽视的第二维度——"资源/容量隔离"：即使数据完全隔离，如果任务队列、数据库连接池这类共享计算资源不按租户设置配额，一个高负载租户依然可以拖累其他租户的正常请求。可以举例说明,验证多租户隔离是否做对,应该专门测试"一个租户的突发流量/异常行为,是否会影响到另一个完全无关的租户",这是比单纯测试"数据查不查得到"更全面的验证思路。
