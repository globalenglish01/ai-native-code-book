# 第22章 —— 长期记忆的存取与裁剪

代码位置：`packages/ainative-memory/src/ainative_memory/store.py`、`packages/ainative-memory/src/ainative_memory/history_budget.py`、`packages/ainative-memory/src/ainative_memory/rendering.py`

## 一个只会精打细算一半的账房先生

想象你在设计一个RAG系统的prompt组装逻辑：检索出来的文档片段，你按token预算精心截断过；抽取出来的实体、关系，你也按预算裁剪过；就连系统提示词，你都反复压缩打磨到刚好够用。你对每一部分的token开销都算得清清楚楚——除了一个地方：**对话历史（`conversation_history`）**。它随着对话轮数一轮一轮往上叠，你从来没有给它设过任何上限。

这不是一个假设的场景。`history_budget.py`模块的docstring直接点名了这个真实的生产反面案例：

> 背景：调研中发现一个真实的生产反面案例——某RAG系统里，检索到的文档片段/实体/关系都有明确的token预算与截断逻辑，唯独`conversation_history`完全没有任何token计数或截断机制，随对话轮数增长可以无限膨胀，即使其余部分的预算算得再精确，加上一段未被计入预算的历史后，最终prompt仍可能超出模型上下文窗口。

这就像一个账房先生，把柴米油盐每一笔小账都算得精细入微，却完全没注意到房租这项最大的固定支出——账算得再准，加上这一笔被忽略的大项，总账照样对不上。**局部精确不等于整体正确**，只要有一处没被纳入统一预算，其余地方算得再仔细也是白费。这一章要看的，就是这个包如何把"长期记忆"和"对话历史"这两件事分别管起来，以及`history_budget.py`如何把"历史必须计入预算"这件事做成默认行为，而不是一个容易被遗忘的可选项。

## 长期记忆存取：`InMemoryMemoryStore`

先看"长期记忆"这条线——它解决的是另一个问题：跨多次对话、多个章节，怎么记住"这个用户/这次会话之前发生过什么"。`store.py`的实现思路很直接，按`owner_id`分组存放：

```python
class InMemoryMemoryStore:
    def __init__(self) -> None:
        # key是owner_id，value是这个owner名下所有记忆条目组成的列表。
        self._entries: dict[str, list[MemoryEntry]] = {}

    async def append(self, entry: MemoryEntry) -> None:
        bucket = self._entries.setdefault(entry.owner_id, [])   # 拿到（或创建）这个owner的记忆列表
        # dataclasses.replace(entry, metadata=...)——基于entry创建一份
        # 新对象，只替换metadata字段，其余字段保持不变；metadata本身
        # 用deepcopy深拷贝，避免和调用方手里的原始字典共享引用。
        bucket.append(dataclasses.replace(entry, metadata=copy.deepcopy(entry.metadata)))

    async def load_recent(
        self, owner_id: str, *, before_sequence: int | None = None, max_items: int = 10
    ) -> list[MemoryEntry]:
        bucket = self._entries.get(owner_id, [])   # 查不到这个owner就当作空列表
        # 条件表达式：传了before_sequence就只保留序号更小（更早）的条目，
        # 模拟"翻页看更早历史"；没传就是全部条目的一份浅拷贝列表。
        candidates = (
            [e for e in bucket if e.sequence < before_sequence]
            if before_sequence is not None
            else list(bucket)
        )
        # sort(key=..., reverse=True)——按sequence字段从大到小排序，
        # 也就是"最新的排在最前面"。
        candidates.sort(key=lambda e: e.sequence, reverse=True)
        # candidates[:max_items]——切片，只取排序后的前max_items条；
        # 返回时同样对每一条的metadata做深拷贝，防止调用方修改
        # 查询结果时意外污染内部真正存储的数据。
        return [dataclasses.replace(e, metadata=copy.deepcopy(e.metadata)) for e in candidates[:max_items]]

    async def delete_by_owner(self, owner_id: str) -> int:
        # dict.pop(key, 默认值)——取出并删除这个key对应的value；
        # 查不到就当作空列表，不会抛KeyError。
        bucket = self._entries.pop(owner_id, [])
        return len(bucket)   # 返回删除了多少条，方便调用方记日志确认
```

`append()`按`owner_id`把记忆条目分桶存放，`load_recent()`支持两种查询模式：不传`before_sequence`就拿"最新的`max_items`条"，传了`before_sequence`就相当于"翻页看更早的历史"（只看序号小于这个值的记忆，再取最新的`max_items`条）。`delete_by_owner()`用`dict.pop(key, 默认值)`一次性把某个owner名下的全部记忆连同对应的key一起清掉，同时返回被删除的条数，方便调用方记日志确认"这次清理删了多少条"。

你可能注意到了每个方法里都出现了`dataclasses.replace(..., metadata=copy.deepcopy(...))`这一行——这正是第5章"别名bug大家族"里讲过的那个真实bug的修复方式：`MemoryEntry`虽然是frozen dataclass，但它的`metadata`字段是普通可变dict，如果存入/取出时不做深拷贝，调用方复用同一个可变dict当"元数据模板"构造多条记忆，或者拿到查询结果后修改了某条的`metadata`，都会静默污染这个类内部真正存储的数据。这个bug已经在第5章详细讲过，这里不再重复，只提醒一句：**这正是"跨模块反复出现的同一类bug"这个说法的又一个真实实例**，能一眼认出"存/取两端都要深拷贝"这个模式，比记住这一个具体函数更重要。

`InMemoryMemoryStore`只负责"存/取/按owner删除"这三件事，`append()`收到什么记忆内容就存什么——**提取什么、怎么提取（比如调用LLM生成一段摘要）完全不是这个类的职责**，那是调用方（通常搭配`ainative_prompt.judge`或调用方自己的LLM调用逻辑）该考虑的事。这种拆分是有意为之：存储层的实现（内存版、数据库版）可以自由替换，不会牵连"怎么生成记忆内容"这一层逻辑。

## 渲染：把记忆条目变成能塞进prompt的文本

拿到`load_recent()`返回的一组`MemoryEntry`之后，怎么把它们变成一段能直接拼进system prompt的文本？`rendering.py`把这件事单独抽成一个纯函数：

```python
def render_memory_entries(entries: list[MemoryEntry], *, header_template: str = "## Memory #{sequence}") -> str:
    if not entries:
        return ""   # 没有任何记忆条目，直接返回空字符串

    # 列表推导式：对每条记忆e，用header_template.format(...)把序号
    # 填进模板里做标题，再拼上正文content，组成一段"标题+正文"文本。
    blocks = [f"{header_template.format(sequence=e.sequence)}\n{e.content}" for e in entries]
    return "\n\n".join(blocks)   # 用空行把所有文本块连接起来
```

`blocks = [...]`这一整行是一个"列表推导式"——你可以把它理解成"用一个简写语法写出来的for循环"：对`entries`里的每一条记忆`e`，都生成一段"标题+正文"的文本，最终把这些文本收集成一个列表。它和写一个完整的`for`循环、每次`.append()`一次的效果完全一样，只是更紧凑。`header_template.format(sequence=e.sequence)`用的是Python字符串的`.format()`方法，把模板里的`{sequence}`占位符替换成这条记忆真正的序号。最后`"\n\n".join(blocks)`把所有文本块用一个空行连接起来，让每条记忆之间在视觉上有清晰的分隔。

这个函数被单独抽出来（而不是塞进`store.py`里）的原因，模块docstring说得很明确：**"存/取/裁剪"和"怎么把一组记忆条目拼成一段可读文本"是两个独立的关注点**——分开之后，调用方可以自由替换渲染格式（比如换成JSON格式而不是Markdown标题），完全不需要改动存储层的任何代码。这是一种很常见、也值得模仿的设计习惯：一个函数只做一件事，"存取数据"和"格式化数据"分别属于不同的函数。

## 对话历史的token预算裁剪：`trim_history_to_budget`

回到本章开头那个"账房先生"的问题。`history_budget.py`把"对话历史必须纳入统一token预算"做成了默认行为，而不是一个可选项——它的核心函数是`trim_history_to_budget`：

```python
def trim_history_to_budget(
    history: list[dict[str, Any]],
    *,
    max_tokens: int,
    content_key: str = "content",   # 每条消息里，实际文字内容存在哪个字段名下
) -> list[dict[str, Any]]:
    kept: list[dict[str, Any]] = []   # 最终决定保留下来的消息
    used = 0   # 目前已经用掉的token预算
    # reversed(history)——倒着遍历，从最近的消息开始往前走。
    for message in reversed(history):
        text = str(message.get(content_key, ""))   # 取出这条消息的文字内容
        cost = _estimate_tokens(text)   # 估算这条消息大概占多少token
        # kept非空——保证至少保留最新的一条，即使它本身就超预算；
        # used + cost > max_tokens——加上这条会超出预算，就此打住。
        if kept and used + cost > max_tokens:
            break
        kept.append(message)
        used += cost
    kept.reverse()   # 倒着塞进去的，顺序是反的，翻回正常的时间顺序
    return copy.deepcopy(kept)   # 深拷贝返回，避免和原始history共享引用
```

先看`reversed(history)`——这是"倒着遍历"的意思，从最后一条（最近的消息）开始一路往前遍历到最早的一条。为什么要倒着来？因为这个函数的策略是"优先保留最近的消息，预算不够时丢弃最早的消息"，从最近的开始往预算里塞、塞不下就停，天然就实现了这个"越新越优先"的效果——如果正着遍历，你反而得先把所有消息都看一遍才知道该从哪里开始丢弃最早的那些。

`if kept and used + cost > max_tokens: break`这一行有一个容易被忽略但很重要的细节：条件里`kept`非空这个判断，保证了**哪怕最新的这一条消息本身开销就已经超过预算，也至少会被保留下来**——不会因为预算设置得极小，最终返回一个完全空的历史。想一想为什么这样设计更合理：如果因为预算太紧就返回空历史，模型会完全丢失最近发生了什么，这比"稍微超一点预算但至少留住了最新一条"要糟糕得多。这是一个很实用的工程取舍：宁可稍微突破预算上限，也不要让上下文完全断裂。

遍历结束之后，`kept`列表内部的顺序是"最新的在前、最早的在后"——因为是倒着塞进去的，顺序自然是反的。`kept.reverse()`把它原地倒回正常的时间顺序，让返回结果和原始`history`的先后顺序保持一致。

## `estimate_history_tokens`：不裁剪，只是"提前知道要花多少"

`history_budget.py`还提供了一个配套的只读查询函数：

```python
def estimate_history_tokens(history: list[dict[str, Any]], *, content_key: str = "content") -> int:
    # sum(生成器表达式)——对history里每条消息m，取出内容、估算token数，
    # 不预先构造整个列表，边生成边累加，最后把所有token数加总。
    return sum(_estimate_tokens(str(m.get(content_key, ""))) for m in history)
```

`sum(...)`括号里的这一整段——`_estimate_tokens(str(m.get(content_key, ""))) for m in history`——叫"生成器表达式"：和上面`rendering.py`里的列表推导式很像，区别在于它不会先构造出一个完整的列表再传给`sum()`，而是一边生成一边被`sum()`消费，省一点内存。效果是：对`history`里每一条消息都重复"取字段、转字符串、估算token"这套逻辑，再把所有结果加总，得到整段历史的估算总token数。

这个函数**不做任何裁剪**，纯粹是给调用方一个"提前知道这段历史大概要占多少预算"的工具。为什么需要它？因为真实场景里，一个prompt的总预算往往是"历史 + 检索文档 + 系统提示词"三者相加，调用方经常需要先知道"历史已经占了多少"，才能算出留给检索文档的预算还剩多少。这个函数和`trim_history_to_budget`分开存在，意味着"估算"和"裁剪"是两个可以独立使用的关注点——你可以只查询不裁剪，也可以直接裁剪不单独查询。

token估算本身用的是一个很朴素的经验公式：

```python
def _estimate_tokens(text: str) -> int:
    # len(text)——字符串长度；// 4——整数除法，自动向下取整，
    # 用"约4个字符算1个token"这个粗略经验比例估算。
    return len(text) // 4
```

字符数除以4，`//`是整数除法（自动向下取整，不会出现"2.5个token"这种没有意义的小数结果）。docstring说明了这个比例的来源——与`ainative_guardrail.budget_middleware`保持一致的经验估算比例，属于"够用就好"（best-effort）的近似，不追求精确到调用真实模型厂商tokenizer的程度。真实项目里如果需要更精确的计数，可以替换成调用具体模型的tokenizer，但那样会引入额外依赖、增加复杂度——对于"历史该不该被裁剪"这类决策，一个足够接近的估算通常就够用了。

## 为什么返回值必须是深拷贝

`trim_history_to_budget`最后一行`return copy.deepcopy(kept)`，docstring里专门解释了这么做的原因：

> 调用方常见的用法是"把裁剪结果当成自己的副本，发给模型之前再做一次编辑/脱敏"，如果返回的字典和原始`history`是同一个对象，这类"看起来安全的修改"会静默改写调用方可能仍然持有、以为完好无损的原始历史记录（比如存在checkpoint/会话存储里的那份）。

这仍然是第5章讲过的那类"别名bug"的一个新变种：`trim_history_to_budget`裁剪之后返回的这份历史，很自然地会被调用方接着做下一步处理——比如下一章要讲的、落盘前的PII脱敏。如果这份"裁剪结果"和调用方手里还留着的原始`history`（也许正存在checkpoint里，等着下次恢复用）共享同一批消息字典对象，那么"只对裁剪结果做脱敏"这个动作，会顺带把原始历史记录也脱敏掉——调用方以为自己修改的是一份独立副本，实际上却在悄悄篡改另一份自己仍然需要保持原样的数据。`copy.deepcopy`保证裁剪结果和原始`history`彻底独立，无论后续怎么处理这份裁剪结果，都不会意外影响调用方手里那份原始记录。

## 本章小结

- 一个真实的生产反面案例：某RAG系统给检索文档、实体关系都做了精细的token预算，唯独忘了给`conversation_history`设任何上限，最终prompt仍可能超出上下文窗口——局部精确不等于整体正确。
- `trim_history_to_budget`把"历史必须计入预算"做成默认行为：调用方想不裁剪，需要显式传一个很大的`max_tokens`，而不是"忘记裁剪"这种隐式默认状态。
- 从最近的消息开始倒序保留、塞不下就停，天然实现"越新越优先"；即使最新一条消息本身就超预算，也至少保留这一条，避免返回完全空的历史。
- `estimate_history_tokens`是独立的只读查询工具，供调用方把历史开销并入"历史+检索文档+系统提示词"的总预算计算。
- 返回值必须深拷贝，否则调用方对裁剪结果的后续处理（比如脱敏）会意外污染仍然持有的原始历史——这是第5章"别名bug"在对话历史场景下的又一次真实体现。
- `InMemoryMemoryStore`的存取深拷贝bug已经在第5章讲过，这里不再重复。

## 动手做

```python
from ainative_memory.history_budget import trim_history_to_budget, estimate_history_tokens

# 列表推导式：模拟生成20轮对话历史，每条都是一个带role/content的字典。
history = [{"role": "user", "content": f"这是第{i}轮对话内容，占一点篇幅"} for i in range(20)]

total = estimate_history_tokens(history)
print("裁剪前估算token数：", total)

trimmed = trim_history_to_budget(history, max_tokens=50)
print("裁剪后保留了多少条：", len(trimmed))
print("裁剪后估算token数：", estimate_history_tokens(trimmed))

# 验证深拷贝：修改裁剪结果，不应该影响原始history
trimmed[0]["content"] = "已被修改"
print("原始history是否被污染：", history[-len(trimmed)]["content"] == "已被修改")
```

## 面试可能会问

**问：设计一个RAG或多轮对话系统的prompt组装逻辑时，你会怎么控制总token预算不超限？**

答题思路：先指出一个容易被忽视的真实反面案例——很多系统对检索文档、实体关系都做了精细的token预算，却唯独忘了给对话历史设上限，导致历史随对话轮数无限膨胀，最终仍可能超出模型上下文窗口。正确做法是把"历史裁剪"做成默认行为而非可选项：从最近的消息开始倒序保留，直到用满预算为止，同时保证至少保留最新一条消息避免上下文完全丢失。再补充一点：裁剪函数返回的结果必须和原始历史深拷贝隔离，否则调用方对裁剪结果的后续处理（比如脱敏）会意外污染仍然持有的原始记录。如果能提到"用一个独立的估算函数把历史开销并入总预算计算"，说明你考虑到了历史、检索文档、系统提示词三者需要统一核算，而不是各算各的。
