# 第9章 —— 连续失败与卡死检测

代码位置：`packages/ainative-guardrail/src/ainative_guardrail/budget_middleware.py`

## 两种不同的"卡住"

Agent"卡住"至少有两种不同的表现形式，需要用不同的机制识别：

1. **同一个工具连续报错**——比如反复调用一个参数错误的API，每次都失败，但AI没有意识到应该换个思路，而是不断用轻微变化的参数重试。
2. **反复做"只读探索"却没有实质进展**——比如反复`ls`、`grep`、`read_file`，却始终没有真正往前推进任务（没有写文件、没有运行测试）。

这一章看`ConsecutiveRetryGuardMiddleware`（应对第一种）和`ConsecutiveCallGuardMiddleware`（应对第二种），以及它们各自设计里一个曾经真实存在过的bug。

## `ConsecutiveRetryGuardMiddleware`：数连续失败次数

核心逻辑很直接——记一个"每个工具当前连续失败了多少次"的字典，超过上限就拦截：

```python
def _maybe_short_circuit(self, request: ToolCallRequest) -> ToolMessage | None:
    name = request.tool_call.get("name", "")
    count = self._errors.get(name, 0)
    if count < self._max:
        return None
    return self._short_circuit_message(request, count)
```

## 一个真实的bug：短路消息污染了自己的计数器

这个类的docstring里坦诚地记录了一个曾经存在、后来被修复的真实缺陷：

> `ConsecutiveRetryGuardMiddleware`合成短路消息污染计数器：原版`wrap_tool_call`把自己短路拦截时生成的合成`ToolMessage`（status="error"）又传回`_record`当作"新的一次真实失败"继续累加，导致`status()`快照随着AI反复尝试已经被拦截的工具无限膨胀、失真。

翻译一下这个场景：假设上限是2次，AI连续失败了2次，第3次调用被拦截（返回一条`status="error"`的合成消息）。**如果这条"我们自己编造出来告诉AI别再试了"的消息，又被同一套计数逻辑当成"第3次真实失败"记录了下来**，那么计数器会变成3、4、5……一直往上涨，即使AI已经完全没有真正执行过这个工具。这个数字后续如果被用来做别的判断（比如"错误率超过多少就升级报警"），就会被这个自我循环污染的数字误导。

修复方式是把"短路"和"记录"这两件事严格分开：

```python
def wrap_tool_call(self, request, handler):
    short = self._maybe_short_circuit(request)
    if short is not None:
        return short   # 注意：这里不调用_record_real_result
    result = handler(request)
    self._record_real_result(request, result)   # 只有真正执行过的结果才被记录
    return result
```

**只有真正调用了`handler`（意味着工具真的被执行了一次）之后拿到的结果，才会被传给`_record_real_result`**。短路路径直接返回，压根不经过记录逻辑。这个修复的一般化道理是：**当你的系统会"合成"一些数据去影响后续行为时（这里是给AI看的提示消息），一定要确认这份合成数据不会被自己的其他统计/监控逻辑，误当成"真实发生的事件"重新计入统计**——这是一种很容易被忽视的"自己骗自己"的循环。

## `ConsecutiveCallGuardMiddleware`：区分"停滞"和"推进"

第二种卡住模式的检测逻辑更有意思，它需要维护两组工具名单：

```python
DEFAULT_STALL: frozenset[str] = frozenset({"ls", "glob", "read_file", "grep"})
DEFAULT_PROGRESS: frozenset[str] = frozenset({"write_file", "edit_file", "run_tests"})
```

判断逻辑：

```python
def _evaluate(self, request):
    name = request.tool_call.get("name", "")
    if name in self._progress:
        self._stall_count = 0   # 出现"推进类"工具，停滞计数清零
        return None
    if name in self._stall:
        self._stall_count += 1   # "停滞类"工具累加计数
        if self._stall_count > self._max:
            return ToolMessage(..., status="error")
    return None   # 既不属于推进类也不属于停滞类，不影响计数
```

值得注意的一处细节，在构造函数里：

```python
self._stall = stall_tools if stall_tools is not None else self.DEFAULT_STALL
```

为什么这里要写`stall_tools is not None`，而不是更简洁的`stall_tools or self.DEFAULT_STALL`？因为`frozenset()`（一个空集合）在Python里同样是"假值"（`bool(frozenset())`是`False`）。如果调用方**明确想传一个空集合**（意思是"我认为没有任何工具算作停滞类"），用`or`写法会把这个合法的空集合误判成"没有传值"，从而错误地套用默认值——这样调用方的意图就被悄悄篡改了。`is not None`才能准确区分"真的没传（None）"和"传了一个恰好是空的值"这两种不同情况。这是一个值得记住的Python细节：**`or`做默认值兜底，只在"任何假值都应该被当作没传"的场景下才安全；一旦"空但有意义"和"完全没传"需要被区分，就必须显式用`is not None`**。

## 本章小结

- "卡住"有多种表现形式（连续失败、反复停滞），需要设计不同的检测逻辑，而不是用一个笼统的"失败次数"指标。
- 一个真实bug：拦截时生成的合成消息，如果被自己的统计逻辑当成"真实事件"重新计数，会导致计数器自我膨胀失真——合成数据绝不能被自己的监控逻辑误判为真实发生的事。
- `stall_tools if stall_tools is not None else DEFAULT`，而不是`stall_tools or DEFAULT`——当"空值"和"没传值"需要被区分时，只能用`is not None`，`or`会把两者混为一谈。

## 动手做

```python
from ainative_guardrail.budget_middleware import ConsecutiveCallGuardMiddleware

guard = ConsecutiveCallGuardMiddleware(max_stall_calls=2)

class FakeRequest:
    def __init__(self, name):
        self.tool_call = {"name": name, "id": "1"}

for tool in ["ls", "grep", "read_file", "write_file", "ls"]:
    result = guard._evaluate(FakeRequest(tool))
    print(tool, "→", "拦截" if result else "放行", guard.status())
```

观察`write_file`出现之后，停滞计数是不是被清零了。

## 面试可能会问

**问：给Agent设计"防卡死"机制时，你会怎么避免监控逻辑本身引入新的bug？**

答题思路：举出"合成的拦截消息被自己的计数逻辑重新统计，导致数字自我膨胀"这个真实例子，说明"任何由系统自己生成、用来影响AI行为的数据，都不应该被系统自己的统计/审计逻辑误当作真实发生的外部事件"这个原则。这体现的是"监控系统自身也需要被谨慎设计，不能想当然"的成熟工程思维，比只会说"加个计数器"更有说服力。
