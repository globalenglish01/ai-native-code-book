# 第37章 —— 结构性禁止忘记加租户过滤

代码位置：`packages/ainative-tenancy/src/ainative_tenancy/scoped_query.py`

## 两种"看起来隔离了，实际上没有"的真实事故

这一章讲的模块，docstring里记录了两个具体的、真实发生过的多租户查询隔离失效案例，非常值得逐一拆解：

> 1. `scope="all"`模式完全不做租户过滤——代码注释明确写着"None = 不过滤"，任何持有合法凭证的调用方都能读到其他租户的全部文档。
> 2. 即使`scope`看似限定了范围，实际检索依然是先对整个共享索引发起不带租户限制的查询，再靠事后过滤（如按`file_path`）实现隔离——隔离效果完全依赖过滤逻辑本身不出现任何疏漏，是比"完全未隔离"更隐蔽的失效模式，因为表面上看起来像是做了隔离。

第一种失效很直观——就是压根没做隔离。第二种更值得警惕：**代码表面上"看起来"做了隔离（确实调用了一个叫`scope`的参数，确实有"按租户过滤"这个步骤），但过滤发生在"查询已经返回了全部数据之后"，而不是"查询本身就带着租户限制发出去"**。这种"事后过滤"的隔离方式，效果完全取决于过滤逻辑本身有没有任何遗漏——一旦某处过滤条件写漏了、或者某条新增的数据路径忘了走这层过滤，隔离就会静默失效，而且因为代码表面上"看起来在做隔离"，这类bug比"压根没写隔离代码"更难被发现、更容易被信任。

## `ScopedQuery`：不给"不限定租户"留任何合法出口

```python
@dataclass(frozen=True)
class ScopedQuery:
    tenant_id: str
    extra_filters: dict[str, Any] = field(default_factory=dict)

    def __post_init__(self) -> None:
        if not self.tenant_id:
            raise MissingTenantScopeError(
                "ScopedQuery requires a non-empty tenant_id — there is no valid "
                "'unscoped' query; use a dedicated admin/system query path instead"
            )
```

`tenant_id`是一个没有默认值的必填字段——Python的dataclass在没有默认值的字段上，会强制要求调用方显式传值，构造`ScopedQuery()`不传`tenant_id`直接就会报错。`__post_init__`是dataclass提供的一个"钩子方法"：所有字段都赋值完毕之后自动被调用，常用来做"构造参数的合法性校验"。这里额外检查了`not self.tenant_id`——同时拦住"传了空字符串"和"传了`None`"两种非法输入（两者在Python里都是"假值"）。

**这个设计最关键的地方在于文档里明确写的这句话："没有‘不限定租户’这个合法选项"**。也就是说，`ScopedQuery`这个类型本身，从构造的那一刻起，就不可能代表"一次不限定租户的查询"——如果真的需要跨租户的系统级查询（比如运营后台需要看全平台数据），这个模块的态度是：**那应该走一条完全独立的、需要额外授权检查的管理员接口，而不是把"开发者不小心忘记传tenant_id"和"这次确实是有意要做一次跨租户查询"这两种性质完全不同的情况，用同一套代码路径、同一个"看起来像是随手漏传了参数"的表现形式混在一起**。这是"结构性禁止"这四个字的具体含义——不是靠代码审查/文档提醒开发者"记得传`tenant_id`"，而是让"不传`tenant_id`"这件事在类型层面直接构造不出来。

## `build_filter`：写在后面的键会覆盖前面的

```python
def build_filter(self, *, tenant_field: str = "tenant_id") -> dict[str, Any]:
    return {**self.extra_filters, tenant_field: self.tenant_id}
```

这一行代码值得放慢速度看。`{**self.extra_filters, tenant_field: self.tenant_id}`——先把`extra_filters`字典里的所有键值对"展开"铺开，再放进（或覆盖）一个`tenant_field`键。**这里的书写顺序至关重要**：在Python的字典字面量里，如果同一个key出现了两次，**后写的那次会覆盖先写的那次**。`tenant_field: self.tenant_id`写在`**self.extra_filters`**之后**，这意味着——即使调用方不小心（或者恶意）在`extra_filters`里塞进了一个同名的`tenant_id`键（比如`extra_filters={"tenant_id": "别的租户"}`，试图覆盖掉真正的租户限定条件），最终返回的结果里，这个键的值也一定会被`self.tenant_id`重新覆盖回正确的值，不会被意外顶掉。

这是一个非常小、但值得反复咀嚼的细节：**"租户限定条件不能被任何其他过滤条件意外覆盖"这个安全承诺，不是靠一句注释提醒"别在extra_filters里传tenant_id"来保证的，而是靠字典合并时的书写顺序，从代码结构上直接确保的**。哪怕未来有人真的不小心往`extra_filters`里塞了一个同名键，这一行代码的行为依然是正确的、安全的。

## 最后一道防线：查完之后再核实一遍

```python
def assert_result_belongs_to_tenant(result_tenant_id: str, query: ScopedQuery) -> None:
    if result_tenant_id != query.tenant_id:
        raise MissingTenantScopeError(
            f"query scoped to tenant '{query.tenant_id}' returned a result belonging "
            f"to tenant '{result_tenant_id}' — the underlying store's filter did not "
            f"actually apply the tenant scope; treat this as a critical isolation failure"
        )
```

文档特别强调了这个函数的定位："**不能替代**`build_filter()`在查询源头就过滤（事后过滤本身正是本章开头讲的第二种失效模式），只用来在真正返回给调用方之前，对‘存储层过滤逻辑本身是否正确生效’做一次独立复核"。

这里有一个精妙的地方：`assert_result_belongs_to_tenant`本身看起来"就是一次事后过滤"，那它和docstring批评的"事后过滤"失效模式有什么不同？**区别在于职责定位，不在于"是否发生在查询之后"这个时间点本身**——`build_filter()`才是真正承担"隔离"这个职责的地方，它必须在发起查询时就生效；`assert_result_belongs_to_tenant`不承担隔离职责，它的职责是"复核隔离是否真的生效了"——如果这个断言真的抓到了一条"归属租户不对"的结果，说明**前面`build_filter()`这道防线本身已经失效了**，这是一次严重的、需要立刻关注的系统性问题，而不是"这次事后过滤帮你兜住了一个漏网之鱼、万事大吉"。**一道防线的"事后检查"，和另一道防线本身用"事后过滤"来实现隔离，看起来都发生在查询之后，但两者的角色和后果完全不同**——前者是纵深防御里的最后一道复核，后者是把本该在源头解决的问题，错误地寄希望于末端补救。

## 本章小结

- 多租户查询隔离最隐蔽的失效模式，不是"完全没做隔离"，而是"看起来做了隔离，实际上是先查询全部数据、再事后过滤"——这种隔离的可靠性完全取决于过滤逻辑本身不出任何疏漏。
- 让"不限定租户"这个选项在类型构造阶段就不可能出现（必填字段+`__post_init__`校验），比"靠文档/代码审查提醒开发者别忘了传租户ID"更可靠。
- 字典合并`{**extra, key: value}`中，写在后面的键值对会覆盖前面的——利用这个规则可以从代码结构上确保关键字段（如租户限定条件）不会被其他数据意外覆盖。
- 一次"事后核实隔离是否生效"的断言，和"用事后过滤实现隔离本身"是两回事——前者是发现问题的最后一道防线，后者才是本该在源头就解决、却被错误地推迟到末端的问题。

## 面试可能会问

**问：你怎么确保一个多租户系统的查询接口，不会因为开发者疏忽而返回了别的租户的数据？**

答题思路：先指出最隐蔽的风险不是"完全没加过滤"，而是"看起来加了过滤，实际是查完全部数据再事后筛选"——这种方式的可靠性完全依赖过滤逻辑本身不出错，一旦某处遗漏就会静默失效。然后给出具体应对：用一个"不允许构造出‘不限定租户’状态"的类型（必填字段+构造时校验），把租户限定条件用字典合并的书写顺序确保不会被其他条件覆盖，并且在真正返回结果前加一道独立的核实断言，作为发现"底层过滤本身失效"的最后防线。这个回答体现的是"隔离的可靠性应该建立在结构性约束上，而不是靠人的细心"这个更深层的工程原则。
