# 第20章 —— 评判聚合与公平性

代码位置：`packages/ainative-eval/src/ainative_eval/judge_aggregation.py`、`packages/ainative-eval/src/ainative_eval/fairness.py`

## 一个真实场景：三个语言，一个"整体还不错"的假象

假设你的团队做了一个多语言AI助手，同时支持日语、中文、英语。上线前你们做了一轮质量评测，每种语言各测一遍核心功能体验，打出分数：日语0.95，中文0.92，英语0.76。

如果你直接把这三个分数取平均——(0.95 + 0.92 + 0.76) / 3 = 0.88——报告会说"整体质量评分0.88，表现良好，可以上线"。这个结论**对日语和中文用户是对的，但对英语用户是一句谎言**：他们实际拿到的体验只有0.76分那么好，平均出来的0.88分从来没有真实存在于任何一个具体用户的体验里。更麻烦的是，**如果平均分能掩盖短板，短板就永远没有动力被修复**——下一轮迭代大概率会继续优化已经做得不错的日语和中文（因为那样能让平均分继续好看），英语用户的体验可能被无限期地搁置。

这一章要讲的两个模块，都是在回答同一类问题的不同侧面：**当你手上有一组"多次独立评判/多个维度"的分数，应该怎么把它们聚合成一个能指导决策的判断，而不是简单粗暴地取平均**。`judge_aggregation.py`处理的是"同一件事被独立评判了好几次"（比如让LLM给同一个回复连续打3次分），`fairness.py`处理的是"同一件事在不同维度/人群上的表现"（比如同一个功能在三种语言上的体验）。两者面对的问题不同，用的聚合策略也不同——一个用中位数，一个用最小值——这一章会讲清楚为什么。

## `judge_aggregation.py`：中位数 + 分歧度

先看这个模块要解决的问题。如果你读过第14章，会记得`ainative_prompt.judge`里的`judge_response`函数，就用了"独立调用LLM好几次、取中位数、衡量分歧度"这一套手法。`judge_aggregation.py`模块的docstring说得很清楚，这里是把同一套统计聚合逻辑，从"怎么调用judge模型"这件事里剥离出来，做成一个**只关心"给定一组已经解析好的分数，怎么聚合成一个最终判定"的纯函数层**——不关心这些分数最初是怎么产生的。

这里有一个值得单独拎出来的架构决策，源码注释解释得很直白：`ainative_prompt.judge.judge_response`用的确实是同一套"中位数+极差判定分歧度"规则，但**它没有直接调用本模块的`aggregate_scores`，而是自己内联实现了一份一模一样的逻辑**。为什么明明是同一套算法，却要在两个包里各写一份，而不是让其中一个依赖另一个？因为项目的依赖关系设计里，`ainative-prompt`和`ainative-eval`都只依赖`ainative-core`，**两者之间刻意不产生相互依赖**。如果`judge_response`改成调用`ainative_eval.aggregate_scores`，就意味着`ainative-prompt`这个包多了一条指向`ainative-eval`的依赖边，这条边一旦建立，以后想要"只用ainative-prompt、不引入ainative-eval的其他内容（比如GDPR相关的模块）"就做不到了。这是一个值得记住的架构权衡：**有时候，为了保持包与包之间清晰、独立的依赖关系，宁可承受"同一套简单算法被复制一份"这种小规模的重复，也不去引入一条会让依赖关系变复杂的连接**。这不是"忘了去重"，而是刻意的取舍。

看数据结构：

```python
DEFAULT_HIGH_UNCERTAINTY_THRESHOLD = 0.4   # 分散度超过这个值就标记为"高度不确定"

# frozen=True——代表"一次聚合计算已经算完的结果快照"，算完就不应该
# 再被改动。
@dataclass(frozen=True)
class AggregatedJudgment:
    """一组独立评分聚合后的结果。"""

    score: float
    """中位数分数。"""

    score_range: float
    """最高分与最低分之差——分数分散程度的代理指标（不是统计学方差）。"""

    high_uncertainty: bool
    """`score_range`是否超过`high_uncertainty_threshold`。"""

    sample_size: int
    """参与聚合的有效分数个数。"""
```

`score_range`的docstring特意强调"是分散程度的代理指标，不是统计学方差"——这和第14章讲过的那个真实命名问题呼应：原来的实现曾经把这个值叫作"variance"，但实际计算的是`max - min`（极差），不是统计学意义上真正的方差（涉及平方和平均），这个版本里直接改名叫`score_range`，避免变量名和实际计算方式对不上误导后来的维护者。这里`AggregatedJudgment`用的是`@dataclass(frozen=True)`——代表"一次聚合计算已经算完的结果快照"，算完之后不应该再被谁悄悄改动，这和第18章`GateResult`选择不冻结的理由正好相反，也印证了上一章说的那个原则：**是否冻结取决于这个对象在生命周期里还需不需要被继续修改**。

再看聚合函数本身：

```python
def aggregate_scores(
    scores: list[float],
    *,
    high_uncertainty_threshold: float = DEFAULT_HIGH_UNCERTAINTY_THRESHOLD,
) -> AggregatedJudgment | None:
    if not scores:
        return None   # 一个分数都没有——没法聚合，诚实地返回None
    median_score = statistics.median(scores)   # 标准库现成的中位数计算
    # 只有多于1个分数时，谈"分散程度"才有意义；只有1个分数直接给0.0。
    score_range = (max(scores) - min(scores)) if len(scores) > 1 else 0.0
    return AggregatedJudgment(
        score=median_score,
        score_range=score_range,
        high_uncertainty=score_range > high_uncertainty_threshold,
        sample_size=len(scores),   # 参与这次聚合的分数一共有几个
    )
```

`statistics`是Python标准库自带的统计计算模块，`statistics.median`直接给出现成的中位数实现，不需要自己手写"排序后取中间值"的逻辑。选中位数而不是平均数的原因，第14章已经详细讲过：中位数对个别极端值不敏感——假设3次评分是0.8、0.85、0.1（最后一次可能是模型抽风），平均数会被那个0.1明显拉低，但中位数（0.8）更真实地反映"大多数评判意见其实是一致的"。

`len(scores) > 1 else 0.0`这个分支值得留意：只有一个分数的时候，谈"分散程度"没有意义（没有第二个数可以比较），直接给0.0，表示"完全没有分歧，因为压根只评了一次"，避免这种边界情况下的计算产生误导性的结果（比如对单元素列表调用`max() - min()`虽然不会报错，但"极差是0"这件事，跟"压根没有第二次评分可比"这件事，含义上是有微妙区别的，用一个显式分支把这个区别说清楚更严谨）。

`if not scores: return None`——空列表在Python里是"假值"，这里的意思是"一个分数都没有，就没法聚合，返回`None`表示'无法聚合'"，而不是硬凑一个看似合理的默认结果（比如返回0分）。这和`fairness.py`里遇到空输入时的处理方式形成了一个有意思的对比，我们接着往下看。

## `fairness.py`：为什么公平性判定要"取最弱"而不是"取平均"

回到开头那个日语/中文/英语的例子。`fairness.py`模块的docstring直接把这个道理写在了最前面：多维度的公平性评分，**如果简单取平均，某一个维度表现明显落后会被其他维度的高分掩盖，整体判定"看起来还不错"，但对那个维度对应的用户来说，体验是真实变差的**。正确做法是取所有维度里最弱的那一个作为整体判定依据，这样任何一个维度的短板都无法被平均分掩盖。

数据结构很简单：

```python
@dataclass(frozen=True)
class FairnessDimensionScore:
    """单个维度（比如某一种语言、某一类受保护特征）的公平性评分。"""

    dimension: str   # 这是哪个维度，比如"en"（英语）
    score: float
    """0-1之间的分数，1表示完全公平/无差异对待，0表示完全不公平。"""


@dataclass(frozen=True)
class FairnessResult:
    """跨维度聚合后的公平性判定结果。"""

    parity_min: float
    """所有维度里最低的分数——整体判定以这个值为准，而不是平均分。"""

    weakest_dimension: str
    """得分最低的具体维度名称——供后续排查/改进优先定位到具体是哪个维度。"""

    dimension_scores: dict[str, float]   # 每个维度各自的原始分数，便于查阅明细
```

`parity_min`这个字段名本身就是设计意图的直接体现——"parity"（对等性）"min"（取最小值），命名已经把"这是取最小值，不是平均值"这件事说清楚了。而`weakest_dimension`这个字段同样值得注意：**它不只是给出一个笼统的分数，还明确指出"具体是哪个维度拖了后腿"**。回到开头的例子，如果报告只说"整体公平性评分0.76"，团队知道分数不够好，但不知道该优先改哪里；如果报告说"整体评分0.76，最弱维度是英语"，团队能立刻知道该把资源投向哪里。**这是聚合类函数设计上一个常被忽略的细节：聚合出一个总分只完成了一半的工作，指出"是谁导致了这个总分"往往和总分本身同样重要，甚至更重要**——因为总分只能告诉你"好不好"，具体的短板维度才能告诉你"接下来该做什么"。

聚合函数本身：

```python
def evaluate_fairness(scores: list[FairnessDimensionScore]) -> FairnessResult:
    if not scores:
        # 没有任何维度数据——这通常意味着调用方代码本身有问题，
        # 主动抛异常，而不是悄悄返回一个没有意义的结果。
        raise ValueError("evaluate_fairness requires at least one dimension score")

    # min(序列, key=...)——key指定"按对象的哪个值来比较大小"；
    # 这里按每个FairnessDimensionScore的score字段找出最小的那个。
    weakest = min(scores, key=lambda s: s.score)
    return FairnessResult(
        parity_min=weakest.score,
        weakest_dimension=weakest.dimension,
        # 字典推导式：把scores列表转换成{维度名: 分数}这样的字典，
        # 方便调用方按维度名直接查具体分数。
        dimension_scores={s.dimension: s.score for s in scores},
    )
```

这里`min(scores, key=lambda s: s.score)`用到了`min()`的`key`参数——`scores`列表里装的是`FairnessDimensionScore`对象而不是裸数字，Python不知道该按对象的哪个字段比较大小，所以要传入`key=`：一个"输入一个元素、返回用来比较大小的那个值"的函数。`lambda s: s.score`是一个匿名小函数的写法，不用`def`单独定义一个有名字的函数，直接内联写"输入`s`，返回`s.score`"这一行逻辑，适合这种只用一次、逻辑很简单的场合。`min()`最终返回的就是`scores`里`.score`字段值最小的那个对象——也就是表现最弱的那个维度，这正是这个模块"取最弱维度而非平均"这个核心设计决策的具体落地。

再看空输入的处理——`if not scores: raise ValueError(...)`，这里选择**主动抛出异常，而不是像`aggregate_scores`那样返回`None`**。源码注释解释了原因："没有任何维度数据时，宁可让调用方明确看到报错，也不要悄悄返回一个看似正常、实际毫无意义的结果"。这里可以对比着体会两个模块面对"空输入"时不同的选择：`aggregate_scores`返回`None`，是因为"多次独立评判有可能全部解析失败，一次都拿不到有效分数"是一种在实际运行中完全正常、可以预见的情况，调用方需要能优雅地处理这种情况（判断一下`is None`就好）；而`evaluate_fairness`选择抛异常，是因为"完全没有任何一个维度的公平性数据"通常意味着调用方的代码本身有问题（忘了传参数、上游数据收集环节漏了什么），这种情况更适合让程序尽早、大声地报错，而不是悄悄返回一个用户根本不知道该怎么解读的空结果。**同样是"空输入"，选择返回`None`还是抛异常，取决于这种情况在真实运行中是"正常但需要优雅处理的边界情况"，还是"本不应该发生、发生了就说明有bug"——这是设计函数错误处理策略时值得反复问自己的问题**。

## 附带的公平性检测工具：`detect_stereotype_skew`与`has_dominant_skew`

`fairness.py`里还有两个配套的小工具，用来检测另一类公平性问题——AI生成内容里是否夹带了刻板印象。模块docstring解释了为什么需要它：**生成内容的刻板印象问题，必须观察一批生成结果的整体分布，单条内容判断不出来**。比如让AI生成100个"典型工程师"的用户画像，如果单看其中一条，很难说这是不是刻板印象；但如果这100条里有90条的性别都设定成同一种，这个分布本身就说明了问题。

```python
def detect_stereotype_skew(
    generated_samples: list[dict[str, str]], *, attribute_key: str, max_dominant_share: float = 0.7,
) -> dict[str, float]:
    if not generated_samples:
        return {}   # 没有任何样本，返回空字典表示"无从判断分布"
    # 列表推导式：从每条样本里取出attribute_key对应的值，取不到就用空字符串。
    values = [sample.get(attribute_key, "") for sample in generated_samples]
    total = len(values)   # 样本总数，用来后面算占比
    distribution: dict[str, float] = {}   # 记录每种取值各出现了多少次
    for value in values:
        # .get(value, 0.0) + 1.0——第一次遇到这个取值时当作0次，然后加1；
        # 之后每再遇到一次同样的取值，都在已有计数上继续加1。
        distribution[value] = distribution.get(value, 0.0) + 1.0
    # 字典推导式：把"出现次数"换算成"占总数的比例"。
    return {value: count / total for value, count in distribution.items()}
```

`[sample.get(attribute_key, "") for sample in generated_samples]`是一个列表推导式——用一行代码从一个列表构造出另一个列表的写法，等价于写一个`for`循环，对每一条生成结果取出它在`attribute_key`这个字段上的值（读不到就当作空字符串）。`distribution.get(value, 0.0) + 1.0`是"用字典给每种取值计数"的标准写法——第一次遇到某个取值时读不到就当作0.0，然后加1，效果上等同于给每种不同的取值各开一个独立的计数器。最后`{value: count / total for value, count in distribution.items()}`又是一个字典推导式，把每种取值的出现次数换算成占比。

```python
def has_dominant_skew(distribution: dict[str, float], *, max_dominant_share: float = 0.7) -> bool:
    # bool(distribution)——先判断这个字典是不是非空；只有非空时才
    # 继续往后走max(...)比较，避免对空字典调用max()直接崩溃报错。
    return bool(distribution) and max(distribution.values()) > max_dominant_share
```

这一行`bool(distribution) and ...`值得留意：先确认分布字典非空，再取`max(distribution.values())`跟阈值比较。为什么要先判断非空？因为`max()`对空序列直接调用会抛出异常——如果`generated_samples`本身是空列表，`detect_stereotype_skew`会返回空字典`{}`，如果不做`bool(distribution)`这层前置判断就直接调用`max(distribution.values())`，会在"压根没有生成任何样本"这种边界情况下让程序意外崩溃，而不是干净地返回"不存在偏斜"（`False`）这个更合理的答案。这是防御性编程里一个很典型的小细节：**在对一个可能为空的容器调用`max()`/`min()`之前，先显式检查它是否为空**。

## 本章小结

- 面对"多个独立评判"和"多个维度"这两类看似相似、实际目的不同的聚合场景，要用不同的聚合策略：多次独立评判同一件事，用中位数抵御个别极端值（噪声）；多个维度衡量不同群体的体验，取最弱维度（`parity_min`）防止短板被平均分掩盖。
- 简单取平均在"多维度公平性"场景下是危险的：它会让整体判断"看起来还不错"，但对表现最差的那个维度对应的用户来说，体验是真实存在的，不会因为别的维度分数高就自动变好。
- 聚合出一个总分只完成了一半工作——指出"是哪个具体维度拖了后腿"（`weakest_dimension`）往往和总分本身同样重要，因为它直接指向了下一步该优先改进什么。
- 两个模块面对"空输入"选择了不同的处理方式（返回`None` vs 抛`ValueError`），取决于这种情况在真实场景里是"正常但需要优雅处理"还是"本不应该发生、发生了就该尽早报错"——这是设计任何聚合/统计函数时都值得考虑的问题。
- 有时候为了保持包与包之间清晰、独立的依赖关系，宁可让同一套简单算法在两个包里各实现一份，也不引入一条会让依赖图变复杂的连接——这不是重复劳动的疏忽，而是刻意的架构取舍。

## 动手做

```python
from ainative_eval import aggregate_scores, FairnessDimensionScore, evaluate_fairness, detect_stereotype_skew, has_dominant_skew

# 场景1：同一个回复独立评了3次分，意见比较一致
judged = aggregate_scores([0.82, 0.79, 0.90])
print(judged)  # score是中位数，high_uncertainty应该是False

# 场景2：3次评分意见分歧很大
judged_noisy = aggregate_scores([0.9, 0.5, 0.1])
print(judged_noisy)  # high_uncertainty应该是True

# 场景3：跨语言公平性 —— 取最弱维度而不是平均分
fairness_result = evaluate_fairness([
    FairnessDimensionScore(dimension="ja", score=0.95),
    FairnessDimensionScore(dimension="zh", score=0.92),
    FairnessDimensionScore(dimension="en", score=0.76),
])
print(fairness_result.parity_min, fairness_result.weakest_dimension)  # 0.76 "en"

# 场景4：检测AI生成的用户画像里，性别分布是否严重失衡
# [{"gender": "male"} for _ in range(8)]——列表推导式，重复生成8个
# 一模一样的字典，_表示"这个循环变量本身不重要，不需要用到它的值"。
samples = [{"gender": "male"} for _ in range(8)] + [{"gender": "female"} for _ in range(2)]
distribution = detect_stereotype_skew(samples, attribute_key="gender")
print(distribution)
print(has_dominant_skew(distribution))  # 80% male，超过默认阈值0.7，应该是True
```

试着把场景3里`en`的分数改成0.99，观察`parity_min`和`weakest_dimension`怎么变化——再试着算一下如果用平均分，这份报告会给出一个什么样具有误导性的"整体印象"。

## 面试可能会问

**问：如果要评估一个AI产品在不同语言/不同用户群体上的公平性表现，你会怎么把多个维度的评分聚合成一个整体结论？**

答题思路：直接指出"简单取平均"是这里最大的陷阱——举一个具体例子（比如日语0.95、中文0.92、英语0.76，平均下来0.88看起来不错，但英语用户的真实体验只有0.76），说明平均分会让某个维度的短板被其他维度的高分掩盖，而这个短板对应的是真实存在、体验真实变差的一群用户。然后讲正确做法：取所有维度里最弱的那个（`parity_min`）作为整体判定依据，同时明确记录是哪个维度最弱（`weakest_dimension`），因为总分只能告诉你"好不好"，具体维度才能告诉你"下一步该改哪里"。如果能进一步对比"多次独立评判同一件事应该用中位数（抵御随机噪声），多个不同维度应该取最弱值（防止真实短板被平均）——这是两种目的完全不同的聚合场景，不能用同一套规则"，会显示出你不只是记住了两个函数,而是理解了它们各自解决的问题本质不同。
