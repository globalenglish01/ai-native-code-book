# 第16章 —— 输出安全扫描

代码位置：`packages/ainative-security/src/ainative_security/output_safety.py`

## 攻击面比你想象的更大

当我们说"要检查AI的输出有没有安全问题"时，大部分人第一反应是"检查文本里有没有出现API密钥"。这确实是`output_safety.py`要做的一部分，但这个模块真正有意思的地方，在于它揭示了一整套"攻击者会怎么绕过你的检测"的思路——本章重点讲三种绕过手法，以及这个框架怎么一层层堵住它们。

## 第一层：明文正则——最基础，也最容易被绕过

最直接的检测方式是用正则表达式匹配已知的威胁模式，比如密钥格式：

```python
# 每一行是一个(规则名, 编译好的正则)元组，攒成一份规则列表。
# (?i)——不区分大小写；\s*[:=]\s*——冒号或等号前后允许有空格。
("api_key", re.compile(r'(?i)(api[_\-]?key|apikey)\s*[:=]\s*["\']?([A-Za-z0-9_\-]{20,})["\']?')),
# AKIA/ASIA开头+16位大写字母数字，是AWS密钥的固定格式。
("aws_key", re.compile(r'(?i)((?:AKIA|ASIA)[0-9A-Z]{16})')),
("private_key", re.compile(r'-----BEGIN (?:RSA |EC |OPENSSH |DSA )?PRIVATE KEY-----')),
```

或者提示注入的经典句式：

```python
# 一段正则被拆成两个相邻的字符串字面量写在两行——Python会自动把
# 紧挨着的字符串字面量拼接成一个整体，纯粹是为了让长正则更易读。
("ignore_instr", re.compile(
    r'(?i)(?:ignore|disregard|forget)\s+(?:all\s+|everything\s+)?'
    r'(?:(?:previous|prior|above)\s+instructions?|above\b...)'
)),
```

这一层能拦住绝大多数"直来直去"的攻击——但攻击者知道有这层检测存在时，会想办法让攻击文本"看起来不像"能被正则匹配到的样子。

## 第二层：绕过手法1——零宽字符

想象攻击者写了这样一句话："ig​nore previous instructions"——中间那个看起来像空格的地方，其实插入了一个**零宽字符**（Unicode里一类"本身不显示、不占宽度"的特殊字符）。人眼看上去这句话和"ignore previous instructions"一模一样，但对逐字符比较的正则表达式来说，"ig"和"nore"之间多了一个它完全不认识的字符，导致原本能匹配"ignore"的规则彻底失效。

`ainative-security`用归一化来应对：

```python
# 这个正则字符类里的内容，是几段Unicode里的"零宽/双向控制字符"
# 范围（它们在这里显示出来几乎不可见，正是它们的特性）。
_ZERO_WIDTH_RE = re.compile('[​-‏‪-‮⁠-﻿]')

def _normalize_for_scan(text: str) -> str:
    stripped = _ZERO_WIDTH_RE.sub("", text)   # 把所有零宽字符替换成空字符串，相当于删掉
    # unicodedata.normalize("NFKC", ...)——Unicode标准库提供的标准化
    # 函数，NFKC这种模式会把"兼容写法"折叠成标准写法（比如全角Ａ折叠成半角A）。
    return unicodedata.normalize("NFKC", stripped)
```

先用一个专门的正则把所有已知的零宽/双向控制字符替换成空字符串（相当于删掉它们），再用`unicodedata.normalize("NFKC", ...)`做Unicode标准化（比如把全角字母折叠成半角字母）。

## 第三层：绕过手法2——同形字，NFKC也救不了

另一种绕过手法更隐蔽：用**长得几乎一模一样、但Unicode编码完全不同**的字符替换关键词里的字母，比如用西里尔字母"о"（U+043E）替换拉丁字母"o"（U+006F）——"ignоre"这个词，人眼完全看不出区别，但对程序来说是两个完全不同的字符序列。

**这里有一个容易被误解的地方：NFKC归一化并不能解决这个问题**。docstring里特别强调了这一点——NFKC只处理"Unicode标准里认定为等价"的写法（比如全角转半角），西里尔字母和拉丁字母在Unicode标准里根本不被视为等价，只是"长得像"而已，NFKC对此无能为力。这个框架专门用`confusables.py`模块维护一份"形近字折叠表"，把西里尔/希腊形近字手动映射回对应的拉丁字母。

## 关键教训：单独一层处理不够，必须组合

这一章最值得记住的一处设计，是`_scan_text`函数的docstring里说明的一件事：

> 归一化和同形字折叠各自独立作用于原始`text`是不够的——一个在同形字token中间插入零宽字符的payload（比如"ign​оre"，о是西里尔字母，中间夹着零宽空格），归一化能去掉零宽字符但不折叠西里尔字符，折叠能处理西里尔字符但不去掉零宽字符，两路各自都命中不了完整的注入短语。

也就是说，攻击者可以**同时使用两种绕过手法**：一部分字母换成同形字，中间再插入零宽字符。如果你的检测流程是"分别做归一化扫一遍、分别做同形字折叠扫一遍"，两次扫描各自都因为"还残留着另一种绕过手法的痕迹"而无法完整匹配到关键词。真正的解法是**组合**：

```python
# 在"已经归一化过（去掉零宽字符）"的文本基础上，再做一次同形字折叠——
# 顺序很关键：先去零宽字符，再折叠同形字，两种绕过手法的痕迹才能
# 同时被清除。
normalized_and_folded = fold_confusables(normalized)
# 只有这次组合处理的结果，跟单独归一化、单独折叠的结果都不一样时，
# 才说明它确实"发现了新东西"，值得作为一个独立的扫描候选加进去。
if normalized_and_folded != normalized and normalized_and_folded != folded:
    _merge(normalized_and_folded, "norm+cfold")
```

先归一化（去掉零宽字符），**在归一化的结果之上**再做同形字折叠——这样两种绕过手法造成的痕迹才能被同时清除，还原出完整可匹配的文本。这一节的教训值得记住：**当你的系统需要应对多种独立的绕过/干扰手法时，不能想当然地认为"分别处理每一种就够了"——攻击者会组合使用它们，你的防御也必须考虑组合场景，而不只是每种手法各自单独出现的场景**。

## 第四层：编码绕过——解码之后再扫一遍

还有一种更直接的绕过方式：把攻击文本整段做Base64/URL/十六进制编码，让它在明文层面完全看不出任何威胁模式的痕迹。这个模块会主动识别"看起来像编码内容"的文本片段，解码后再扫一遍：

```python
def _decode_layers(text: str) -> list[str]:
    variants: list[str] = []   # 收集所有"解码出来、值得进一步扫描"的候选文本
    if "%" in text:   # 文本里出现了%，可能是URL编码（比如%20代表空格）
        dec = urllib.parse.unquote(text)   # 尝试做URL解码
        if dec and dec != text:   # 解码出了东西、且和原文确实不一样
            variants.append(dec[:_MAX_VARIANT_LEN])   # 截断到最大长度，避免过长文本拖慢后续扫描

    # _B64_BLOB_RE.findall(text)——正则找出所有"看起来像Base64编码"的
    # 片段；[:_MAX_DECODE_CANDIDATES]——只取前N个候选，避免逐个尝试
    # 解码耗费太多计算资源。
    for blob in _B64_BLOB_RE.findall(text)[:_MAX_DECODE_CANDIDATES]:
        # "=" * (-len(blob) % 4)——Base64要求长度是4的倍数，不够的话
        # 需要补齐等号；这个表达式算出恰好需要补几个等号。
        raw = base64.b64decode(blob + "=" * (-len(blob) % 4), validate=False)
        # errors="ignore"——遇到解不出来的字节直接跳过，不因为个别
        # 字节解码失败就让整个函数报错崩溃。
        dec = raw.decode("utf-8", errors="ignore")
        if dec and _printable_ratio(dec) >= 0.8:   # 可打印字符占比够高才认为解码有意义
            variants.append(dec[:_MAX_VARIANT_LEN])
    ...
    return variants
```

这里有个值得学的细节——`_printable_ratio`函数：

```python
def _printable_ratio(s: str) -> float:
    if not s:
        return 0.0   # 空字符串，占比没有意义，直接给0
    # sum(1 for c in s if 条件)——生成器表达式：遍历字符串里每个字符c，
    # 满足条件就贡献1，sum把所有贡献的1加起来，等于"满足条件的字符总数"。
    # c.isprintable()——判断这个字符是不是"人类可读的可打印字符"；
    # 额外允许换行/回车/制表符这几个"虽然不算可打印、但确实是正常文本"的字符。
    ok = sum(1 for c in s if c.isprintable() or c in "\n\r\t")
    return ok / len(s)   # 满足条件的字符数 除以 总字符数，得到占比
```

为什么解码之后不能直接拿去扫描，还要先检查"可打印字符占比"？因为很多看起来"像"Base64编码的文本，其实只是碰巧符合Base64的字符集规则（大小写字母+数字+少量符号），本身根本不是真正的编码内容——比如一个普通的session ID或哈希值。强行把这类文本硬解码，得到的往往是一堆毫无意义的二进制乱码。**只有解码后大部分字符都是"人类可读"的（占比达到80%），才认为这次解码"解出了真正有意义的内容"，值得继续拿去扫描**——否则会产生大量误报，把正常业务数据误判成"编码后的攻击载荷"。

这里也留意到一处曾经真实存在的容量问题：`_MAX_DECODE_CANDIDATES`这个上限，最初设成12，后来发现真实日志/工具输出里经常同时出现几十个"看起来像Base64"的片段（大多是session ID、哈希值这类正常数据），如果真正藏着密钥的那一段恰好排在候选列表的第13位之后，会直接被这个过低的上限挡在外面、完全没有机会被解码检测——这是又一个"过于保守的资源限制，反而造成了真实的漏检"的例子，后来被调高到64。

## 本章小结

- 安全扫描需要面对多种绕过手法：零宽字符插入、同形字替换、编码混淆——每一种都需要专门的应对措施。
- NFKC归一化不能解决同形字问题（西里尔/希腊字母在Unicode标准里不被视为和拉丁字母等价），需要专门的折叠表。
- 攻击者会组合使用多种绕过手法，防御措施也必须按组合场景设计（先归一化去零宽字符，再对归一化结果做同形字折叠），不能假设每种手法只会单独出现。
- 编码绕过的检测要配合"可打印字符占比"这类启发式判断，避免把正常的、恰好符合编码字符集的业务数据（如session ID）误判为攻击载荷；同时要留意"候选数量上限"这类资源限制，设得太低会造成真实的漏检。

## 面试可能会问

**问：如果你要设计一套检测提示注入攻击的系统，你会考虑哪些绕过手法？**

答题思路：不要只讲"用正则匹配关键词"，要主动提到攻击者会用零宽字符打断关键词、用同形字替换字母、用编码混淆整段文本这几类常见绕过手法，并说明各自需要的应对措施（去除零宽字符、同形字折叠、解码后重新扫描）。如果能补充"这些手法可能被组合使用，防御也需要按组合场景设计，不能只按单一手法各自应对"，会显著体现你的思考深度超出了"背了几个安全术语"的层面。
