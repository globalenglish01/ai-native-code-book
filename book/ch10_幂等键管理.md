# 第10章 —— 幂等键管理

代码位置：`packages/ainative-guardrail/src/ainative_guardrail/idempotency.py`

## 一个每个人都遇到过的用户体验问题

你在一个购物网站点"确认支付"，页面卡了几秒钟，你以为没点中，又点了一次——如果系统设计得不好，你可能会被扣两次钱。这就是"幂等性"要解决的问题：**同一个操作被意外重复提交时，效果应该和只提交一次完全一样，而不是被重复执行**。

在Agent系统里，这个问题同样存在，甚至更容易发生——因为Agent经常会在网络抖动、超时之后自动重试某个操作，如果这个操作本身有副作用（发邮件、扣款、创建工单），"自动重试"和"被扣两次钱"之间只差一个幂等键的距离。

## 核心数据结构：状态，而不只是"存在与否"

一个常见但不够好的实现思路是："检查这个操作的ID是否已经处理过，处理过就跳过"。`ainative-guardrail`的设计比这更进一步——**区分"正在处理中"和"已经有最终结果"这两种状态**：

```python
# StrEnum——Python标准库的"字符串枚举"，每个成员既是一个独立的常量
# （比如IdempotencyStatus.COMPLETED），本身又表现得像一个字符串。
class IdempotencyStatus(StrEnum):
    IN_PROGRESS = "in_progress"   # 这个操作正在执行中，还没有最终结果
    COMPLETED = "completed"       # 这个操作已经跑完，有确定的结果了
```

为什么这个区分很重要？想象一个请求正在处理中（比如正在真的调用支付网关，还没等到网关返回结果），这时候客户端因为超时又发了一次重试请求——**这次重试应该被告知"请稍后再试"，而不是直接返回一个还不存在的结果**。等到第一次请求真正处理完成、状态变成`COMPLETED`之后，后续的重复请求才应该直接拿到已经算好的结果，而不是重新执行一遍扣款。

## 竞态条件：为什么"检查+写入"必须是一步

`occupy()`方法的docstring里强调了一件容易被忽略的事：

> "占用幂等键"必须一步到位完成，避免两个几乎同时到达的请求都误以为自己是第一个。

想象一个反例：如果占用逻辑写成两步——"先查询这个键是否存在"，再"如果不存在就写入"——两个几乎同时到达的重复请求，都可能在"查询"这一步得到"不存在"的结果（因为第一个请求的"写入"还没来得及真正完成，第二个请求就已经查询过了），于是两个请求都误以为自己是第一个，都真的去执行了一次扣款。这就是经典的"竞态条件"（race condition）：两个操作的执行顺序如果交错，会导致本该互斥的逻辑被同时满足。

在内存版实现里，这个"一步到位"是靠Python字典单次赋值天然的不可分割性来保证的：

```python
def occupy(self, key: str, *, ttl_seconds: int) -> IdempotencyRecord | None:
    existing = self._records.get(key)   # 查一下这个key之前有没有被占用过
    now = time.time()   # 当前时间戳（秒）
    # 既要"确实存在这条记录"，又要"这条记录还没过期"，两个条件都满足
    # 才算"目前真的被占用着"。
    if existing is not None and existing.expires_at > now:
        return existing   # 已被占用，返回既有记录
    # 走到这里说明可以占用——用一次字典赋值直接写入新记录，
    # 这一步在单进程内是"不可分割"的，不会被其他请求打断。
    self._records[key] = IdempotencyRecord(status=IdempotencyStatus.IN_PROGRESS, expires_at=now + ttl_seconds)
    return None   # 占用成功
```

这里的docstring特别提醒——**如果真实项目要换成Redis实现，必须用`SET key value NX EX ttl`这种"一步到位"的原子命令**，不能自己拆成"先`GET`查询、再`SET`写入"两条命令去实现，否则并发场景下同样会出现竞态条件。这是一个很重要的迁移提示：内存版实现之所以"恰好"是安全的，是因为单进程内的字典操作不会被别的线程打断；换成分布式存储时，这个"恰好安全"的假设不再成立，必须显式选择支持原子操作的命令。

## 失败必须释放，否则用户被"锁"一整个TTL窗口

`idempotent_operation`这个上下文管理器，把"失败时必须释放幂等键"这条规则做成了默认行为：

```python
# @contextmanager——把下面这个生成器函数改造成能配合with语句使用的
# "上下文管理器"，yield前后分别对应"进入with块"和"离开with块"两个时机。
@contextmanager
def idempotent_operation(store, key, *, ttl_seconds=DEFAULT_TTL_SECONDS):
    existing = store.occupy(key, ttl_seconds=ttl_seconds)   # 尝试占用这个幂等键
    if existing is not None:
        # 占用失败，说明已经有一份记录存在——直接抛异常，
        # 把这份既有记录一起带出去，让调用方能读到具体状态。
        raise DuplicateOperationError(key, existing)
    try:
        yield   # 把控制权交给with块内的业务代码（比如真正的扣款逻辑）
    except BaseException:
        # 只要业务代码执行过程中出现任何形式的中断，都要释放幂等键。
        store.release(key)
        raise   # 不带参数的raise——原样重新抛出刚才捕获到的异常
```

用法是这样的：

```python
try:
    # with语句进入这个上下文管理器——如果幂等键已经被占用，
    # 会在这一行直接抛出DuplicateOperationError。
    with idempotent_operation(store, "charge:order-42"):
        charge_credit_card(...)   # 真正的扣款逻辑，只有占用成功才会走到这里
except DuplicateOperationError as exc:
    # exc.record是那份"既有记录"，可以读出它当前的状态。
    if exc.record.status is IdempotencyStatus.COMPLETED:
        return exc.record.result   # 直接复用之前的结果，不重复扣款
    return "please retry shortly"  # 仍在处理中
```

如果`with`块内的`charge_credit_card(...)`执行到一半抛出了异常（比如支付网关连接失败），`except BaseException:`会捕获住它，调用`store.release(key)`把幂等键释放掉，再用`raise`（不带参数）把原始异常原样重新抛出。**为什么要故意捕获最宽泛的`BaseException`（而不是更常见的`Exception`）？** 因为"只要发生了任何形式的中断，都必须释放幂等键"这条规则不允许有例外——如果只捕获`Exception`，某些更罕见的中断类型（比如`KeyboardInterrupt`）就会绕过释放逻辑，导致幂等键卡在`IN_PROGRESS`状态直到TTL过期，用户在这整个窗口期内都没法重新提交同一个操作，即使故障早就恢复了。

## 本章小结

- 幂等性要区分"正在处理中"和"已有最终结果"两种状态，而不只是简单地判断"处理过没有"。
- "检查是否可以占用+真正占用"必须是原子的一步操作，否则并发场景下会出现竞态条件；内存版实现的"天然原子性"来自单进程字典赋值，迁移到Redis等分布式存储时必须显式选用原子命令（如`SET NX`）。
- 处理失败时必须释放幂等键，否则用户会被锁在TTL窗口期内动弹不得——用`try/except BaseException`加`store.release()`把这条规则做成默认行为，而不是指望每个调用方自己记得写。

## 动手做

```python
from ainative_guardrail.idempotency import InMemoryIdempotencyStore, idempotent_operation, DuplicateOperationError, IdempotencyStatus

store = InMemoryIdempotencyStore()   # 内存版的幂等记录存储，方便demo/测试

def try_charge(order_id: str):
    try:
        # f"charge:{order_id}"——用订单ID拼出一个独一无二的幂等键字符串。
        with idempotent_operation(store, f"charge:{order_id}"):
            print(f"真的在扣款：{order_id}")
            # 处理完成后，把这个键的状态标记为COMPLETED，并存下结果。
            store.complete(f"charge:{order_id}", result={"status": "ok"}, ttl_seconds=3600)
    except DuplicateOperationError as exc:
        print("重复请求，状态：", exc.record.status)

try_charge("order-1")
try_charge("order-1")   # 第二次应该走DuplicateOperationError分支
```

## 面试可能会问

**问：如果客户端重试一个下单/支付请求，你怎么保证不会被重复处理？**

答题思路：讲清楚"幂等键"的核心机制——用一个唯一标识（比如订单ID）去"占用"一个操作槽位，占用本身必须是原子操作以避免竞态条件；再强调要区分"正在处理中"和"已完成"两种状态，分别给客户端不同的响应（稍后重试 vs 直接返回缓存结果）；最后提到失败时必须释放幂等键，避免用户被无意义地锁住一整个TTL窗口。如果能提到"从内存实现迁移到Redis时，必须换成原子命令而不是拆成两步"，说明你真正理解了并发安全的本质，而不是记住了一个流程。
