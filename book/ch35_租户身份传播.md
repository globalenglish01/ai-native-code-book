# 第35章 —— 租户身份传播

代码位置：`packages/ainative-tenancy/src/ainative_tenancy/context.py`

## 一个真实发生过的多租户事故

如果你的SaaS产品服务多个公司客户（"租户"），最核心的安全承诺就是"A公司永远看不到B公司的数据"。这句话说起来容易，真实系统里怎么保证它？很多团队会用数据库层面的"行级安全"（Row-Level Security，RLS）机制——给每张表加一条规则："只返回当前会话变量里指定的租户ID对应的行"。

模块docstring里记录了一次真实发生过的事故背景：**RLS策略本身定义得完全正确，但运行时真正激活这条策略所需要的"会话变量"，从未被设置过**——策略写对了，却像一把没被挂上门的锁，形同虚设、完全没有生效。这提醒我们一个容易被忽视的道理：**"隔离规则被正确定义"和"隔离规则在运行时真的生效"是两件不同的事**，中间缺的这一环——"当前请求到底是哪个租户"这个信息，必须被可靠地、显式地传播到每一处需要它的代码，而不能假设"反正规则写好了就一定会起作用"。

## `contextvars`：一种"按调用链隔离"的全局变量

这一章的核心工具是Python标准库的`contextvars`模块。理解它，最好先理解它要解决的问题：假设你的Web服务同时处理来自租户A和租户B的两个并发请求，如果"当前是哪个租户"存在一个普通的全局变量里，两个请求几乎必然会互相污染——请求A设置的值，可能被请求B的代码读到，因为它们运行在同一个进程里，共享着同一份全局变量。

`ContextVar`是解决这个问题的专用工具：

```python
_current_tenant: ContextVar[TenantIdentity | None] = ContextVar("ainative_tenancy_current_tenant", default=None)
```

它的值是"按当前执行上下文隔离"的——可以粗略理解成"按每一条独立的调用链隔离"：请求A设置的租户身份，只在请求A自己的整条调用链里可见，不会被并发运行的请求B看到，即使两者跑在同一个进程里。这正是"多个请求共享同一个进程，但各自的身份信息互不干扰"这个需求的标准解法。

## `tenant_scope`：作用域必须有明确的边界

```python
@contextmanager
def tenant_scope(tenant_id: str) -> Iterator[TenantIdentity]:
    identity = TenantIdentity(tenant_id=tenant_id)
    token: Token = _current_tenant.set(identity)
    try:
        yield identity
    finally:
        _current_tenant.reset(token)
```

用法是`with tenant_scope("tenant-42"): handle_request()`——进入`with`块时，把当前上下文的租户身份设置好；`try/finally`保证不管块内代码是正常执行完，还是中途抛出了异常，`finally`里的`reset(token)`都一定会被执行到。这里用的是`reset(token)`，而不是简单粗暴的"设成`None`"——`Token`是调用`.set()`时返回的一个"回执"，`reset(token)`能**精确地**恢复成"调用`.set()`之前"的那个值，这样才能正确支持"嵌套"的`tenant_scope`（比如一个系统级后台任务，需要临时代入某个租户身份执行一次操作，执行完之后要准确恢复到外层原本的状态，而不是被意外清空）。

## 一个容易被忽略的边界：`asyncio.create_task`

这一章最值得记住的一处细节，藏在`tenant_scope`的docstring里：

> `contextvars`的传播是"创建时拷贝"语义——在`tenant_scope()`作用域内`asyncio.create_task()`派生出的后台任务，会拷贝一份创建时刻的租户身份快照，即使父作用域后续退出、`_current_tenant`已经`reset`，这个已经在运行的后台任务也**不会**感知到这次reset，会在自己的整个生命周期里继续沿用创建时刻那个租户身份。

这不是bug，而是`contextvars`本身的标准行为——但它意味着一个真实的风险：**如果你在处理请求A时，创建了一个"生命周期可能比这次请求本身更长"的后台任务（比如一个异步的清理作业），这个任务会永远带着"创建它那一刻"的租户身份运行，即使外层请求早就处理完、退出了`tenant_scope`**。文档明确指出应对方式：这类任务必须在自己的任务体内部**重新显式**调用一次`tenant_scope(...)`来锚定正确的租户身份，不能依赖"我是在某个`tenant_scope`内被创建的，所以租户身份一定是对的"这种隐式假设——因为这个假设在"任务比创建它的请求活得更久"的场景下并不成立。

## 断言而不是返回值：把"忘记检查"从可能性中消除

```python
def get_current_tenant() -> TenantIdentity:
    identity = _current_tenant.get()
    if identity is None:
        raise NoActiveTenantError(...)
    return identity

def assert_tenant_authorized(resource_tenant_id: str) -> None:
    current = get_current_tenant()
    if current.tenant_id != resource_tenant_id:
        raise TenantAuthorizationError(...)
```

留意这里的设计选择：`get_current_tenant()`在没有租户上下文时**直接抛异常**，而不是返回`None`让调用方自己判断"是不是拿到了`None`，要不要处理这种情况"。`assert_tenant_authorized`同样是"断言失败就抛异常"，而不是"返回一个`True`/`False`让调用方自己决定要不要往下走"。

为什么这个选择很重要？如果设计成"返回布尔值"，调用方完全有可能因为疏忽——**忘记检查这个返回值**——就继续往下执行，一次本该被拦截的越权访问就这样被无声地放行了。而设计成"断言失败直接抛异常"，这类疏漏会在开发/测试阶段就直接暴露成一个真正的报错，而不是悄悄潜伏到生产环境才被发现。**当一件事关乎安全隔离这类不能有任何侥幸的场景时，选择"不这样做就会直接报错"的设计，比选择"给调用方一个信号、指望它一定会正确处理"的设计更可靠**——这是一个值得记住的通用原则，本书前面第10章讲幂等键管理时，`DuplicateOperationError`直接抛异常也是同样的思路。

## 本章小结

- "隔离规则被正确定义"和"隔离规则在运行时真正生效"是两件不同的事——本章开篇的真实事故里，RLS策略写对了，却因为激活它所需的运行时信息从未被设置，导致隔离形同虚设。
- `ContextVar`能让"当前租户身份"这类信息按调用链隔离传播，不需要每层函数签名都显式传递`tenant_id`参数，也不会被并发的其他请求意外污染。
- `tenant_scope`用`try/finally`+`Token.reset()`保证作用域退出时精确恢复原状，支持嵌套场景。
- `asyncio.create_task`创建的后台任务是"创建时拷贝"租户身份快照，不会跟随父作用域的后续变化——生命周期可能超出父请求的任务，必须自己重新显式声明租户身份。
- 涉及安全隔离的判断应该设计成"不满足就直接抛异常"，而不是"返回布尔值让调用方自己记得检查"——后者容易因疏忽而被静默绕过。

## 动手做

```python
from ainative_tenancy.context import tenant_scope, get_current_tenant, assert_tenant_authorized, NoActiveTenantError, TenantAuthorizationError

try:
    get_current_tenant()
except NoActiveTenantError as exc:
    print("作用域之外调用，正确拒绝：", exc)

with tenant_scope("tenant-a"):
    print(get_current_tenant())
    try:
        assert_tenant_authorized("tenant-b")   # 尝试访问别的租户的资源
    except TenantAuthorizationError as exc:
        print("越权访问被拦截：", exc)
```

## 面试可能会问

**问：在一个多租户系统里，你会怎么保证"当前请求属于哪个租户"这个信息，能被系统深层的代码可靠地拿到？**

答题思路：介绍`contextvars`这个机制——它比"每层函数签名都显式传`tenant_id`参数"更不容易遗漏（任何深层调用都能直接读取，不需要一路透传），又比"用普通全局变量"更安全（按调用链隔离，不会被并发请求互相污染）。如果能补充"后台任务/异步任务的生命周期如果超出创建它的那次请求，需要重新显式声明租户身份，不能依赖隐式传播"这个边界情况，会体现出对`contextvars`底层行为的真实理解，而不只是知道这个工具的名字。
