# 第43章 —— 复杂案例的委派与审批（综合实战二）

代码位置：`examples/products/flagship_support_platform.py`

## 客服机器人不应该什么都自己扛

上一章搭好的骨架，能处理"你好"、"我要退款"这类常规问题。但一个真实的客服系统迟早会遇到超出普通客服能力范围的情况——比如账单纠纷、拒付（chargeback）、涉及法律问题的投诉。这类案例通常需要更专业的判断，而且往往涉及金钱损失，贸然让一个通用客服Agent自己"编"一个解决方案去处理，风险很高。

更现实的做法是：识别出这类复杂案例，**委派**给一个专门处理这类问题的"专家"去处理（可能是另一个更专精的Agent，也可能是真人客服），并且在真正执行委派之前，插入一个人工审批的环节——这一章要看的，正是`flagship_support_platform.py`里"识别复杂案例→人工审批→委派专家处理"这条完整链路是怎么用`ainative-workflow`（DAG工作流）和`ainative-a2a`（多智能体委派）两个包组合起来的。

## 用一个两节点的DAG，表达"先判断，需要的话再等人工签字"

```python
self.escalation_workflow = Workflow([
    WorkflowNode(name="triage", fn=self._triage, output_key="needs_escalation"),
    WorkflowNode(
        name="human_signoff", fn=self._human_signoff, depends_on=("triage",), output_key="signed_off",
        condition=lambda ctx: ctx.get("needs_escalation"),
    ),
])
```

第26-28章讲过的`Workflow`/`WorkflowNode`在这里派上了用场——这是一个只有两个节点的最简单DAG：`triage`（分诊，判断这个案例是否需要升级）先跑，`human_signoff`（人工签字确认）依赖`triage`的结果，而且带了一个`condition`——只有`triage`判断"需要升级"时，`human_signoff`这个节点才会真正执行。

```python
def _triage(self, context: dict) -> bool:
    return any(kw in context["user_message"].lower() for kw in ESCALATION_KEYWORDS)

def _human_signoff(self, context: dict) -> bool:
    if not context.get("human_approved"):
        raise WorkflowPaused(payload={"reason": "escalation requires human sign-off before specialist handoff"})
    return True
```

`_triage`本身很朴素——检查用户消息里有没有出现`ESCALATION_KEYWORDS`（"billing dispute"、"chargeback"、"legal"）这几个关键词。真实项目里这一步通常会换成一个更精细的分类模型，但**这个节点的职责边界很清楚：只负责判断"要不要升级"，不负责"升级之后具体怎么处理"**——这种职责拆分，正是第26章讲过的"用DAG把决策节点串起来"的意义所在：`triage`这个节点未来想换成任何更复杂的判断逻辑，都不需要动`human_signoff`或者整个平台的其他部分。

## `WorkflowPaused`：人工审批不是一个"顺便调用"的函数，而是让整条链路真的停下来

`_human_signoff`里最关键的一行是`raise WorkflowPaused(...)`——第28章讲过的HITL（Human-In-The-Loop）机制在这里的具体应用。这里没有写成"调用一个`ask_human()`函数、同步等待返回结果"，而是**直接抛出一个特殊的异常，让整个工作流在这里真正暂停下来**，把控制权交还给外层调用方：

```python
run = await self.escalation_workflow.run({"user_message": user_message})
escalated = False
if run.is_paused:
    run = await self.escalation_workflow.resume(run, resume_context={"human_approved": True})
```

这个设计背后的考量是：**"等待人工审批"这件事，在真实系统里可能耗时几秒钟，也可能耗时几个小时甚至几天**（人工客服可能正在处理别的工单）。如果用"同步阻塞等待"的方式实现，意味着这次请求对应的整个调用链路（可能还占用着一个HTTP连接、一个进程）要一直挂起，直到人工做出决定为止——这在真实的Web服务里几乎是不可接受的。用"暂停并保存状态、等外部信号触发恢复"这种方式，工作流的执行状态（`run`这个对象）可以被安全地持久化到数据库，原本占用的请求资源可以立刻释放，等真人客服几个小时后真正做出审批决定，再用`resume(run, resume_context={"human_approved": True})`把这个具体的`run`重新接续下去执行。

这个示例本身为了演示方便，用`resume_context={"human_approved": True}`模拟了"人工立刻批准"这个场景——真实项目里，`run.is_paused`为真时应该把这个暂停状态存下来（比如写入数据库、发一条待办通知给真人客服），等收到外部系统真正的审批回调之后，再调用`resume`，而不是像这里这样紧接着立刻恢复。

## 只有真正跑完这条工作流、且确认需要升级，才会真正发起委派

```python
if run.context.get("needs_escalation") and run.is_completed:
    result = await self.dispatcher.delegate(
        capability="resolve_billing_dispute", payload={"case_summary": redacted}, sender_agent=self.agent_name,
    )
    raw_reply = result.output["resolution"] if result.status == "success" else "Escalation failed; please contact support directly."
    escalated = True
```

第29、30章讲过的`ainative-a2a`委派链路在这里被调用——`self.dispatcher.delegate(capability="resolve_billing_dispute", ...)`不是直接调用某个具体的Agent实例，而是按"能力"（capability）去委派，具体由哪个Agent来处理这个能力，是`InMemoryAgentRegistry`在幕后完成的匹配：

```python
self.registry = InMemoryAgentRegistry()
self.registry.register("billing_specialist", AgentCapability(
    name="resolve_billing_dispute", description="Handles complex billing disputes and chargebacks",
))
```

这种"按能力而不是按具体名字委派"的设计，好处在于：如果未来需要新增第二个账单专家Agent（比如按语言分工，一个处理中文案例，一个处理英文案例），只需要在`registry`里再注册一份能力声明，`SupportPlatform`的委派代码完全不需要改动——它自始至终只关心"我需要一个能处理`resolve_billing_dispute`这个能力的Agent"，不关心具体是哪一个。

**留意`payload={"case_summary": redacted}`这一行**——传给专家Agent的是`redacted`（脱敏后的文本），不是原始的`user_message`。这是上一章强调过的"防护顺序不能颠倒"原则的又一次体现，而且这次的场景更值得警惕：**这次传递跨越了一次A2A委派边界**，从"客服Agent自己的进程内"传到了"另一个专家Agent"手里。配套的测试用例专门验证了这一点：

```python
async def test_pii_in_escalated_case_is_redacted_before_reaching_specialist():
    """The specialist agent must only ever see redacted case data — the raw
    user_message (with PII) must never cross the A2A delegation boundary."""
    ...
    specialist_input = platform.specialist.audit_log.all()[0].input_summary["case_summary"]
    assert "13812345678" not in specialist_input
```

这条测试的注释写得很直接："专家Agent只能看到脱敏后的数据——原始的（带PII的）用户消息绝不能跨越A2A委派这条边界。"**任何一次跨进程/跨Agent的数据传递，都应该被当作一次需要重新审视安全边界的机会**，而不能想当然地认为"反正数据在我们自己系统内部流转，应该是安全的"。

## 专家Agent自己的每一次工具调用，都要留痕

```python
class BillingSpecialistAgent:
    def __init__(self) -> None:
        self.audit_log = InMemoryToolCallAuditLog()

    async def handle(self, task: A2ATask) -> dict:
        start = time.monotonic()
        case_summary = task.payload.get("case_summary", "")
        resolution = f"Billing specialist reviewed case and issued a partial refund for: {case_summary}"
        self.audit_log.record(ToolCallRecord(
            tool_name="review_billing_case", agent_name="billing_specialist", status="success",
            duration_ms=(time.monotonic() - start) * 1000, input_summary={"case_summary": case_summary},
        ))
        return {"resolution": resolution}
```

第24、25章讲过的`ainative-mcp`审计记录（`ToolCallRecord`）在这里被专家Agent自己用来记录"我处理了这个案例"这个动作——`duration_ms`、`input_summary`、`status`这些字段，让事后审计（"这个账单纠纷到底是谁在什么时候、花了多长时间处理的，处理时看到的输入是什么"）成为可能。这条审计记录和上面提到的"专家只能看到脱敏数据"这个安全要求，其实是同一件事的两个侧面——**审计记录本身也会成为长期存储的数据，如果传给专家的输入没有脱敏，这条审计日志本身就会变成一个新的PII泄露点**。

## 本章小结

- 客服系统识别出超出常规处理能力的复杂案例（账单纠纷、拒付、法律问题）时，应该走"委派给专家处理"的路径，而不是让通用Agent勉强自己处理。
- 用一个简单的两节点DAG（`triage`判断是否需要升级 → `human_signoff`需要人工确认）能清晰地表达"先判断、再视情况决定是否需要额外审批"这种业务逻辑，且各节点职责边界清楚，互不干扰。
- 人工审批环节用`WorkflowPaused`异常真正让工作流暂停、把执行状态交还给调用方持久化，而不是用同步阻塞等待模拟"等人"这件事——这避免了请求资源被长时间占用的问题。
- 按"能力"而不是按具体Agent名字发起委派，让新增/替换处理某类任务的专家Agent，不需要改动发起委派的那一方代码。
- 任何一次跨越A2A委派边界的数据传递，都要重新审视一遍安全边界——原始的、未脱敏的数据不应该跨越进程/Agent的边界，即使是在同一个系统内部流转。
- 专家Agent处理任务时产生的每一次工具调用，都应该被审计记录下来，但这条审计记录本身同样要遵守"不能带着未脱敏的敏感信息落盘"这条原则。

## 动手做

```python
import asyncio
from products.flagship_support_platform import SupportPlatform, fake_llm_respond

async def main():
    platform = SupportPlatform()

    # 一次普通对话，不涉及升级
    turn1 = await platform.handle_turn("user-1", "Hi, I'd like a refund.", fake_llm_respond)
    print(f"[普通对话] 是否升级: {turn1.escalated_to_specialist}")

    # 一次带有敏感信息、且触发升级关键词的对话
    turn2 = await platform.handle_turn(
        "user-1", "My phone is 13812345678 and I want to file a billing dispute chargeback", fake_llm_respond,
    )
    print(f"\n[复杂案例] 存储时已脱敏: {turn2.redacted_for_storage}")
    print(f"[复杂案例] 是否升级给专家: {turn2.escalated_to_specialist}")
    print(f"[复杂案例] 专家回复: {turn2.bot_reply}")

    # 验证专家审计记录里，看不到原始手机号
    audit_records = platform.specialist.audit_log.all()
    print(f"\n专家审计记录数: {len(audit_records)}")
    print(f"审计记录里的手机号已脱敏: {'13812345678' not in str(audit_records[0].input_summary)}")

asyncio.run(main())
```

## 面试可能会问

**问：如果一个AI客服需要在处理某类案例前引入人工审批，你会怎么设计这个"等待人工"的机制？**

答题思路：先排除"同步阻塞等待"这种做法——人工审批可能耗时几秒到几天不等，长时间占用请求连接/进程是不现实的。正确的思路是让整个处理流程能够"暂停"：把当前执行到哪一步、已有的上下文数据完整保存下来，释放掉这次请求原本占用的资源，等外部系统（真人客服提交了审批意见）真正给出信号后，再用保存的状态把流程接续下去继续执行。可以提到用DAG/工作流引擎配合一个特殊的"暂停"信号（比如一个专门的异常类型）来实现这一点，好处是"判断要不要审批"和"审批之后具体怎么处理"这两个职责能保持清晰分离。如果能补充"任何一次涉及委派给其他子系统/子Agent的场景，都要重新检查一遍数据是否已经脱敏"，会展现出更全面的安全意识。
